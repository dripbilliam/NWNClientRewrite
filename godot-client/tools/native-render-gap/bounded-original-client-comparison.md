## Bounded findings and next evidence

1. **Main iteration is the first measured constraint in these windows.** World and rig callbacks are visible contributors, but most of the 17.36 ms busy-window main time remains unassigned by the selected source zones. A main-thread hierarchy/call tree for that exact window is needed before selecting a large rewrite.
2. **Render submission is a second substantial cost.** The ~5 ms render-thread zone is CPU time and overlaps the main thread. Collect actual 3D draw calls, visible instances, material switches and GPU timestamps in the same view to distinguish renderer submission from GPU execution or viewport overhead.
3. **The original BSP/bucket path and the client scene path differ structurally.** The mapped original culls before bucket admission; the client has Godot visibility and selective batching. A matched original/client scene census, rather than static call counts, is needed to determine whether this difference explains the reported 2–3× frame-rate gap.
4. **Do not use this frozen trace to accept today's source.** First complete NWN-75's remaining branches, then make the full dependent comparison. If a new FPS capture is requested while the original-tree agents run, pause their work for the measurement as agreed.

## Direct request-to-ready comparison — 2026-11-12

This is a bounded structural comparison requested before completion of NWN-75. It does **not** establish equal throughput or quality between clients. The original map is [model instance](../nwn75/model-instance-branch.md), [resource storage](../nwn75/model-resource-storage.md), and [texture publication](../nwn75/texture-publication-per-frame.md). The client route is `systems/native_render/{area_stream,object_stream,creature_stream}.gd` → `systems/native_data/{asset_service,resource_catalog}.gd` → `systems/native_render/{resource_pool,model_template,model_instance}.gd`.

| Stage | Installed original | Current client | Finding |
| --- | --- | --- | --- |
| Request and source bytes | `NewCAurObject`/`LoadModel` → `IODispatcher::ReadSync` → installed `AurGetResource` → `CRes::Demand`, resident bytes or storage classes 1/2/3/5. `FindModel` can reuse a global Model before parsing; ordinary `LoadModel` also has a parse-then-deduplicate route. | Area, object and creature streams group requests by model/specification. `AssetService::request` enqueues up to 128 pending/running jobs and dispatches at most four active workers. Each `_work` calls `catalog.get_resource`, computes a source SHA-256, then checks memory/prework/decoded caches before or during parsing. The catalog itself caches/coalesces source bytes. | Both reuse source/model data, by different ownership schemes. Hashing and cache validation are additional client work on each submitted job. No matched native/client timing for this stage is available. |
| Decode and texture dependency | Original parses a text or binary Model, creates typed `MdlNode` data, and initializes material texture **references**. `AurTextureMakeCurrent` walks pending textures; `BuildAndStoreTexture` is built/image-state gated. | Asset workers parse models, prepare mesh/skin/animation data, enumerate every renderable mesh's texture names, read and decode their rasters, and return a bundle. On main-thread publication, `ResourcePool.prepare_texture` creates an `Image` and `ImageTexture` on a cache miss. | The client deliberately prepares texture dependencies before first visible draw, including assets that may never enter view. Native image/GL publication is pending/first-use gated. The number and cost of unused client textures in a live area have not been measured. |
| Scene object preparation | A parsed Model is shared; `NewCAurObject` creates a Gob and recursive typed Part tree, runs postprocess and initializes materials. | A worker bundle reaches a synchronous main-thread `completed.emit`. `ModelTemplate.build` creates a Godot `ModelInstance`, then a fresh root, reparents its parts, and by default calls `PackedScene.pack`; subsequent placements instantiate or clone that template. The recipe/cooperative path is opt-in (`--model-template=recipe`, or a configured cooperative pool). | The Godot node/scene conversion is a concrete extra preparation stage. It can save repeated construction on later placements, so its total value depends on reuse. The 2026-11-11 diagnostic report recorded one `PackedScene.pack` at **43.136 ms** inside a **44.404 ms** template build; that is a main-thread publication spike, not a native/client matched delta. |
| Cache lifetime and repeated preparation | Resident CRes and global Model/texture tables are gated in the mapped paths; their full runtime eviction policy is not yet established. | `ResourcePool` retains at most 512 template, 4,096 mesh, 512 texture and 2,048 material **bindings**, while live scene references may survive eviction. The 2026-11-11 three-area diagnostic report records 402 template, 3,513 mesh and 619 texture evictions. | Eviction permits repeated work when an identity is requested again. These cumulative counts do not prove same-area thrashing or a per-frame FPS cost. |

The [direct original constructor test](original/constructor-runtime-test.md) subsequently observed `NewCAurObject` build the same installed tile twice in one native process, with distinct Gob pointers sharing one Model pointer. Its debugger-step wall times are too intrusive and variable for a numeric native/client speed ratio. They do confirm the native ownership and reuse pattern on a real tile; the separate Godot headless model-prep experiment below remains a client-only comparison.

The diagnostic report is `reports/native-tracy-frametime-20261111-live-a.native.json`; it belongs to the private project frozen for that capture, whose source differs from the current workspace. In its heavy 60–70 s window, asset polling and object/creature/terrain publication together averaged about **0.66 ms** of an **18.86 ms** main interval ([review](../../.cache/native-tracy/arelith-review-cache-a/newestertrace-review/REVIEW.txt), [window data](../../.cache/native-tracy/arelith-review-cache-a/newestertrace-review/extra-review.json)). The later `thenewone` trace recorded zero mean asset calls in its selected busy windows. These observations make load/publication a demonstrated **hitch** path and a weak explanation for the sustained threefold FPS gap in those windows. They do not show that the client prepares assets as fast as the original.

The strongest concrete client-side preparation cost to revisit is synchronous default template packing and publication. The strongest unquantified structural difference is eager raster preparation before draw. A measured per-resource census of requested, decoded, published, first-drawn and evicted identities would decide whether this preparation is wasted in the active area. A native timing/profile for the same area is still required for a speed ranking against the installed binary.

## Direct Part-tree component experiment — 2026-11-12

`tests/nwn75_direct_model_prep_benchmark.gd` compares three **client** ways to publish one already-decoded installed original tile (`tcn01_a01_01`, fixture SHA-256 `aa449ce06d8fb14a47296edc968de5232efe99080ee1ab7662ad374eb69db6d6`): the default PackedScene template, a fresh `ModelInstance.install` Part tree for every placement, and the existing known-node recipe template. Each leg uses a fresh `ResourcePool`; 32 placements stay alive until the leg ends. The packed/direct/recipe/recipe/direct/packed order controls some temporal drift. First and last placements must match on physical Part names, parents, transforms, mesh surface byte hashes, bounds and reference counts. The [report](../../.cache/nwn75/direct-prep-d.json) passed this structural check.

| Client path | First placement, two legs | 32 placements, two legs | Mean repeat placement |
| --- | ---: | ---: | ---: |
| PackedScene template | 5.55–7.42 ms | 17.19–19.42 ms | 0.37–0.39 ms |
| Fresh direct Part tree | 5.34–5.94 ms | 57.65–61.26 ms | 1.69–1.78 ms |
| Known-node recipe | 8.17–8.80 ms | 40.12–40.94 ms | 1.03 ms |

For this 26-node/21-mesh/8-texture tile, skipping template creation can help a *single* placement, but a direct GDScript Part tree is much slower after reuse. The PackedScene route wins by four placements in three of four A/B checks across the [earlier 4-leg run](../../.cache/nwn75/direct-prep-c.json) and the 6-leg run; the exact crossover varies with warm-up. The recipe genuinely skipped packing and shared cached GPU resources, but its scripted clones cost more total CPU than PackedScene instantiation here. This is **not** a benchmark of the original binary's compiled Part constructor, actor/skin models, resource I/O, GPU pixels, live scene admission or FPS. It does not justify replacing the production template route globally. A model-use-aware direct option for rare one-off statics remains a candidate for a visual and live acceptance test.

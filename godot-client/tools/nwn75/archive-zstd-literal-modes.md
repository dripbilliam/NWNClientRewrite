# NWN-75: Zstd compressed-block literal modes

Pinned installed `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This is a conditional descendant of the [XRES algorithm-2 frame path](archive-zstd-frame-sequence.md): ordinary frame block type 2 enters `ZSTD_decompressBlock_internal 0x1409e9120` at `0x1409e982d`, which calls the literal parser `FUN_1409e8740` at `0x1409e9166`. It maps the other literal modes and the single-stream/table-reuse choices; it does not establish which installed resource uses them.

The literal section requires at least three input bytes before reading `(first_byte & 3)`. **Type 0 raw** parses a one-, two- or three-byte header (header size bits `first_byte >> 2 & 3`). The declared literal size and header must fit the remaining compressed block. If there are at least eight spare bytes after that payload, the parser keeps a borrowed pointer into the input at context `+0x7118` (`0x1409e8a2b`–`0x1409e8a32`). Otherwise it calls CPU copy `0x140c417f0` at `0x1409e8a02`, stores the owned context workspace pointer at `+0x7118`, length at `+0x7138`, and writes eight trailing zero bytes. Thus the raw mode can avoid a copy, but only under the size gate. Evidence `ev_f8597d1eafc0754171b93f813b895889659d0a80fa0c95d5dbb6625142e9184b`.

**Type 1 RLE** parses the same one-/two-/three-byte size shape, rejects a decoded size above `0x20000`, and requires one payload byte. It calls CPU fill `0x140c42060` at `0x1409e897f` to write that repeated byte for the declared size plus eight sentinel bytes in context `+0x71d0`, then records workspace pointer/declared length at `+0x7118/+0x7138`. The fill itself is the previously verified CPU-store helper; it is not a GPU operation. Evidence `ev_f8597d1eafc0754171b93f813b895889659d0a80fa0c95d5dbb6625142e9184b`, `ev_5274015a3873f341153bd9c8ab6afa941edf9c5a4e3b4a3e52cdf0f56ed012f2`.

**Type 2 Huffman-new** and **type 3 treeless** parse compressed and regenerated literal lengths from a three-, four- or five-byte header. Type 3 requires the prior table-valid flag at context `+0x70a8` before decoding; type 2 can install a new table at `+0x18` on success. Both require encoded bytes and decoded size `<=0x20000`. Header layout selector zero chooses one stream. Type 2 calls `HUF_decompress1X1_DCtx_wksp_bmi2 0x140a1fc90` at `0x1409e88b7` (table read then `HUF_decompress1X1_usingDTable_internal 0x140a1fd70` at `0x140a1fd06`). Type 3 calls `HUF_decompress1X_usingDTable_bmi2 0x140a207b0` at `0x1409e8865`; its installed table-format flag chooses X1 `0x140a1fd70` at `0x140a207da` or X2 `0x140a20220` at `0x140a207d0`. Their direct byte/word stores reach context literal workspace. For nonzero header layout, type 2 selects the existing new-table four-stream Huffman path at `0x1409e88be`, and type 3 selects the reused-table four-stream dispatcher `0x140a22eb0` at `0x1409e8873`. That dispatcher chooses X1 `0x140a20a90` at `0x140a22eda` or X2 `0x140a219a0` at `0x140a22ed0` from the table-format flag. The X2 body validates four stream starts/lengths and directly writes decoded words/bytes into the context workspace, including `0x140a21b92` and `0x140a221b9`; the X1 body is covered in the [frame/sequence note](archive-zstd-frame-sequence.md). On a successful literal parse, the compressed-block decoder calls sequence-table parser `0x1409e8a50` at `0x1409e9189`, then chooses ordinary `0x1409eac80` at `0x1409e9241` or its large-window/batched alternative `0x1409e9c60` at `0x1409e921f`. The ordinary path reads context `+0x7118/+0x7138` literals, writes literal and match bytes into the provider output, then the frame/provider/service acceptance gates from the linked frame note apply. Header mode, previous-table availability, X1/X2 table format, stream shape, sequence mode, output length and later resource/render use are runtime-dependent. The [batched sequence executor](archive-zstd-large-window-sequences.md) is mapped separately; rare Huffman error/near-end arms remain open.

# NWN-75 native server resource-file batch continuation

Pinned `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This continues the connected client resource dispatcher `0x1407a41a0` → `0x1407ab2f0` for major `0x34`, minor `5`. It records the original binary's conditional work, not a claim that a packet arrives during a particular frame. The independent minor-1 override and minor-4 refresh routes are in [server override/refresh](server-resource-override-refresh.md).

The minor-5 body reads a request DWORD and a WORD entry count. Each entry reads a `CResRef`, resource type, operation DWORD and, for operations other than `1`, flags, byte length and a byte pointer from `CNWMessage`. It strips nonalphanumeric characters from the resref and forms `TEMPCLIENT:%s`. Message overflow exits the entry processing. The `TEMPCLIENT:` key table is added at priority 99,000,000 during conditional default search-path setup, as documented in [key selection](resource-key-selection-object-ownership.md). The exact packet fields and whether the table exists remain runtime dependent. Handler pseudocode `ev_37757f2819fa72a5d8e721ac08c673a2dbf278ea43b4839484ff45e22ec0830f`; dispatch `ev_da80319219c32a6591ef7bcccbf62897fbddc07f8be8afe8388140ae740bc846`.

When operation equals `1`, the handler calls `CExoResMan::RemoveFile` `0x140191460` at `0x1407ab537` and records one result byte. `RemoveFile` resolves the alias, checks the path with `_stat64i32`, changes mode and invokes the import labeled `_rmdir` by Ghidra; the exact filesystem result is conditional. That imported label should not be generalized into a proven successful regular-file deletion. The non-removal branch reads the payload and optionally a SHA1. With the hash flag, it may reuse NWSync resref data through `HasResRef` `0x1401b1a00` and `GetResrefData` `0x1401b1810`; otherwise it computes SHA1 over the supplied bytes. A zero length or hash mismatch emits an error status rather than publication. The handler's decompiled SHA1/local-variable expression is ambiguous, so the precise reuse predicate remains unresolved. `RemoveFile` evidence `ev_2e6ee8f82c934caaf7939e1265719aaab74217b7c646dabea4e162bf04dead9c`; handler evidence above.

For a payload admitted to the next step, the handler constructs a `DataBlock`, appends bytes and queues a `ResRefBatchInsertEntry` in a local vector. It also opens the named `TEMPCLIENT:` file through `CExoFile` and writes the bytes with `fwrite` under `FileOpened`. The opened branch records its status without checking the `CExoFile::Write` return value, so the status alone does not prove a complete write. The `CExoFileInternal` constructor resolves the alias and invokes its C runtime open wrapper; these are the installed binary's filesystem boundary. `CExoFile` constructor `ev_1f25c19aa86b1f5e2c036ed28ae279c36be87947c7870f207c8dc8280746e02c`, internal constructor `ev_5ae78204d1a8f1082d99061d0b46275a68cf277bebd7b66a755c79d804b0e221`, write `ev_0321a931d0157561825983869b180210c9ed0f4b5c7b26c319beefdabd8168ea`.

After the entry loop, a nonempty local batch is passed to `NWSync::CNWSync::BatchInsertResRefData` `0x1401b1130` at `0x1407abb14`. Its `EnsureReady` can join NWSync initialization before the call proceeds. The internal `0x1401c07a0` calls provider virtual `+0x20`; the installed `SQLiteStorageProvider` constructor/vtable route to `Store` `0x1401c6240` and `StorageShard::Store` `0x1401c67c0` is separately pinned in [task-pool ownership](task-pool-ownership.md). This handler uses the direct batch call, not that document's separate `BatchInsertResRefDataAsync` task producer. The storage leaf compresses and binds/executes SQLite records under provider and shard gates. Batch wrapper `ev_e4d602090fb43a9190822ea91ec565c1250d2b01f27b4d0e33cb73caf41a0ea1`, internal virtual call `ev_7efb2e9c428baa6b44afad7d72556603c8449413997a037ceb51fe626d7c1b58`, shard leaf `ev_6ebdbffe4ca801e4a48d2098cf355924e39ee5f7b56f0618af95fd86647409f2`.

If any file operation changed the TEMPCLIENT directory, the handler calls `UpdateResourceDirectory` `0x140195d70` at `0x1407abb80`. It selects the matching directory key table and calls `RebuildTable` `0x14018ccf0` at `0x140195d44`. Rebuild transfers matching resident `CRes` objects to new entries, resolves missing entries against the ordered key tables, dumps idle resources or flags demanded resources for deferred invalidation, and can take a higher-priority source. Thus the packet can change later resource lookup and draw publication without itself drawing. The handler finally writes request ID and per-entry status bytes into a major-`0x34`, minor-`6` response and calls `FUN_1407c25c0` at `0x1407abc39`; that path reaches `CNetLayer::SendMessageToPlayer` at `0x1407c2a7f` under connection/window gates.

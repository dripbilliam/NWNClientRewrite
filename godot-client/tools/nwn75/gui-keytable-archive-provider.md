# NWN-75: GUI demand through a key-table archive provider

Pinned original `nwmain.exe` SHA-256: `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. Addresses are PE virtual addresses. This supplements [GUI resource demand and decoders](gui-resource-demand-decoders.md) with a producer-to-consumer proof for the **source-1 resource-file** branch. It maps one conditional plain-entry read to a CPU copy or Win32 file-read boundary. Source-2 encapsulated archives, compressed entries, active resource ids and actual cache state remain separately conditional.

## Provider construction and selection

`CExoResMan::AddFixedKeyTableFile` `0x14018e300` calls `AddKeyTable` `0x14018e330` at `0x14018e31d` with source kind `1`. `AddKeyTable` allocates a `CExoKeyTable` and calls `BuildNewTable` `0x14018a690` at `0x14018e643`; that function stores source kind `1` at key table `+0x20` and tail-jumps from `0x14018a7e4` into `AddKeyTableContents` `0x140189280`. The contents builder validates/open-reads key-table headers and, on the successful allocation path, creates each resource-file object with `CExoResFile` vtable `0x140da1298` (LEA `0x140189bfc`, store `0x140189c03`), publishing it in key-table object array `+0x50` at `0x140189c25`. Failed header, allocation, or resource-file initialization exits do not publish a usable provider. REA `ev_a44601c4e5ed6f2d7fb331c228460867899b6b0a1741418f1d09bfd1a0753012`, `ev_652d2dcb5b939b47323364a97ccdd2b3bd61da5974790b9ed8402d26f4177214`, `ev_1dd4f6bac4dda2a6bb0c70104b78d81b8c47b42ce3a197bc235712dafb6b1d78`, `ev_ffa50a0fd15bf25365580d95f744df19cc0d1e023d350bfc15c4970f43fdc11b`.

At demand time `CExoResMan::Demand` `0x14018ef90` selects source kind `1` and calls `ServiceFromResFile` `0x140193b80` at `0x14018f276`. That service rejects a null resource or a marked already-serviced one, finds a manager key table whose id `+0x48` matches `CRes+0x14`, and selects the indexed provider from key table `+0x50` using `CRes+0x10`. It calls provider virtual `+0x28` for size, allocates the resource buffer, then calls provider virtual `+0x40` at `0x140193ed3` to fill it. The pinned `CExoResFile` vtable has `+0x28` → `GetResourceSize` `0x14018b250` and `+0x40` → `ReadResource` `0x14018cb80`. Therefore a provider built by the source-1 contents path resolves this virtual read target to `CExoResFile::ReadResource`; which table/index a particular GUI asset chooses is runtime data. A complete read is required before the resource's serviced hook runs. REA demand `ev_5d7c92d55b6cd5dcc52fae8cadb9fc10e71b7c4d0aa03060a91a32c581d0f472`, service `ev_ef4e9e25f3e8f1ca5d917424c4353734e1f1a363f93fef6f9079960620478436`, vtable bytes `ev_db595f7c6cc62ebf57313ccc502cab7d9f437252cf45e6a59e4b7260c9441c09`.

## Plain entry to CPU or file boundary

`CExoResFile::ReadResource` `0x14018cb80` first requires open archive state at `+0x2c`, a nonnull destination and an index below the archive entry count. It calls `CExoFile::Seek` at `0x14018cbe2` to position at the entry offset. Entry compression flag `1` goes to `CExoPackedFile::ReadNWCompressedBuffer` at `0x14018cc0a`, the distinct decoder path already mapped in the GUI decoder supplement. A **plain** entry calls `CExoFile::Read` at `0x14018cc34` when caller capacity is smaller than stored entry size (truncated request), or at `0x14018cc71` for the full stored size. Either read must return the requested count; short reads log and fail this service. REA `ev_ca2a0df5c75f71854418245e895d5797b76aea5db4aa662d2b3b08938b2832c0`.

`CExoFile::Read` `0x140166ca0` loads its internal object and tail-jumps at `0x140166ca4` to `CExoFileInternal::Read` `0x140167c60`. Generic internal mode `2` clamps length to its memory-backed range and calls the CPU copy routine `0x140c417f0` at `0x140167ca7`, then advances its cursor; this is a no-file-read leaf if that mode is active. The file-stream mode instead calls `fread` `0x140c7e2a0` at `0x140167cdb` and returns bytes read. `fread` → `fread_s` → `_fread_nolock_s` at sites `0x140c7e2b3`, `0x140c7e350`. `_fread_nolock_s` can copy available CRT buffer bytes without an OS read; on its direct large-read branch it calls `_read_nolock` `0x140ca7764` at `0x140c7e1e6`. For a file handle, `_read_nolock` reaches imported `KERNEL32.DLL::ReadFile` through cell `0x140d7c678` at `0x140ca7a53`; console, error, EOF and text translation paths are separate gates. Thus `ReadFile` is a conditional external boundary, not a per-demand guarantee. REA internal read `ev_1c8aec1da419d7171a77c8834e685c8e89f354ce81a9ad6c076671c9b2e1ee77`, CRT read `ev_d7558fd4a8c2fe6fd26e41f2002c4503386159ffb7bbd661b6ac0ebeafeabb45`, Win32 read `ev_3c7dede7cc27d86ab2b6fb25341355a9c378d85955a370eb8762b08dc7672583`, import identity `ev_73f3133af47e1d6740ec716e18e6903b62bb0f0f084a6bcb07c5a709ecfce4e8`.

## Bounded frontier

This proves the source-1 built-in provider class and one plain-entry read route. It does not determine a GUI asset's active `CRes` source selector, table/index, archive entry compression flag, CRT buffer contents or successful byte count. A runtime table mutation or nonstandard provider object would change the virtual target; no such mutation is claimed here. The compressed source-1 branch remains with the provider/decoder map, and source-2 encapsulated and JPEG internals remain separate branches.

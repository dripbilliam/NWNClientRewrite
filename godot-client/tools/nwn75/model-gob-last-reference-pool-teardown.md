# NWN-75 model Gob last-reference pool teardown

Pinned original `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This follows a bounded model lifetime after [Gob model construction](gob-lod-scene-publication.md) and [model parser storage](model-name-parser-tree.md). It connects one admitted ordinary TriMesh source-node destructor to the already mapped pool/buffer release leaf. Exact direct sites are in the ledger.

`NewCAurObject` `0x1400931f0` retains the selected primary Model at Gob `+0x68`, with optional alternate Models at `+0x70/+0x78`; assembly at `0x140093613..0x140093637` increments each nonnull Model `+0x94` reference count. It creates corresponding Part trees at `0x140093645/0x140093677/0x1400936a9`. `Gob::~Gob` `0x1400889c0` first raises `Dying`, clears animation and Scene membership, then destroys its owned Part tree before releasing Model references. Its auxiliary Model array `+0x120/+0x128` and each of `+0x68/+0x70/+0x78` decrement `Model+0x94` inline, calling `MaxTree::operator_delete` at `0x140088b14`, `0x140088b46`, `0x140088b5e` or `0x140088b76` only when the new count is zero. The two standalone `Model::DelRef` overloads `0x14008dd20/0x14008dd50` use the same zero-count delete target; the Gob destructor uses its own inlined decrement. The Gob-pointer overload has only two incoming DATA references in the REA census and no proved direct in-image caller, so it remains an alternate disconnected source in the ledger. One Gob deletion therefore does not prove Model/node/pool deletion while another owner retains the Model. For a positive Model-kind object, `MaxTree::operator_delete` `0x14008a070` invokes its object destructor, reads its root node at `+0x50`, and selects a node destructor from the node-kind bits at root `+0x98`. An ordinary TriMesh with low-bit pattern `0x21` reaches `MdlNodeTriMesh::~MdlNodeTriMesh` `0x1400896c0` at `0x14008a26f`; other node types take distinct branches. The TriMesh destructor releases its optional postprocess helper, its optional pool handles and each handle in its variable pool list. Fifteen callsites enter `RenderInterface::DeletePool` `0x1400be990`, including an unguarded `+0x280` call whose callee rejects sentinel `0xffffffff`. It also frees its face/array storage and invokes the base node destructor. This source-node cleanup occurs after the Gob Part root is destroyed in the examined Gob path. A retained shared Model or different root subtype bypasses this particular TriMesh destructor route. Evidence: `ev_8045101cb398e0fa3e39262bf4ded402593d45e4547e131664247298b13811b6`, `ev_ea3d3a0d3afd8528c2679c1b13f996256def9e5384cf716a3dc2a20bb2612922`.

`RenderInterface::DeletePool` is a jump to `GLRender::DeletePool` `0x1400afd20`. With a valid pool ID it adds the ID to a reusable list, subtracts its recorded bytes from `totalmempool`, and frees CPU pool storage. Only a pool record with GPU-backed flag `+0x19==1` calls `RenderInterface::DeleteBuffer` at `0x1400afd8f`; that previously mapped wrapper/GL leaf can reach extension `glBindBuffer`/`glDeleteBuffers`. Model reference count, root/child node kinds, valid pool handles and GPU-backed flags remain runtime selectors. This map does not infer how often Gobs or Models are destroyed in a live scene.

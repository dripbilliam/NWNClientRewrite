# Original item icon presentation path

Scope: installed `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. Addresses are image virtual addresses. REA/Ghidra pseudocode is derived from the binary, not original source.

1. `CNWItem::UpdateIcons` at `0x14083f6f0` reads its base-item record and item-dependent parts. Depending on that record, it selects a simple `CGuiIcon`, `CCompositeIcon`, `CLayeredIcon`, or `CArmorIcon`. It checks resource existence and constructs the selected icon at item offset `+0x238`, releasing the previous icon there. It also updates stack-count text. Evidence: REA `ev_4d222a6b2b39bef78897f04743935db82f0202aecb3958a3b9f9bd3721a1a506`.
2. The four icon constructors at `0x1401e2f60`, `0x1401e2e40`, `0x1401e3000`, and `0x1401e2ca0` store resource references, dimensions, colors, and layer data. Their observed direct calls do not load image pixels or upload a texture. Evidence: REA `ev_4f5e2b1d7cd1507e127a577746d87d1e307005238147359136763c1a31c4baed`, `ev_76bd440fbc1dd23f3506c543121734d1eea3b5e6cea6a216dd5e8a2d21ad2477`, `ev_950b176b95923235341f4b21d3d67ebe1921187881083573ac7a7c6edc33e7bd`, `ev_56b7ce2861c8fa3a651724f429469e11a1d1405d614848d27f6ec99b5a0b6b84`.
3. `CGuiIcon::CreateCopyIconModel` at `0x1401e3b00` creates a `GUI_ICON_%dX%dL` model, replaces `gui_replace01` with the item's selected icon resource, and assigns texture attributes `icons`. `CCompositeIcon::CreateCopyIconModel` at `0x1401e3930` creates `GUI_ICON_%dX%dLC` and sets `gui_replace01/02/03` in order. `CLayeredIcon::CreateCopyIconModel` at `0x1401e3c80` creates `GUI_ICON_%dX%dL` and uses the palette-aware model slot `+0x58` for `gui_replace01`. `CArmorIcon::CreateCopyIconModel` at `0x1401e3920` enters `LoadArmorLayeredIconModel` at `0x1401e4470`, which creates `GUI_ICON_ARMR%dL`, binds up to six available component resources through that palette-aware slot, and assigns `icons` attributes to each. The simple and composite branches use model slot `+0x60` for the named texture replacement. Evidence: REA `ev_f592b316b6669f7e425b4ebc1a2bd929d6a3b62543a862274e46b479e5e8e78f`, `ev_4c034ff1eb08ec94ee30566ca59c0af529fd59e4e731c6a817647fa5092332a6`, `ev_71db9e9b2cf3f76653e4a2f48a3153cb5fbd7513073f4b388f432959e32bf125`, `ev_814fc3e8b52253262823b5a901a0c00d08c64058017ca7c095767a09618c0ecd`, `ev_a8fd2bfd659b91307baf594603d4ec5b3804cf4256f6a4d490af48caad35a76e`.
4. The resulting model follows the shared GUI scene/model draw route and texture acquisition described in [GUI presentation](gui-presentation.md) and [texture acquisition](texture-acquisition.md). This connects item-specific icon selection to the render tree, but does not establish the first callsite for every inventory widget, active runtime icon count, or whether a given image was already resident when that widget opens.

The observed item constructor path does not contain an all-icons startup preload. This is a bounded statement about those functions, not proof that no other native startup code warms textures. The separate texture-acquisition map documents named texture reuse and conditional build/upload; it does not establish that every item image is resident before the main menu. The inventory control at `0x14087f640` actually attaches the icon Gob to its model and repositions it at the grid cell. Its parent's GUI scene carries the icon into the ordinary scene-camera draw path. This is detailed in [the native item-icon render tail](../nwn84/native-icon-render-tail.md). Runtime first-draw residency and every other UI attachment remain to be verified.

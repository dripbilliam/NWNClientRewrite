# File-backed 16-bit image and header fallback

Pinned original `nwmain.exe` SHA-256: `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This maps the initial file callback and its separate header-only sibling; exact edges are in [the ledger](texture-file-4pc-image-header-ledger.json). The installed Aurora resource-backed 4PC/TGA callbacks are mapped in [4PC/TGA publication](texture-4pc-tga-resource-publication.md). Runtime callback state determines which route is active.

`AurGetImageWrapper` `0x1400e5c60` first offers the compressed callback if enabled. If that returns null or is disabled, it calls cell `AurGet16bitImage` `0x14128ede0` at `0x1400e5e66`, setting bytes per pixel to two. The shipped cell points to `ImageRead16bit` `0x140072b00`; on a null result the wrapper tries `AurGetRaster` at `0x1400e5e92`. Thus the 16-bit route is a conditional CPU source for the already mapped `CAurTextureBasic::ConstructImage` and later texture publication. Evidence wrapper `ev_daa23b7c38295e4fe0523577c3b90af43def7f2a5e52696ec8b0c3a48dae14eb`, shipped pointer `ev_771dad8df7e92f00b6135fcffa168e7d0aa4941111c1d72c8241d5eda0d52bd1`.

`ImageRead16bit` initializes a 256-byte local path, copies at most 255 input bytes, and attempts CRT `fsopen` on the supplied name at `0x140072b6c`. If it fails, it appends `.4pc` and retries at `0x140072ba9`; failure returns null. On an open file it issues four 4-byte `fread` calls at `0x140072bc9/bdd/bf1/c05` for width, height, alpha-like float and format-like integer, allocates `width × height × 2` bytes at `0x140072c15`, reads that payload at `0x140072c33`, calls `fclose` at `0x140072c3b`, and returns the allocated pointer. The decompiled body does not check the four read counts, payload read count or allocation result before passing the destination to `fread`; the loaded values and error behavior remain input-dependent. The direct body has no GL call. Evidence `ev_1896df4a23b979023a40c210bd36a4f9f3ed6d0e6ce9c34f6cf9bdd24449f607`.

The separate `ImageRead16bitHeader` `0x140072c70` uses the same initial-name then `.4pc` open sequence at `0x140072cda/0x140072d18`, reads the same four 4-byte fields at `0x140072d34/d48/d5c/d70`, closes at `0x140072d78`, and returns one on open success without allocating or reading pixel bytes. `AurGetImageHeaderWrapper` `0x1400e5b90` tries KTX/S3TC headers when compressed inspection is enabled, then calls this header function at `0x1400e5c20`, falling back to raster-header callback if it returns zero. `CAurTextureBasic::LoadImageHeader` `0x1400ec900` also invokes it directly for indexed multi-image names at `0x1400ec9d7/0x1400eca3c`, accumulating heights. Ghidra lists only data references into `LoadImageHeader`, no direct code caller, so a live invocation and relationship to any specific frame remain unproved. Evidence header `ev_06521f83a477d22c39f9e4af5f46d68df127441c2efaee9c196b5fb4162d957b`, wrapper `ev_614a88c60a8470943cd4a9dc3dfc2ab8246bc9f52d7fd0001aaf14c54c684ce3`, Basic method `ev_188251d8dde193c12b22b6f925a8d47e1a5bbc35c221e146c0085999790e07de`.

Both file routines use the shared CRT chain: `fsopen` to conditional imported `KERNEL32.DLL::CreateFileW`, `fread` through buffered `_fread_nolock_s` or conditional imported `KERNEL32.DLL::ReadFile`, and `fclose` to conditional imported `KERNEL32.DLL::CloseHandle`. Exact lower calls and gates are in [archive open/close](archive-open-close-header-loading.md) and [file resource read](model-resource-storage.md). A successful full-image buffer belongs to the CPU Basic image path and can later be released by its ownership-mode [FreeImage](texture-consumer-binding.md) route; header-only reads publish only scalar metadata. These calls inherit the texture caller's thread and show no worker handoff. Callback replacement, authored name, actual file selection, CRT buffering, header validity, GPU upload and Scene visibility remain dynamic.

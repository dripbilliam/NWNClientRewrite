# NWN-75: XRES Zstd raw and RLE block output

Pinned installed `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This follows the two noncompressed Zstd block types left separate by the [compressed-block branch](archive-zstd-frame-sequence.md). It remains a conditional XRES algorithm-2 path from a source-1/source-2 archive entry; it does not identify which installed assets select these blocks.

The existing archive chain admits a compressed entry, validates XRES version 3 with algorithm 2 and Zstd inner version 1, and calls `ZSTD_decompressDCtx 0x1409e9670`. That reaches `ZSTD_decompressMultiFrame 0x1409e9950` at `0x1409e968f` and, for an ordinary frame, frame decoder `FUN_1409e96a0` at `0x1409e9bd6`. The frame decoder validates its header/dictionary state and reads a three-byte block header at `0x1409e97ba`–`0x1409e97d2`. Bit zero is the last-block flag; `(header >> 1) & 3` selects type 0 raw, type 1 RLE, type 2 compressed and type 3 invalid. A type-3 block returns error `-0x14` at `0x1409e98d0`. Evidence `ev_2b732628dea318d42019c894c2c36d7ea3b2f7f9289de399eb4b99d2caf270ec` and original instruction sites.

For type 0, header `>>3` gives both payload and output length. The decoder requires the full payload to remain in input at `0x1409e97fa`, then checks output capacity at `0x1409e985c`; on success `0x1409e986e` calls CPU copy `0x140c417f0` from input payload to the caller's output buffer. For type 1, only **one** input byte is required, while header `>>3` is the output length. It checks that byte at `0x1409e97fa` and output capacity at `0x1409e983d`, then `0x1409e984f` calls `FUN_140c42060` to fill the output buffer with that repeated byte for the declared length. The fill body performs CPU byte/vector stores and has no graphics call. Both paths reject short input or insufficient output before copying/filling; the ordinary type-2 branch instead enters the separately mapped entropy/sequence decoder. Evidence: frame `ev_2b732628dea318d42019c894c2c36d7ea3b2f7f9289de399eb4b99d2caf270ec`, fill `ev_5274015a3873f341153bd9c8ab6afa941edf9c5a4e3b4a3e52cdf0f56ed012f2`.

After either output branch, the decoder rejects encoded error-size values at `0x1409e9876`. If the frame checksum flag is set, it updates XXH64 over the just-produced bytes at `0x1409e9897`. It advances output by produced count and input by the one-byte RLE payload or full raw payload at `0x1409e989c`–`0x1409e98a2`. When the last-block bit is set, it checks any declared content size at `0x1409e98bf`–`0x1409e98ce`; with the checksum flag it compares the four-byte trailer against `ZSTD_XXH64_digest` at `0x1409e98ea`–`0x1409e98f7`. On acceptance the frame returns produced length to MultiFrame and the provider. The provider still checks for decoder error and records used DataBlock bytes, then `ReadNWCompressedBuffer` must fit/copy them into `CRes+0x20`; the source-1/source-2 service requires its own exact returned-length match before the subtype serviced hook. These gates are mapped in the linked compressed-block branch. No GL call occurs in raw/RLE output.

Active archive entry, frame header, raw/RLE type, payload, checksum flag and result, resource subtype and later model/texture render use remain runtime choices. Skippable/concatenated frames and other Zstd compressed-block modes remain separate frontiers.

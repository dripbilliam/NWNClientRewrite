# NWN-75: original scene area-entry and teardown path

Pinned `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This maps the scene lifecycle adjacent to the render path. The large area-entry caller is unnamed in the provider; its observed tile, loading-screen and `mainscene` work supports calling it an area-entry handler, and its packet admission is followed in [area packet to Scene build](area-packet-to-scene-build.md). The outer virtual caller is traced in [network admission](network-frame-to-area-packet.md); the OS thread remains unobserved. All sites below are recorded in `branch-ledger.json`; static code does not establish elapsed time.

## Area entry and BSP initialization

`FUN_1407dba70` creates `mainscene` through `NewCAurScene` `0x1400cb1c0` at `0x1407dc8ed`, stores the result at its state `+0x248`, then calls Scene virtual `+0xd8=Scene::SetBlindLights` `0x1400d3330` at `0x1407dc937` with null. It obtains the tileset, allocates a `0x60`-byte-per-tile array, and calls Scene virtual `+0x28=Scene::InitBSP` `0x1400ca3b0` at `0x1407dca43`. Original instructions pass the two tile dimensions, border `5`, a true bin-init flag and cell size `10.0` (constant bytes at `0x140d8216c`). The Scene vtable `0x140d8dd30` resolves both virtual slots. On tileset lookup or tile-array allocation failure, the same handler calls Scene virtual destructor `+0x0=0x1400c29e0` at `0x1407dc970` or `0x1407dca09`. The handler suspends texture updates before per-tile loading and resumes them afterward. Its packet path is followed in [area packet to Scene build](area-packet-to-scene-build.md); the outer virtual caller is traced in [network admission](network-frame-to-area-packet.md); the OS thread remains unobserved. ## Per-tile model placement

The area-entry tile loop sets each tile ID, looks up `CNWTileData`, builds a record in the `0x60`-byte array, applies orientation and height transition, and calls `FUN_14084ef10` at `0x1407dd119`. That helper reads `CNWTileData::GetModelResRef`, copies the resource name, and calls the Scene virtual `+0x30` at `0x14084f14c`. Scene vtable bytes `0x140d8dd60` identify that target as `Scene::SpawnTile` `0x1400d41a0`. It saves the resulting `CAurObject*` in the tile record at `+0x38`; if nonnull, the area handler performs additional tile registration through `FUN_1407d8dd0`. Evidence: area handler `ev_f95eaa0a0bafbeb7b15f37558791794c8c2a1933dffefee3b9c58131537cf941`, helper `ev_f110b18d9e1728b3d70bb17a7a0012acc1d124a3161ee04d1744a11678822e34`, vtable bytes `ev_ad6bb78374a7405d846e557ce2240aed0a15d8758be3b2fe6d95fa2eea188fdd`.

`Scene::SpawnTile` calls `FindModel`, selects static texture mode for an available model, then constructs either an object-backed tile Part tree or an instance Part tree. It applies tile rotation, expands reference Parts, collapses the tree, and returns texture mode to dynamic. It gets or allocates `TileData`, attaches an object-backed tile Gob to the Scene when present, and calls `ProcessStaticParts`. The latter handles special part names, classifies triangular meshes, adds their faces to Scene bins through virtual `+0x2a0=Scene::AddFacesToBins`, computes bounds, and routes remaining Parts by type and tile mode. `Scene::SpawnTile` optionally combines Parts, merges their bounds, adds them to the BSP, then links neighboring tiles and their border lists. This is area loading/scene publication, not a demonstrated per-frame operation. ## Scene teardown and invalidation

The Scene deleting-destructor thunk `0x1400c29e0` calls `Scene::~Scene` `0x1400c1c20` and frees the `0x518`-byte object when its delete flag is set. The destructor detaches all Gobs through `Gob::SetScene(null)`, removes its named console fields and global `_Scenes` entry, destroys the LightManager through its vtable, traverses its BSP with `DeleteNonGobParts` `0x1400d9100`, destroys the BSP and WindManager, destroys triangle bins and list storage, releases the scene texture, and clears active bins when initialized. For the scene whose name matches `mainscene`, it calls `VertexDataObjectManager::Repack` `0x1400be390` before destroying draw buckets and remaining arrays. This teardown can therefore include buffer handling, not just object deallocation. Evidence: deleting thunk `ev_d1ed00272fe5071834c78d73b941fe6ed8603f7e5e34b51e33789d34adc5b0dc`, destructor `ev_9e802bd7b0e6aca27fe4d398c3eccb7dfe399651ab19baeeac749b7e2a851c2a`, LightManager destructor slot `ev_7ce8e463796a4f5c7ced264e221a62618361b5825c8922f9763359edf7f67c03`.

`DeleteNonGobParts` visits non-Gob-owned Parts in the BSP node data, conditionally decrements Model references, invokes the installed `AurSceneCleanupCallback`, deletes Parts through virtual destructors, and destroys the node-data object. The original `.data` cell at `0x14128ebf8` initially points to `FUN_1400bf480`, whose bytes are `c2 00 00` (`RET 0`), a no-op default callback. `SDL_main` loads the address of `NWMainSceneCleanupCallback` (`0x140042a30`) at `0x140046c2a` and stores it into that cell at `0x140046c37`. All six `DeleteNonGobParts` `FF 15` callback calls at `0x1400d9132`, `0x1400d9172`, `0x1400d91e4`, `0x1400d9246`, `0x1400d92a6`, `0x1400d9306` read the same cell, so the actual target depends on initialization. On the observed SDL_main-installed route, the callback can tail-jump to `UpdateScreen` at `0x140042ac3` under elapsed-time and server-loop gates. This creates a bounded reentrant screen route during eligible scene teardown; every Part destructor variant and possible later callback rebinding remain open. `VertexDataObjectManager::Repack` reads lockable vertex pools, compacts item data and unlocks them; the pool helper may conditionally publish through `glBufferData` or `glBufferSubData`, as detailed in [lens-flare-occlusion.md](lens-flare-occlusion.md). Evidence: cleanup caller body `ev_76e75e57199a5cc5f151e9fe16ebb2854bd1816b3db7e1b8e57a7075c7c96066`, installed callback `ev_f3621c6c91028fd618e7751df218b1a2eecdb2211d4351e8e9a8fdea47f436be`, pinned PE RIP-relative load/store and `FF 15` pointer-cell instructions, Repack `ev_3fc619d9109d6d03e604e2c1862a9b8d76d1eff8ddcaf14a0f69994af00240c6`.

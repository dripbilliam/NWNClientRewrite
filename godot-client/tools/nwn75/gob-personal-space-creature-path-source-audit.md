Its complete REA incoming set contains **three DATA references in virtual tables and one in the PE export address table**, with no direct code call. Pinned qwords at `0x140d81680`, `0x140d83158`, and `0x140d88c40` all equal `80a9044001000000` → `0x14004a980`. That export is an external entry, not evidence of a live caller. ## Creature path-array teardown

The constructor-backed `CNWCCreature::vftable` `0x140e474e8` has slot zero qword `d0bc7f4001000000` → deleting destructor `FUN_1407fbcd0` `0x1407fbcd0`. Its body directly calls `FUN_1407fb8c0` at **instruction** `0x1407fbcdf` (`e8dcfbffff`), then conditionally frees the `0x480`-byte creature object when its delete flag's low bit is set. The destructor body tests the creature-owned Vector array pointer at `+0x298` and frees it when nonnull, then continues other owned-object and base cleanup. This is the owner of the array that the model Gob's `GetPath` callback merely borrows at Gob `+0x158`; it does not prove the Gob view is still live during teardown.

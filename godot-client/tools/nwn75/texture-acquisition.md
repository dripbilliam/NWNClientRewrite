# NWN-75: original scene texture acquisition

Status: partial original-binary branch map for pinned `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This follows texture acquisition from `Scene::Render` and related material calls. It records original behavior only, without frequency or performance comparison.

`Scene::Render` obtains an environment texture through `AurTextureGetFallbackEnvironmentMap` `0x1400e88e0` when its cached pointer is null. That helper requests `chrome1` through `AurTextureGet` `0x1400e8100`, maintains a reference-list entry for the cached pointer, and returns it on later calls. It does not perform that lookup when the cached pointer is already present (REA `ev_8eceedf95827aae15e846bb5dc82b5e04394ace3f135820132f5513101864a65`). `AurTextureGetReference` `0x1400e8b60` is another caller: it first asks `AurTextureGet` for a named texture, then calls it again with that result to create a reference wrapper (REA `ev_75368d94af22e27b50b2177d95fe61232ce2fad1041ccdff4e4806e4f84764d8`).

The tile-set environment-map name lookup in `Scene::Render` calls `CNWTileSet::GetEnvMapResRef` `0x1402c67a0`. Its body copies the stored resource-reference bytes from TileSet `+0x39/+0x41/+0x49` into the return object and has no resource I/O or GL call itself (REA `ev_07e25fa7763386dde0bc422330fd46d5a99969a854f236a9715738cd22a9135c`). Later texture lookup uses that returned name.

`AurTextureGet` has two distinct input routes. With a nonnull name it calls `AurTextureFind` twice, first with no supplied image data and then with the supplied data/format arguments. A successful lookup returns the existing texture; the first result has an additional Basic-texture state check. If both lookups miss, it allocates a `0xf0`-byte `CAurTextureBasic`, calls its constructor and `Init`, then appends it to `RefreshTextures`. With a null name and an existing texture pointer, it allocates a `0x28`-byte `CAurTexture` reference object and assigns the existing texture into its `SafePointer` field at `+0x18`. These are allocation/lookup/queue routes, not direct GL texture publication. The optional connected-Tracy branch builds diagnostic strings; that branch does not prove ordinary texture work always executes. REA `ev_58e32829c45065d42dbb23e27380ac551464fb5b01ef76a91a9f508a9abccc9b`.

`SafePointer<CAurTexture>::operator=` `0x14004bb00` removes its previous pointer from that texture's back-reference array, repairs the moved entry's index, then stores the new pointer and appends itself to the new texture's back-reference array, growing it when full. This is reference bookkeeping with conditional `_realloc_base`, not an immediate texture build or GL call. It is called on the reference-wrapper route above and elsewhere from scene texture fields (REA `ev_6ac4832371265af1bf9231abcd2de2354c477796a67178e81b1fc25603e0bf57`).

`AurTextureFind` searches `_m_OrderedTextureList` with `DAT_14140b300` entries. When no filename data is supplied, or its boolean mode is set, it scans for a case-insensitive name match. With filename/format data it computes `AurTextureCalculateHashID` and searches by ordered hash; equal-hash candidates are checked against filename, format count and optional parameter values before returning a texture. A miss returns null. This is a CPU lookup over the current texture registry, not a GL call. REA `ev_b03932a88d72506a61079ec0167d4de6b7f387e78062ba08eb9589f4d2e53a66`.

`Scene::Render` later calls `AurTextureMakeCurrent` `0x1400e8be0`. When not suspended, it resets image timing counters; unchanged anisotropy and pending textures call `AurTextureBuildAndStoreAll`, while changed anisotropy calls `AurTextureRefreshAll`. It advances `texcurrentframe` on each invocation (REA `ev_7710c198e332b386a70fa12ca95cdef641f7a310f8160ac8e8b6899f5d354733`).

`AurTextureBuildAndStoreAll` `0x1400e6910` uses pending count `DAT_14140b330` and the `_RefreshTextures` array populated by the new-Basic route above. It walks pending entries backward and calls `CAurTextureBasic::BuildAndStoreTexture` for each whose `+0xeb` flag is clear, then resets the pending count. It sorts `_m_StaticTextureList`, updates `basictexturecount`, and rebuilds `_TextureIndices` and `maxtexid` from admitted static textures. Thus a nonempty pending queue can include global ordering/index reconstruction in the same synchronous call. The comparator passed at `0x1400e6d56` is original code `0x1400ef1a0`: four decoded instructions compare the float at `CAurTextureBasic+0x30` and put larger values first (`MOVSS`, `COMISS`, `SETA`, `RET`). `CAurTextureBasic::ParseField` parses the asset key `alphamean` into that offset, while its constructor defaults the value to `-1.0`. `AurTextureGetOrdering` `0x1400e8b50` simply returns the resulting `_TextureIndices` list. The texture build's image/GL descendants and full list-update side effects remain open. REA `ev_4c5b25e1f83a3edcd2708f5a81f6f909b9b741e150ec1f910dd914d435b7f8fa`, `ev_b2dd32c23ecb4cd1e301b41e4f7d16c1eb5a117230364ec7d34e91aa814e23d4`, comparator instructions `ev_346b27e08820a5b7e8355258bd5a3643d9471bd2d5084ffb55f3627bfa069caa`, `ev_18b574c7283b6aff55ac8b3034a559f9927a5f01401da99e2c91d5d1445b90ed`, `ev_b6553a5f885fb3addd8fb846aef2f4ce29574dbc3ef36f69fe9b656cdee4ba80`, parser `ev_20268a1ff656eb3ffe22cf37d278d8272f952622791f8d02277c90cb63c1e602`, constructor `ev_7c6b4e03abdc85bad33e4653d02caa5265596f7ede5fbfae061f8f6b7ed5b276`, ordering accessor `ev_81196e73b90f70df46c79e949e6e253ed4c605759c0ea18faed76380475635de`.

The texture sort itself is the same original `std::_Sort_unchecked` shape used for the live Gob bucket: insertion for fewer than 33 pointers, partition/recursive sort otherwise, and a heap fallback when the depth budget expires. Its five direct callback sites, eight partition sites, three median sites and two heap sites all receive the comparator pointer passed by `AurTextureBuildAndStoreAll`; they are address-level edges in `branch-ledger.json`. The four helper bodies have no other unresolved computed calls. Evidence: REA `ev_d0de7f305061f03a3b1d28641deef2109563336546a32d52b4c69562f3cd858d`, `ev_ccc40d0ceccadf9894c883f37debac01977763b1668ee5e8545120acb95c160a`, `ev_d8b2f8b8810d265ade9eec6aa53c9f5affb79451cba9e8af828225d1884c62ab`, `ev_964a5f58bea7d298e3d14f4f105bfad0c76dc791900ddaba863acd775feb5403`.

`CAurTextureBasic::AddToOrderedLists` `0x1400e57d0`, called from its constructor, inserts every new Basic texture into the hash-ordered `m_OrderedTextureList`, then appends it to either `m_StaticTextureList` when byte `+0xdd` is zero or `m_DynamicTextureList` otherwise. Both append lists double capacity from 16 as needed. The texture constructor initializes `+0xdd` from `g_bModeIsDynamic`. `RemoveFromOrderedLists` `0x1400ed6a0` reverses those two memberships. This identifies the source population of the static list subsequently sorted by `alphamean`; it is construction/lifetime work, not a fresh per-frame insertion. Evidence: REA `ev_428d0531ff66bf431bff554c8c41aaebb8691996890ebb120539ee5137b21ccd`, `ev_7c6b4e03abdc85bad33e4653d02caa5265596f7ede5fbfae061f8f6b7ed5b276`, `ev_eac07325558ae3b113a7ef14b8fd4d2eb9080c686af8050372f8931a41a824cc`.

An unspecified `alphamean` is also computed during `CAurTextureBasic::BuildAndStoreTexture` `0x1400ea5e0`. After image construction and the texture object's virtual `+0xe8=CAurTexture::glImage` `0x1400ee130` call at `0x1400eaace`, if image data exists and the float remains `-1`, uncompressed images with `+0x70<1` call `ImageGetAlphaMean` `0x140071bb0`; its CPU loop averages alpha byte 3 across pixels for four-or-more-byte pixel formats and returns `1.0` for smaller formats. Other image modes use `0.5` for four-byte data or `1.0` otherwise. That value is stored at Basic `+0x30` before the static-list sort above. The later Basic virtual `+0xf0=CAurTextureBasic::FreeImage` `0x1400eb640` call at `0x1400eab38` conditionally releases its CPU raster or frees the owned buffer. Original Basic vtable `0x140d90d90` contains both targets; its `+0x8` and `+0x10` slots resolve the two virtual calls inside `CAurTexture::glImage` to `AsCAurTextureBasic` `0x1400e5a10` and `GetReferencedTexture` `0x1400ebb00`. The separate `+0x10` call on the Basic `+0x38` texture controller at `0x1400eab2f` is the build-time `Init` dispatch mapped in [controller build initialization](texture-controller-build-init.md). Evidence: REA `ev_3da65d17a98f227ececaf4b457322e76a4829c312b383a4a4d88ed612c3cda32`, `ev_8d7b83b9a627c69c549c051cf66ea986b977b968ed52a2bab386ecab4b560ee1`, `ev_b2e85194d6b4aa14cefdd0f1e6976bc998fd394dd10df86b3e26f3215c2b706f`, `ev_4ce63326ada5bb6844bb53c40e38d960c99192296a78ce676109d0aee70d64ab` and original PE slot file offsets `14221944/14221952` (REA mappings `ev_d9ec777ac7964090b0de0bc490e37c88367b006ae03f8e0eebbe6f7834b1583b`, `ev_8cd622c8d061d154da48100eaa1a5c70b644dfbd9ff415903758653b0ea1846d`).

The resulting `CAurTextureBasic::glImageBasic` `0x1400ee1b0` has two publication branches. With `g_bGeneratePLTOnGPU` off or image kind `+0x84 != 4`, it allocates texture IDs when absent, binds each one, and invokes `RenderInterface::CreateTexture` or `CreateCubeTexture` for its tile/face count. Their GLRender implementations reach `glTexImage2D`/`glTexSubImage2D` and compressed upload or mipmap extension calls according to texture format. With GPU PLT generation enabled for kind 4 and a palette source present, it lazily constructs the master-palette texture and shared quad/FBO/shader, allocates image/palette textures, draws the `vs_pltgen`/`fs_pltgen` quad into the target texture, optionally generates mipmaps, and restores viewport/bind/state. This is a conditional asset-publication render inside the texture build, not an ordinary scene bucket draw. The original Basic getter and GL extension callsites in both upload implementations are already mapped in [2D texture indirect calls](texture-create-indirect-callsites.json) and [cube texture indirect calls](texture-cube-indirect-callsites.json); those maps are for the Basic candidate and do not exhaust other texture subclasses. Evidence: REA `ev_73403af00633745774d0de4928fa5a3d9f11a946ea304aa7116e71c1641307cd`, `ev_e1457697c281f0b9e795822e361fb5ff23463a3aee7d7f612d5a10add1480310`, `ev_1f9ddbaf37d8d5b350a93d0e301578f18f700a525062108567526dd3e25174a8`.

The [GPU PLT publication continuation](texture-gpu-plt-publication.md) gives the precise first-use palette, quad, FBO and shader sites and the offscreen draw handoff. The [texture RTTI census](texture-rtti-primary-vtables.md) bounds the getter targets to the two RTTI-backed primary classes in this image.

On an anisotropy change, `AurTextureRefreshAll` `0x1400e8eb0` resizes/copies the ordered texture list into `_RefreshTextures`, iterates it, and for each eligible Basic texture calls its virtual `+0xf0=FreeImage`, marks rebuild state, deletes old GL texture IDs through `RenderInterface::DeleteTextures` when present, then calls `AurTextureBuildAndStoreAll`. It also invokes `AurInitFont`. This is a conditional global refresh, not the ordinary unchanged-anisotropy path. REA `ev_c772db02f44800eb4190e137dcdbd516b76ef24343dbf480852ec48940b0699a`; the Basic `+0xf0` target is established by vtable `0x140d90d90` in `gui-presentation.md`. The scene's material-time controller bind branch is mapped in `texture-controller-runtime.md`.

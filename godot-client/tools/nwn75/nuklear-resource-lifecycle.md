# NWN-75 original Nuklear GL resource lifecycle

Scope: installed `nwmain.exe`, SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. Addresses are original image VAs. This describes only original UI resource ownership and static call paths; it does not establish runtime frequency or compare another client.

## Owner and handle block

The outer `SDL_main` setup path calls `0x140a70a50` at `0x140046da5`. That function calls the Nuklear device creator `0x140a6f9d0` at `0x140a70aee`, then font/config refresh `0x140a70d90` at `0x140a70afa`. Later, after the update loop exits, `SDL_main` calls UI teardown `0x140a71ef0` at `0x140046de2`. The UI draw function `0x140a71760` also calls `0x140a70d90` at `0x140a7185f`. These direct E8 edges and `.pdata` bodies are pinned in the PE; the outer-loop body is retained REA `ev_833c7aa9adb229ef33dd413c495d7c0f61fbec645c741d6268e78b62f252dd65`.

The device creator, draw, refresh and teardown all reference a dedicated UI global block. Original RIP-relative loads/stores identify the following roles; these are distinct from generic `GLRender` stock-program and default-VAO caches.

| UI global | Observed role and proof |
| --- | --- |
| `0x141429a60`, `0x141429a64` | Vertex and element buffer IDs from `glGenBuffers` at `0x140a6fcdd`/`0x140a6fcf2`; draw binds/uploads them; teardown passes each to `RenderInterface::DeleteBuffer` at `0x140a720dd`/`0x140a720e8`. |
| `0x141429a68` | UI VAO ID from `glGenVertexArrays` at `0x140a6fd07`; draw reads it at `0x140a71995` and binds it. No delete of this UI handle has yet been established. |
| `0x141429a6c` | UI program ID from `glCreateProgram` at `0x140a6fac0`; draw reads it at `0x140a71980`; teardown uses it for detach/delete. |
| `0x141429a70`, `0x141429a74` | Vertex and fragment shader IDs from `glCreateShader` at `0x140a6fad7`/`0x140a6faee`; teardown detaches each from the UI program and deletes each. |
| `0x141429a78`–`0x141429a80`, `0x141429a84`/`0x141429a88` | Three attribute locations from `glGetAttribLocation` and two uniform locations from `glGetUniformLocation`, then used by draw. These are integer locations, not separately deleted GL objects. |
| `0x141429a8c`, `0x141429a50`–`0x141429a5c` | UI atlas texture ID is created/replaced at `0x141429a8c`; refresh copies it into Nuklear's conversion null-texture ID at `0x141429a50` and computes its half-pixel UV at `0x141429a58`/`0x141429a5c`. ## Device creation and draw use

`0x140a6f9d0` allocates/resets Nuklear atlas CPU state, creates the UI program and vertex/fragment shaders, supplies/compiles both shader sources, checks their status and info logs, attaches/links them, checks the link status, obtains `Texture`/`ProjMtx` uniform and `Position`/`TexCoord`/`Color` attribute locations, then generates VBO/EBO and UI VAO. It ends by resetting array/element bindings through `RenderInterface::BindBuffer` at `0x140a6fd10`/`0x140a6fd1c`. Exact GL callsites: `glCreateProgram` `0x140a6fac0`; `glCreateShader` `0x140a6fad7`/`0x140a6faee`; `glShaderSource` `0x140a6fb11`/`0x140a6fb2e`; `glCompileShader` `0x140a6fb3d`/`0x140a6fb83`; `glGetShaderiv` `0x140a6fb56`/`0x140a6fb9c`; `glGetShaderInfoLog` `0x140a6fb74`/`0x140a6fbba`; `glAttachShader` `0x140a6fbcf`/`0x140a6fbe4`; `glLinkProgram` `0x140a6fbf3`; `glGetProgramiv` `0x140a6fc0c`; `glGetUniformLocation` `0x140a6fc25`/`0x140a6fc44`; `glGetAttribLocation` `0x140a6fc63`/`0x140a6fc82`/`0x140a6fca1`; `glGenBuffers` `0x140a6fcdd`/`0x140a6fcf2`; `glGenVertexArrays` `0x140a6fd07`. The loader at `0x140b7a350` names shader pointer cells `0x1414424d0`–`0x1414425c8`; the buffer and VAO cells are `0x141442470` and `0x141443f58`. REA creator `ev_ae160a95018d6d6c2012c2406ddd469a1dadaa784f98f18b8403156d73f66a9a`, shader loader `ev_34f0426e6ddccc2d5835824caea17d347c8be1b00ffbc169322aa1e7cc808463`, existing `gl-extension-pointers.json`.

On a draw, `0x140a71760` reads this UI program/VAO/buffer block, maps its vertex/index buffers, converts numeric Nuklear commands through `0x140a7c340`, uploads/unmaps, then binds textures/scissors and issues indexed draws for nonempty commands. The program selection at `0x140a71984` goes through `RenderInterface::GlUseProgramConditionally` `0x1400bede0` → `GLRender::GlUseProgramConditionally` `0x1400b3eb0`; it calls `glUseProgram` only when the requested nonzero ID differs from the cached current program. This is the observed consumer of the UI program, not a new program allocation per draw. Draw REA `ev_6b5e1be5df3d0ec1c19e05d9f5114d2a9453a5c0bd89c9f09f1a3012d4826278`, program gate `ev_f5dacfa37625b01fe10ffdd65cedde3908c20a69cd7163152274bb572287076a`; its 16 computed extension sites are classified in `nuklear-gl-callsites.json`.

## Font atlas creation and refresh

`nk_sdl_refresh_config` `0x140a70d90` enters its rebuild body only when dirty byte `0x1412996e0` is nonzero. It then clears the byte, builds font entries through `0x140a824b0`, bakes pixels and glyph metrics through `0x140a82f20`, uploads the atlas through `0x140a6fe10` at `0x140a714f0`, and publishes the active baked font view at `0x141429c20`. The baked entry's width and glyph callbacks resolve to `0x140a6ba50` and `0x140a6b9a0`; numeric kind-16 text and its converter use that view. The setup path calls refresh after device creation, and draw calls it again on its draw path; the dirty-byte gate means that a draw-time refresh call alone does not imply baking or uploading. Refresh does not directly call device creator `0x140a6f9d0`, so the observed refresh path can update font/atlas state without recreating the program/VBO/EBO/VAO in that function. REA refresh `ev_27d673120a5dffd05d650a50a873aa339ed1664f665392bfa2a223413498697c`, baking/upload `ev_920bdd7df85f131e5eb7c4f87ab666e559ffb8110b92c6b3bff758c3a3565b97`, callback chain in `nuklear-command-conversion.md`.

The refresh also installs a concrete stored allocator pair. It takes `0x140a6c550` at `0x140a70f21` and `0x140a6c890` at `0x140a70f2f`, then writes those function pointers to atlas context slots `0x141430218` and `0x141430220` at `0x140a70f47`/`0x140a70f4e`; user context `0x141430210` is zeroed. The font-entry builder `0x140a824b0` calls its context `+0x18` allocator at three conditional sites (`0x140a82539`, `0x140a825b6`, `0x140a8269d`). On this configured refresh route, that target is `0x140a6c550`, which passes its size argument to CRT `_malloc_base` `0x140c7f8a8`; the latter reaches Windows `HeapAlloc` and can retry through its new-handler on failure. The installed free callback `0x140a6c890` forwards its pointer to CRT body `0x140c4f024`; its deeper release path remains open. This is conditional CPU allocation during font refresh, not a GL draw. REA assignment instructions `ev_4e5d2c35fed306511801ab3b35c7b127f917603d462336b6cd0a5945cc4c9def`, `ev_72efd39a3451bf4aab5c805714af8ea77b017e6cf6d48cb8484dc2b0b2f79538`, `ev_1d732d04663b8d12c26c9bc2eccb965c215dec7d5059d7d436850d090fec0f17`, `ev_10238618bf3de431c4a89e7e025e03ab600ba9c21be4ef2aac175ae0b25842b0`; builder `ev_920bdd7df85f131e5eb7c4f87ab666e559ffb8110b92c6b3bff758c3a3565b97`, allocator `ev_c32b0f91d738b0f6b33a6595445d60b01a6ef4e59d8435b9cea793deb48a37ce`, CRT `ev_41dd87c3412f2ae94ab815f9845350a1faced30752a2660c948bfc33da40de1b`.

The atlas uploader `0x140a6fe10` conditionally deletes the previous texture ID through `RenderInterface::DeleteTextures` `0x1400be9b0` at `0x140a6fef7`, then calls imported `glGenTextures` at `0x140a6ff08`, `glTexParameteri` at `0x140a6ff2e`/`0x140a6ff44`, and `glTexImage2D` at `0x140a6ff7b`. The imported IAT cells in the pinned PE are `0x140d7ca50`, `0x140d7c9e8`, and `0x140d7c9f8`. The old-texture delete thunk reaches `GLRender::DeleteTextures` `0x1400afe20`, which clears cached matching texture bindings before `glDeleteTextures`. This is the Nuklear atlas texture's own replacement path; the separate `CAurFont`/`CAurTextureBasic` TTF and texture lifecycle in `gui-presentation.md` is another font family.

## Teardown and unresolved edges

The UI teardown entry `0x140a71ef0` frees the font/atlas CPU allocations and calls atlas cleanup `0x140a841c0` at `0x140a7206a`, then detaches both shaders from the UI program (`glDetachShader` at `0x140a72082`/`0x140a72097`), deletes both shaders (`glDeleteShader` at `0x140a720a6`/`0x140a720b5`), and deletes the program (`glDeleteProgram` at `0x140a720c4`). These use the same UI handle globals above. The original GL loader binds those names to cells `0x141442510`, `0x141442508`, and `0x141442500`; the call instructions load read-only pointer-table cells `0x140ee4808`, `0x140ee4800`, and `0x140ee47f8` respectively. Teardown then calls `RenderInterface::DeleteTextures` at `0x140a720d2` for the atlas ID and `RenderInterface::DeleteBuffer` at `0x140a720dd`/`0x140a720e8` for VBO/EBO. The latter thunk `0x1400be970` reaches `GLRender::DeleteBuffer` `0x1400afc00`. REA teardown `ev_31fa676acca921352feeb7b86e05666bb07b19aadcc1fe805d5e19215edbb577`, atlas CPU cleanup `ev_eb3c0f8599822d5733232dba7c6978e55530d04e0518f54628a679349d34437b`, GL loader `ev_34f0426e6ddccc2d5835824caea17d347c8be1b00ffbc169322aa1e7cc808463`.

The analyzed UI teardown body does **not** read VAO ID `0x141429a68` or call `glDeleteVertexArrays`. A pinned whole-`.text` reference scan found only the loader assignment to `glDeleteVertexArrays` cell `0x141443f50`, and a pinned `.rdata` 8-byte pointer scan found no table entry containing that cell address. This establishes no explicit UI VAO deletion on the observed path; another indirect owner or GL context destruction is not ruled out. `GLRender::Shutdown` `0x1400bb560` has generic renderer-owned program teardown, but no evidenced data-flow from its handles to the Nuklear UI globals. The known reset path's default VAO is likewise a separate renderer cache. Neither generic path is assigned ownership of UI VAO `0x141429a68` without an original pointer edge.

The [lifecycle continuation](nuklear-resource-lifecycle-continuation.md) gives the exact UI handle-reference census, distinguishes the two VAO extension-pointer sets, and bounds the observed SDL/context shutdown and resource-reload routes. Any alternate font-view substitution and whether atlas refresh runs in a particular frame remain open. Static call order does not prove an OS thread or measured frequency.

## Shared node dispatch and list input

`ParseNode` selects `MdlNodeAnimMesh::MdlNodeAnimMesh` at `0x1400a0f45` for `animmesh` and `MdlNodeSkin::MdlNodeSkin` at `0x1400a102e` for `skin`. Both first construct a TriMesh base. AnimMesh sets kind `0xa1`, parse field `+0x8=0x140092500`, postprocess `+0x10=0x140092510`, instance creation `+0x28=0x140092440`, and vertex generation/temporary cleanup `+0xa0/+0xa8`. Skin sets kind `0x61`, `+0x8=0x140093060`, `+0x10=0x140093070`, `+0x28=0x140093000`, and its own `+0xa0/+0xa8`; it retains the TriMesh control field. `ParseNode` calls each node's `+0x8` for lines until `endnode` at `0x1400a109f`, then calls `+0x10` at `0x1400a10b3`. The wrapper parse/postprocess functions are tail jumps to the respective `Internal...` bodies. REA `ev_d48a96fe`, `ev_a9e0ea73`, `ev_f493d499`, `ev_aff1e4d7`, `ev_90d19cad`.

The subtype list templates recognize a leading count with `sscanf("%d %c")`. An absent count reads nonblank lines until `endlist`, growing a CPU array; a count without a second character reads that many lines; a count plus a second character invokes `AurResGetData(count × element-size)` and copies the block into the array. Element sizes are 12 bytes for Vector, 16 for Quaternion, 72 for SkinVertexWeight, and 4 for int. Those list readers terminate at CPU allocation/copy or the resource-data accessor, not at a GL call. The resource storage beneath `AurResGetData` is covered elsewhere in the map. REA `ev_4d298594`, `ev_086838b3`, `ev_d3e09276`, `ev_5db75239`.

## AnimMesh

`MdlNodeAnimMesh::InternalParseField` `0x140099c80` accepts `sampleperiod` into node `+0x2c8`, `animverts` as a Vector list at `+0x2d0`, and `animtverts` as another Vector list at `+0x2e0`. It then tail-jumps to `MdlNodeTriMesh::InternalParseField` `0x14009e950` for shared mesh fields. The subtype fields are case-insensitive exact token checks after a length-limited first-word extraction. REA `ev_aff1e4d7`.

`MdlNodeAnimMesh::InternalPostProcess` `0x1400a9220` runs its substantial branch only when the node's `+0x284` vertex-count field is zero. It calls `MdlNodeTriMesh::ProcessVerts`; derives animation sample counts from the authored lists and base vertex/TexVertex counts; allocates a normal-sample array at `+0x2f0`; computes per-sample normals across face adjacency; updates bounds; and invokes its `+0xa0` vertex-generation field, installed by its constructor as `MdlNodeAnimMeshGenVertices` → `InternalGenVertices` `0x1400a8300`. That builder's per-corner candidate construction and exact [sample-sensitive deduplication](model-text-animmesh-vertex-dedup.md) are now expanded. The postprocess then builds neighbor and vertex indices, calls `MdlNodeTriMesh::GenerateVertexData` at `0x1400a967f`, allocates/copies persistent [position and UV sample arrays](model-text-animmesh-sample-publication.md) when sample counts are nonzero, calculates tangent basis, and invokes `+0xa8` temporary-array removal. The shared [vertex-stream builder](model-text-trimesh-vertex-streams.md) reaches `RenderInterface::RequestPool/LockPool/UnlockPool` for base streams and conditional attributes. When `+0x284` is already nonzero, this postprocess returns without that rebuild. REA `ev_3824c818`, `ev_8139649e`, `ev_fbbde492`, `ev_f41f3a9c`.

On later `CreateInstanceTreeR` traversal, node `+0x28` at `0x14008dae0` resolves to `MdlNodeAnimMeshCreateInstance` → `InternalCreateInstance` `0x1400917f0`. It allocates a `0xc0` PartTriMesh, runs its constructor, installs `PartAnimMesh` vtable, and copies node `+0x224` to Part `+0xac`. Later control interpolation and animated buffer publication are mapped in `animation-and-emitter.md`; this supplement does not treat a parser call as a per-frame update. REA `ev_f7ea47f2`, `ev_09952950`.

## Skin

`MdlNodeSkin::InternalParseField` `0x14009e760` accepts `weights` into a SkinVertexWeight list at `+0x2c8`, `qbone_ref_inv` Quaternion list at `+0x2f0`, `tbone_ref_inv` Vector list at `+0x300`, and `boneconstantindices` int list at `+0x310`. It then tail-jumps to the shared TriMesh parser. These are authored CPU arrays, including per-vertex weights and bone references; no render pool is requested by the subtype field parser. REA `ev_90d19cad`.

`MdlNodeSkin::InternalPostProcess` `0x1400a99e0` acts only when `+0x284` is zero. It appends the current global mirror-list values into its TriMesh postprocess data (reallocating as required), then calls `MdlNodeTriMesh::ProcessVerts` at `0x1400a9ac1`. It does not publish a skin pool in that body. `CreateInstanceTreeR` later calls node `+0x28=0x140093000`, a tail jump to `MdlNodeSkin::InternalCreateInstance` `0x1400df1a0`, which creates a `0xc0` PartTriMesh and installs the PartSkin vtable. REA `ev_70ee47bd`, `ev_9490ce05`, `ev_f7ea47f2`.

The PartSkin postprocess is the next publication stage: if its MdlNode has no geometry data at `+0x278`, it returns. Otherwise `PartSkin::PostProcess` `0x1400df860` resolves bones, calls the node's `+0xa0=MdlNodeSkinGenVertices` → `MdlNodeSkin::InternalGenVertices` `0x1400df200`, whose per-corner candidate construction and [weight-sensitive deduplication](model-text-skin-vertex-dedup.md) are now expanded, then requests and locks [paired Skin index/weight pools](model-text-skin-pool-publication.md) at `0x1400dff06/0x1400dff18` and the second stream. It fills these pools from the authored weights/bone indices and unlocks them; the later pool-to-GL upload is mapped in `geometry-and-draw-boundary.md`. `PartSkin::PostProcess` and the computed `+0xa0` target are also recorded in `model-instance-branch.md`. REA `ev_86cdb10a`, `ev_2f2eaff1`.

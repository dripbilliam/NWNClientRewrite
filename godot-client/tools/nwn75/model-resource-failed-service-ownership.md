# NWN-75: model resource failed-service ownership

Pinned installed `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This closes one concrete failure-owner path left open by the [source-1/source-2 archive branches](archive-zlib-fast-decode-ownership.md) and [model resource storage](model-resource-storage.md). It covers an MDL request through the installed Aurora callback and a failed read/service after `CExoResMan::Malloc`. It does not claim all resource subclasses or all failure cases free at the same point.

`ServiceFromResFile 0x140193b80` and `ServiceFromEncapsulated 0x140192cf0` set `CRes+0x30` to expected size and call `Malloc 0x140190e50`; on a complete read they invoke the resource's `+0x20` serviced hook, but a short/mismatched read logs and returns failure without invoking that hook. `Malloc` writes its allocation into `CRes+0x20` and, when `CRes+0x38` is nonzero, allocates ten prefix bytes and stores the adjusted data pointer. Neither failing service body calls `FreeResourceData` after the read mismatch. `CExoResMan::Demand 0x14018ef90` receives zero, clears its in-service bit and returns null without incrementing `CRes+0x8` demand count or freeing that buffer. Thus the buffer may still be owned by the CRes object after this local service failure. For an MDL request, `CAuroraModel::CAuroraModel 0x1400f4690` installs wrapper table `0x140d921f0` at `0x1400f46ed` and, when a new resource is needed, constructs `CResMDL 0x1400fa8d0` at `0x1400f47bd`; that resource installs table `0x140d92b00` at `0x1400fa8ec`. `CAuroraModel::LoadModel 0x1400f4a70` calls `CRes::Demand` at `0x1400f4a7d`; a null result returns zero without setting its loaded flag `+0x28`. `CAuroraInterface::GetResource 0x1400f63d0` handles a failed `LoadModel` at `0x1400f67b7` or its second attempt at `0x1400f6a13`, removes an old list entry when appropriate and invokes the wrapper's virtual deleting destructor at `0x1400f67e9` or `0x1400f6a41`. The constructor-backed `CAuroraModel` table `0x140d921f0` has slot zero `0x1400f4930`. This is a conditional MDL-wrapper cleanup, not the archive service itself freeing the data. The deleting wrapper destructor `0x1400f4930` calls `CResHelper<CResMDL,2002>::~CResHelper 0x1400f4810` at `0x1400f496d`. The helper obtains `CRes::GetData`, calls `CRes::Release` at `0x1400f4861`, and passes a Boolean indicating null data to `CExoResMan::ReleaseResObject` at `0x1400f4876`. For the failed-demand count of zero, `CRes::Release` returns `-1` without freeing. `ReleaseResObject` decrements an object count above one and returns that remaining count, retaining the shared CRes. For a final object owner it returns zero; it may queue a nonnull-data resource for reclamation, then the helper invokes CRes virtual deleting destructor at `0x1400f4891`. The constructed `CResMDL` table `0x140d92b00` resolves slot zero to `0x1400fa920`, which calls `CRes::~CRes 0x14018dd50` at `0x1400fa939`. That destructor removes a pending-list node if present, frees nonnull `CRes+0x20` (backing pointer adjusted by ten bytes when `+0x38` is set) at `0x14018de4a`, and clears pointer/size. This proves final-owner MDL wrapper cleanup of a failed-service buffer; it does not prove immediate disposal before the wrapper is destroyed, nor that a shared CRes with another object owner has already been freed. Later reservice behavior with retained objects and other subtype owners remains an explicit frontier. No draw or GL call is on this failure path.

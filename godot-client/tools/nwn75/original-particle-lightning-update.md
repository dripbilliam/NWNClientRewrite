## Target ownership and update admission

The factory installs the LightningEmitter vtable on the model-instanced PartEmitter. Its `Initialize` `0x140061d30` calls base `PartEmitter::Initialize` (which selects the render callback), registers `_EmitterTarget` on owner Gob `PartEmitter+0x50`, and clears emitter `+0x1cc`. The registered `SetEmitterTarget` callback `0x1400643c0` scans emitter child Parts `+0x38/+0x40` through virtual `+0x70=AsPartReference`. On an admitted PartReference, it copies its referenced Gob field `+0x68` to `PartEmitter+0x1c0`, samples that Gob's virtual `+0xc0=GetPosition` (constructor-backed Gob base slot `0x140d88ac0`, `ev_15dd5e10911047e0f9099bb67a11928c97ae578a55fa4549a0802d3cab696213`), and stores initial target direction/position fields `+0x248..+0x25c` through the Lightning subtype test `+0x108`. With no admitted reference, it deregisters the callback from the owner Gob. Thus `+0x1c0` is a target Gob pointer selected by a reference Part, not an independently owned model. Authored reference presence and event timing remain runtime gates. Evidence factory `ev_e9806c355853e25ce0b29fba8bd9035e6d113563e1d021a4effee3441c5add89`, Lightning initialize `ev_32c154425f1ffedf227096ba7da18069f58e6b2e96e53a8a790e61f6f4175f34`, callback `ev_a20a60bfc6fbdf7caa78b86fccd0c5b2bbd0ba8a8d85cf115b24a4fa3eeb2bd3`.

`Scene::DoEmitterBucket` `0x1400c7ae0` conditionally calls `PartEmitter::AnimateParticles` `0x140061210` with Scene `DeltaT`; after its tile-fade and pose gates, its virtual `+0x100` reaches `LightningEmitter::Update` `0x140065290`. The first step increments Lightning timer `+0x1c8` and reads integer-converted segment count from emitter `+0x74`. If count is zero or target Gob `+0x1c0` is absent, it removes every live Particle from `+0x188/+0x190` into reuse list `+0x130/+0x138`, growing that list when needed, then returns. It does not destroy those particles or call GL. With a target and nonzero integer count, it grows or shrinks the live list toward that count; authored positive counts are the meaningful segment case. Growth consumes reuse entries first; if none, it allocates an ordinary `Particle` (never Chunky in this body), initializes it once through `Particle::initialize` at `0x140065470`, optionally assigns a random atlas frame under source flag `+0x174` bit 5, and appends it. Reused particles do not pass through this initialization call. Shrinkage moves excess live entries to the reuse list. Evidence Update `ev_3f42edbd7257e3953b1080f297e157e959056e33766cc0c1ccc286a5904d08ce`, RNG source `ev_95cdd088fd6dcb5f6e18adf92c290ea96578aa8174ff5274f2a6d552200fa6c4`.

For each live segment, Update advances particle clock `+0x74` and, in render mode `6`, blends previous position `+0x64..+0x6c` toward current position for motion blur. Its target position branch then compares accumulated timer `+0x1c8` with interval `+0xec`. While the timer is at or below interval, it reads target Gob `GetPosition` at `0x140065a4c`, computes a rotation from prior target direction to the new one, rotates the current segment positions, and updates the cached direction and origin `+0x248..+0x25c`. Beyond the interval, it optionally randomizes the first endpoint from emitter `+0xe0/+0xe4`, reads target Gob position again at `0x1400657a8` to set the last endpoint, and, when the endpoints differ, resets the timer, computes a cross-axis, calls `RecursiveFractal` `0x140062460` at `0x1400658dc`, and perturbs interior segments with caller-thread CRT RNG under the distance and authored amplitude gates. `RecursiveFractal` writes midpoint particle positions at `Particle+0x10/+0x18`; it samples RNG for sign and optional offset when emitter `+0xf0>=0.01`, then recursively halves its span until zero. The function's depth parameter increments but is not itself a stop test. These are CPU particle geometry writes. Evidence Update `ev_3f42edbd7257e3953b1080f297e157e959056e33766cc0c1ccc286a5904d08ce`, fractal `ev_1ff832019830188ce5ae5831700c712b21c7d452907115921e2b16481be83bd5`. The more detailed [scheduling continuation](original-particle-lightning-scheduling-leaves.md) records these exact interval branches and list operations.

`LightningEmitter::Update` has no direct GL call. After update, positive live count is sorted into Scene's render list, then the installed PartEmitter `+0x1b0` callback runs at `0x1400c7dae`. Base initialization may select Standard/Linked/MotionBlurred; nonempty authored model name can override with RenderNothing. Linked mode `3` requires at least two live segments before shared `RenderEmitter` draws; the shared body commits six vertices per effective segment and calls `RenderInterface::RenderVertexStreamData` at `0x140064109`, reaching nonindexed `glDrawArrays` under shader/material/fade gates. Runtime mode, segment count, target lifetime, visibility, possible derived Gob slot overrides and actual draw choice remain open. Evidence Scene `ev_b4881207528882fb849869474dcd3a31c18cf9f00dad89280e126d85fcdd7ed3`, shared renderer `ev_34f8fbdda88642e9a5fcc853ff16fcb539af3e4923e97fbbca235e05c24b6605`, GL body `ev_f07bc8ffc5b8e28cb307462a960e15bf144503071ed421fe7b86612de920e47a`.

## Four subtype virtual-slot audit

All four constructor-backed emitter vtables have one concrete `+0x100=Update` target. `Fountain` vtable `0x140d84518` → `0x140064b30` (`ev_520894cc8c811e832afbd96dfd4d936606d987b7af982d9dc6242b8c5404971f`); `Explosion` `0x140d84630` → `0x1400647c0` (`ev_98f3eaba9b7f6ca920aff8f9b252098d9b41e30b3427a886f338441aed24d5b4`); `Single` `0x140d84748` → `0x140065cd0` (`ev_f85821f96d09c01094edaafbddec74ebb87e9ae1327d4698b594af3d26c3f730`); `Lightning` `0x140d84860` → `0x140065290` (`ev_86b95f05d47bf275e93cf4a2ec709abccc7687b656adaa1c0a808dd51279d50f`). Their `+0xf8=Initialize` slots point to base `0x140061d80` for the first three and Lightning `0x140061d30` for the fourth (slot evidence `ev_5f1488d225baf629680425da3f9a5da9ad9fe89d1ea10a703294be0d00aaa1b4`, `ev_398962dd1a4753a489750a87ed7675391f420d6921def2487fc2df053c31bd34`, `ev_11e253701cfd3ec53ddd8cadddea8cdaf4683db90031740f73421c919c1d6a95`, `ev_16e5623f822dc98516604c01b9f2aa41d79d4e1b87cd683d6d03b245bbe49004`).

Computed update-call audit: Fountain has owner Gob adjusted scale `+0x2d0`, movement field `+0x170`, and two particle initialize virtual `+0x10` sites; Explosion has the same three target families with one particle initialize site; Single has a first-use `chkRandom` tail jump, an existing-particle movement tail jump, and a disabled-particle virtual destructor `+0x0`; Lightning has owner adjusted scale and two target Gob `GetPosition` `+0xc0` sites. Each is mapped above or in the linked subtype supplements; no additional targetless computed call remains in these four analyzed Update bodies. This is a constructor-backed static census, not proof that every possible authored emitter subtype or callback executes in a given area.

# NWN-75: DanglyMesh model payload to draw handoff

Pinned original `nwmain.exe` SHA-256: `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This supplement follows one authored model node subtype, `danglymesh` / binary kind `0x121`, through parse, typed `PartDanglyMesh`, primitive setup, and conditional draw. The exact instruction sites and full REA evidence IDs are in `model-dangly-payload-ledger.json`. Shared TriMesh parsing and render APIs are linked to their existing supplements rather than duplicated.

## Text payload

`ParseNode` `0x1400a0d90` selects `MdlNodeDanglyMesh::MdlNodeDanglyMesh` `0x140087510` at `0x1400a0f80`. The constructor first builds a TriMesh base, installs kind `0x121`, initializes the constraints list at `+0x2c8`, and installs subtype parse/postprocess/CreateInstance/GenVertices/cleanup entry fields at `+0x8/+0x10/+0x28/+0xa0/+0xa8`. The per-line `ParseNode` call through `+0x8` is at `0x1400a109f`; its final postprocess call through `+0x10` is at `0x1400a10b3`. Those computed sites resolve for this constructor through `0x140092840 → 0x140099e20` and `0x140092850 → 0x1400a9880` respectively. See `model-name-parser-tree.md` for the surrounding text parser and node nesting.

`MdlNodeDanglyMesh::InternalParseField` `0x140099e20` checks a case-insensitive first token, with a `0x400`-byte length guard. It parses `displacement` into float `+0x2d8`, `period` into `+0x2e0`, and `tightness` into `+0x2dc`. `constraints` invokes `Parse<float>` `0x1400969f0` for the list at `+0x2c8`. This reader supports lines until `endlist`, a leading fixed count, or a count-plus-marker raw data read of four bytes per element through `AurResGetData`, followed by a CPU copy. After the subtype tests, the parser tail-transfers to shared `MdlNodeTriMesh::InternalParseField` `0x14009e950`. A token-length failure goes to range-check failure, outside this normal payload path.

When the node's `+0x284` vertex count is zero, `MdlNodeDanglyMesh::InternalPostProcess` `0x1400a9880` calls `MdlNodeTriMesh::ProcessVerts`. With face count `+0xb8 > 0`, its constructor-installed `+0xa0` resolves through `MdlNodeDanglyMeshGenVertices` `0x140092830` to `InternalGenVertices` `0x1400a89b0`; it then copies the generated vertex count, builds neighbor lists and vertex indices. The generator reads the original vertex's constraint for each face corner, constructs and compares `NodeVertexDangly` CPU records, reuses or appends deduplicated vertices, rewrites face indices, and replaces the constraint list with remapped values. Its exact [constraint-sensitive vertex comparison and remapping](model-dangly-generated-vertex-dedup.md) are now expanded. Postprocess calls `GenerateVertexData` `0x1400a7790` and `CalculateTangentSpaceBasis` even when no faces took the subtype generator branch, then tail-invokes `+0xa8` cleanup through `0x140092860 → 0x1400a9e90 →` shared TriMesh cleanup. `GenerateVertexData` conditionally requests, locks, fills and unlocks render pools for base/attribute streams. If `+0x284` was already nonzero, this postprocess returns without rebuilding.

## Binary payload

In binary node reader `FUN_14007abe0`, source kind `0x121` selects a `0x2e8` TriMesh-derived node. It copies binary floats at `+0x27c/+0x280/+0x284` to node displacement/tightness/period at `+0x2d8/+0x2dc/+0x2e0`, then calls common node/mesh readers `0x140078ab0` and `0x14007be10`. The binary branch installs the same subtype parse/postprocess/CreateInstance/GenVertices/cleanup targets as the text constructor. Only when binary constraint count `+0x274` is nonzero does it resize the node's float list and copy `count × 4` bytes from the binary-relative offset at `+0x270`. The shared binary reader's face/index/vertex-pool work is covered in `model-name-parser-tree.md`. The static path establishes source offset arithmetic, not validation of malformed offsets or counts.

## Typed Part and render boundary

`CreateInstanceTreeR` `0x14008dab0` calls node `+0x28` at `0x14008dae0`, resolving for this subtype to `MdlNodeDanglyMeshCreateInstance` `0x140092760`. It allocates a `0xe0` `PartTriMesh`, calls the base Part constructor, installs the `PartDanglyMesh` vtable, initializes dynamic fields and copies node `+0x224` to Part `+0xac`. `PartInitMaterial` `0x140093850` descends only when the Part can be viewed as a TriMesh; after Skin and AnimMesh tests, a positive `AsPartDanglyMesh` result at `0x140093927` selects `VertexPrimitiveDangly` construction `0x1400aaf80` and stores the primitive in Part `+0x90`. It can also load material textures before that test.

The visible scene bucket branch tests `AsPartDanglyMesh` and invokes `PartDanglyMesh::Animate` via `+0xd0` at `0x1400d7709`; its wind/dynamic-pool continuation is in `bucket-classification.md` and `original-scene-animation-nonemitter.md`. `PartDanglyMesh::Draw` `0x1400a22d0` requires an active Part, a nonnull source node, nonzero face count, and a vertex count or temporary vertex data. It sets transform/primitive state and conditionally calls `RenderBumpyShiny` if the material has that map and bumpy water is enabled; otherwise the environment/material branch calls `RenderEnvironmentMapped` or `RenderFlat`. The primitive-to-GL continuation is already mapped in `part-draw-subclasses.md`, `primitive-vdo-preparation.md`, and `geometry-and-draw-boundary.md`.

## Open boundaries

- Shared TriMesh field parsing, binary face/index decoding, material texture loading, and individual attribute-pool branches are reached here but remain delegated to their existing supplements. This document does not assert those branches are always taken.
- The computed `+0xa0`, `+0xa8`, `+0x28`, animation, and Part-type targets are proven for the constructor-installed Dangly subtype. Other runtime writes to those fields are not ruled out.
- Malformed binary offsets/counts and text list error behavior are not established as safe by these normal-path observations.
- This static map does not establish per-frame frequency, actual visible population, or performance cost.

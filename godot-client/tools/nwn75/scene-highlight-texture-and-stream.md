# NWN-75: highlight texture and zero-vertex stream closure

Scope: installed `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This extends [auxiliary passes](scene-auxiliary-passes.md) and the [optional pass callsite census](scene-optional-pass-callsite-census.md) beyond their already recorded immediate calls. It does not claim that highlights are active in a particular frame.

## Texture producer and consumer

`Scene::SetHighlightGobTexture` `0x1400d3420` is the Scene virtual at vtable `0x140d8dd30+0x128` (`0x140d8de58`). It removes the prior Scene `+0xa0` safe-pointer registration, calls `AurTextureRelease` `0x1400e9130` at `0x1400d348d` **with a null argument** (`XOR ECX,ECX` at `0x1400d347d`), calls `AurTextureGetReference` `0x1400e8b60` at `0x1400d349a` with the supplied name, and assigns the result into Scene `+0xa0` through `SafePointer<CAurTexture>::operator=` `0x14004bb00` at `0x1400d34af`. The null-argument call does not establish release of the prior texture. The reference helper calls `AurTextureGet` `0x1400e8100` twice (`0x1400e8b79/0x1400e8b96`); its generic resource and publication descendants are covered in the texture/resource notes. The safe-pointer assignment removes an old observer registration and adds the new one, growing its registration array when full. Evidence: `ev_4f6d163576f0808117f29597fe6dd79365d7d7d67ae8158c98737c71ded9285c`, `ev_75368d94af22e27b50b2177d95fe61232ce2fad1041ccdff4e4806e4f84764d8`, `ev_6ac4832371265af1bf9231abcd2de2354c477796a67178e81b1fc25603e0bf57`.

`Scene::DoHighlightGob` `0x1400c8260` consumes Scene `+0xa0` only when its highlight count `+0x88` is positive and the pointer is nonnull. Its computed call `0x1400c83be` uses texture vtable `0x140d90c70+0x100=CAurTexture::BindInUnit` `0x1400ea490`, which reaches the already mapped texture/GL bind path. The pinned slot bytes are reproduced by [highlight Part slot audit](audit-highlight-part-slots.cjs). The setter's analyzed incoming references contain its vtable entry and data references but no direct code caller; [client area setup](scene-highlight-texture-caller.md) supplies one verified virtual caller and the literal name `fxpa_dot02`. Other indirect callers remain open. Evidence: `ev_4b3f5f7c91ac25cd3d4a04937f20eb41a1bacd8412d489062083ef814f4fba49`, `ev_ac9380e2ae3fb1df0fdc420e25ff94be22bf758b7794fe0969f108298ddac332`.

## Full RTTI-backed Part selector scope

`WritePartHighlightVertices` `0x1400d4f30` calls Part virtual `+0x58=AsPartTriMesh` at `0x1400d5022`, then `+0xa0=AsPartSkin` at `0x1400d502f`. The pinned executable's 18 RTTI-backed primary Part vtables have only **two targets per slot**. TriMesh, Skin, AnimMesh, DanglyMesh and AABB use `PartTriMesh::AsPartTriMesh` `0x14008c4e0` (self); the other 13 use `Part::AsPartTriMesh` `0x1400616f0` (null). Only Skin uses `PartSkin::AsPartSkin` `0x14008c4d0` (self); the other 17 use `Part::AsPartSkin` `0x1400616e0` (null). The complete per-table rows are reproducible with `audit-highlight-part-slots.cjs`, using the [RTTI Part census](part-draw-rtti-census-ledger.json) as its table inventory. These are candidate dispatches for admitted subtype objects, not runtime frequency claims. Evidence for selector bodies: `ev_ceaad6e516e22997f57e7cec2e23d766559ff33e9dfa74a1a311cdd9ae5b3a08`, `ev_7dbd4e99a09b06cc9cb4fd3bcc976e53757b47a617515998ae620f86b530a932`, `ev_ce442f03bfc4b9f913150f87ed58f3016289dcf59548a0a1bd6a5f0bbcea53c8`, `ev_85e0f0cb28d11582cb5ec6bb4d395b10ebb217ed08b15e2b56848f902042fd14`.

The CPU producer skips invisible Parts; for visible Parts it composes transforms and recursively visits children. It emits outline geometry only when `AsPartTriMesh` is nonnull and `AsPartSkin` is null. Its `MdlNode::AsMdlNodeTriMesh` `0x14008c360` call at `0x1400d50a8` returns self only if model-node flags `+0x98` include `0x21`; the producer then reads that node's bounding box and emits three groups of six vertices. `PartAABB` also has a self-returning `AsPartTriMesh` slot, so the slot census alone does not exclude it from this branch; whether its model-node flags and object state satisfy the subsequent dereference is a separate runtime question. Evidence: `ev_a9159a320254fa50722d89dc3015811733fb8df07d0450e7d33dc66819ffdb90`, `ev_ddda084c62ef70937d23813090051d2ab332a2937625fe305db598c081e2d31f`.

## Zero-count submission boundary

For each highlighted Gob, `DoHighlightGob` resets vertex count, calls `GetVertexData` `0x1400bd890`, the CPU producer, `CommitVertexData` `0x1400bd5d0` at `0x1400c863c`, and `RenderVertexStreamData` `0x1400beed0` at `0x1400c8654`. Each attached Gob passing its visibility/attachment filters repeats those steps at `0x1400c876e/0x1400c8786`. There is **no post-producer nonzero-count guard** in either caller branch. A Part tree with no emitted outline vertices therefore submits count zero. `CommitVertexData` forwards `count × stride` to `RenderInterface::UnlockPool` `0x1400bf3d0` → `GLRender::UnlockPool` `0x1400bbad0` → `FUN_1400bbaf0`; the latter returns before buffer publication when byte count is zero. In contrast, nonnull `GLRender::RenderVertexStreamData` `0x1400b5c20` still sets the stream and program and reaches `glDrawArrays(..., count=0)` for this unindexed stream (or `glDrawElements` for an indexed stream). It does not contain a count-zero early exit. Evidence: `ev_4b3f5f7c91ac25cd3d4a04937f20eb41a1bacd8412d489062083ef814f4fba49`, `ev_71e930d1efbf7426cd7d3969222610941cc416b18acb16119d2f7887e428c1e6`, `ev_e83d601a6cdb6ddff4c4c13c508896de862ad8a24d41171019061c15c2a086e8`, `ev_faed7a96ea930f48e2170d7800f7dc1d4110c2b5267b35fe6813a21dee29899a`.

This is a concrete native behavior and possible low-cost draw guard for a future optimization comparison. No captured frame establishes how often zero-count highlights occur or their measured cost. The [area setup setter invocation](scene-highlight-texture-caller.md) and authored name are now verified; other indirect invocations and runtime Part subtype distribution remain open.

## Highlight producer and owned geometry

`AurPartTriggerCreate` `0x1400ef450` defaults PartTrigger highlight `+0xd8`, pass selector `+0xe0` and pulsing flag `+0xf4` to zero. The connected trigger message route creates that Part and stores it at client trigger object `+0x1b0`; `FUN_14086f1d0` calls `FUN_14086fa60` `0x14086fa60` after creation, while update handlers `FUN_1407b1d30` and `FUN_14086f2a0` also call it. This is the one analyzed direct caller of both `AurPartTriggerSetHighlightParams` `0x1400efa60` and `AurPartTriggerSetHighlight` `0x1400efa50`. Depending on object state, GM permission and a client setting, it selects highlight RGB and alpha (zero, 0.25 or 0.35 in the observed branches), publishes color/alpha/pulse parameters, then calls SetHighlight with `true`, object `+0x194` height and pass flag `true`. The static branches do not establish a particular live color or trigger count. Evidence: creation `ev_d48a8a44b8419a61ebbdfed632e96969cd5cd9fe943484996e4440613f1bb5cf`, update `ev_fe3af54390f01eff8af083373fafbaf21c399b754f13a12cf5902a0b12c8dccc`, setter incoming `ev_92d02d157ec7202527515ce17644d28c4cafd8ef272b1aca33841e0bda539079`, `ev_183782d8373e5b5a2b3a66f346fa3ef59f1accc54e77fac4fb9d94200b5434d1`.

`AurPartTriggerSetHighlightParams` stores RGB at PartTrigger `+0xe4..+0xec`, alpha `+0xf0`, pulse flag `+0xf4` and frequency `+0xf8`. `AurPartTriggerSetHighlight` stores the enabled byte `+0xd8`, pass selector `+0xe0`, and absolute height `+0xdc`. If enabled with more than one boundary point `+0x98`, it resets counts and rebuilds Part-owned elevated/lowered boundary lists at `+0xa0/+0xb0/+0xc0` from the original point array `+0x90`; capacity grows only when required, and its bounding box is updated. These CPU lists are built on highlight-setting calls, not inside the frame's `DoHighlightTriggers`. The frame's stencil volume renderer below instead generates a transient indexed vertex stream from the original points and height. Evidence: params `ev_b158e3c969c152d76c8b6764fdca81047691c5b8f2414d0d295874adb3871ff2`, highlight setter `ev_88aa4242fa0e00797a93f4c0ee8da5bf87285849623c65e5d11584b60a40f19c`.

## Two Scene stages and GL boundary

`Scene::RenderSinglePass` invokes Scene virtual `+0x1f0=DoHighlightTriggers` twice: at `0x1400d1841` with bool **false** before shadows and at `0x1400d23b7` with bool **true** after water. Original instructions `xor edx,edx` and `mov dl,1` establish the two arguments. `DoHighlightTriggers` `0x1400c8930` first filters `_triggerbucket` for PartTrigger `+0xd8 != 0` and `+0xe0 == pass_bool` into a temporary growable pointer array. A zero selected count avoids stencil/outline work. The network-trigger update path above sets `+0xe0=true`, placing those admitted highlights in the second stage. Trigger bucket source, BSP visibility and deletion are in [message to draw](trigger-message-to-scene-draw.md) and [BSP visible callback](scene-bsp-visible-callback.md). Evidence: false/true instructions `ev_a0589d64c4af8fdbd74fde9a835fee162a0a6c393babcfa9c22e8b330fd00889`, `ev_5ed55657f2a3819b6a4fedd22193128f1e0388a06a647e4ba7efb76a7d35cd19`, Scene body `ev_75cce1234a5f9cbb8ab6f83e3f01fd564764091b87ae9dd4d8ef250a192c29fd`.

For each selected trigger, the Scene clears stencil to `0x7f`, enables stencil writes, clears the stencil buffer, disables color writes, and invokes PartTrigger virtual `+0xf8=DrawVolume` twice: `0x1400c8b22` with one stencil operation/front-face mode, then `0x1400c8b46` with the opposite. The constructor-backed `PartTrigger` table resolves both calls to `0x1400f02e0`. `DrawVolume` requests/reuses a shared indexed stream sized for `2*n+2` vertices and `6*n` element indices (`n=PartTrigger+0x98` original boundary count), copies the point ring at Z ± `+0xdc`, adds two center vertices, writes the index strip, commits element and vertex data, and calls `RenderInterface::RenderVertexStreamData` with primitive `4`. Because Scene calls it twice, this transient vertex/index generation and both commits run twice per selected trigger under the observed code, even though the source Part and height are unchanged between calls. Primitive 4 maps through `0x140d8ad20` to enum 5 (`GL_TRIANGLE_STRIP`); the indexed stream reaches imported `glDrawElements`. State wrappers reach `glClearStencil`, `glClear`, `glStencilFunc`, `glFrontFace` and conditional cached GL state changes as already mapped in [shadow/stencil APIs](scene-shadow-stencil-apis.md). Evidence: Scene body above, Part volume `ev_fd708248871d7d8925ed2836de64b0788bccb72c1819edeebdeaae718d857c62`, primitive table `ev_86029388673407b6b80a9ce6cdea01e45dc807d026f86191208263f57ea2e915`.

After stencil volumes, the Scene restores color writes, computes six camera-oriented outline vectors with cross/normalize operations, allocates a small transient `List<Vector>`, translates to the camera position, sets color from Part `+0xe4..+0xf0` (with sine-driven alpha only if pulse flag `+0xf4` is set), and calls `RenderInterface::DrawFromVerts` `0x1400bea50` with primitive `3`. That thunk forwards to `GLRender::DrawFromVerts` `0x1400b1be0`, which requests/reuses a nonindexed stream, copies the list, commits vertex data and calls `GLRender::RenderVertexStreamData` → imported `glDrawArrays`. Primitive 3 maps to enum 4 (`GL_TRIANGLES`). The temporary outline list and filtered pointer array are freed before returning; rendering does not own the Part. Evidence: Scene body above, DrawFromVerts `ev_0b448edfb5a4d60f77fa41a07a63e9c85fd55ddf1635e8766655adc7fc1b1495`, shared stream renderer `ev_faed7a96ea930f48e2170d7800f7dc1d4110c2b5267b35fe6813a21dee29899a`.

The per-trigger duplicate volume construction is an original-code structural observation, not a recommendation or measured hotspot. Runtime presence of highlighted triggers, stencil state changes and driver cost remain unmeasured.

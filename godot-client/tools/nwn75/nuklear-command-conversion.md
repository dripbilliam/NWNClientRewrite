# NWN-75: original UI command conversion

Status: **partial original-binary map**. The source is the installed `nwmain.exe`, SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. Addresses are image virtual addresses. Ghidra pseudocode is reconstructed machine-code behavior, not original source. This records what the original does; it makes no comparison or recommendation.

`0x140a71760` sets up the GL UI draw pass and calls `0x140a7c340`. The latter rejects missing input/output pointers, initializes conversion state, optionally prepares the command list, then walks a linked command chain. Each command begins with a numeric kind and a next-command offset. The converter returns a bitmask that tests the capacities of the command, vertex, and index buffers; its caller then draws the converted command list through `glDrawElements`. Converter evidence: REA `ev_ad209304a0b1e3d9ce73250523f0be0b533a57ffa37433b89d53a3d9236ce940`. The caller's draw evidence and external GL pointer resolution are in `gui-presentation.md` and `nuklear-gl-callsites.json`.

The optional prepass `0x140a60b00` is now traversed. It initializes a pending command pointer from context state, conditionally emits an image command through `0x140a7db90`, then walks command-linked records to patch their next offsets and clear a transient flag. The image producer rejects empty/outside-clip rectangles and otherwise calls central allocator `0x140a619c0` with numeric kind `0x11` (17) and size `0x38`, writing bounds, texture/UV data and color. This is CPU command preparation, not an extra GL draw. The Ghidra body contains questionable pointer arithmetic in its list loops, so this map identifies branch purpose and called targets without asserting a precise list count or cost. REA `ev_64dad159dd9722d4aa71d1c49c8a94d50a30313fcc1319bb3f931bfd95a1e864`, producer `ev_818a30b40c225f53acb4567e65082a238a7bdfd32e7aea13956b96626dcca278`.

The central command allocator `0x140a619c0` stores the numeric kind and linked next offset after reserving aligned command bytes through `0x140a60850` (REA `ev_9cd214bbe564915bfe9784267d27360442c7dd05eee036bef954331cd793f2c7`). Its Ghidra incoming-reference census found 21 distinct direct caller procedures. Inspecting the numeric kind passed at those callsites accounts for **every converter case 1–18**. `nuklear-command-producers.json` lists all 21 callers with individual REA evidence IDs; the incoming-reference census is `ev_d5ff3259fb576944c4c5aefc7d7d0998afcfe3c972e8e3810196bbb32614608c`. This is a static producer/consumer mapping, not proof that every command is emitted in gameplay or that no callback constructs commands through another route. Two concrete higher-level producers are the UI context finalizer's rectangle and triangle helpers, as described in `gui-presentation.md`.

The next static caller layer is in `nuklear-producer-incoming.json`: **169 direct callsites** into those 21 producer procedures, each with the enclosing caller address and per-query evidence. Three producer procedures (`0x140a8c270` for kind 11, `0x140a8bea0` for kind 13, and `0x140a89050` for kind 18) have no observed direct incoming calls. They could be reached through computed function pointers, called by code Ghidra did not recover, or be unused; this census does not distinguish those possibilities. The other producers have direct upstream paths, but most are still one or more call layers away from a named live UI entry. The allocator-caller census is not exhaustive for **inline writers**: `0x140a67830` reserves through lower buffer helper `0x140a60850` and writes numeric kind `0x11` (17) itself, as mapped below.

The JSON SingleGroup content path `0x140950d90` → virtual `+0x38` target `0x140952960` → `0x140951260` reaches an image nine-slice helper `0x140a7d2e0`. That helper subdivides source margins and destination rectangles, then repeatedly calls `0x140a67830`. The latter clips each tiled rectangle, reserves a `0x38`-byte command with `0x140a60850`, writes kind `0x11` (17), texture/UVs, dimensions, color and next offset directly. The ordinary converter's kind-17 case later turns those commands into textured quads; this is a concrete inline producer outside the 21 direct callers of `0x140a619c0`. REA parent content body `ev_fad75cefad3cd5f81b65559a485d8c263e4b4dddc0ad801c7d6dbbc2cf0195da`, helper `ev_49aaee944cf97cdd317a2daba0b1d67ea8cf43552e4df91b1ebc525f9c98c24d`, writer `ev_7c927d99bfa67d10319a3dfebdc21eb0dc6d58a9d410edac3d634f5308218551`.

## Numeric command switch

These labels describe **observed geometry behavior**. They do not assume a source enum. The common geometry sinks are `0x140a7f960` (append one XY point), `0x140a7fa60` (rectangle/path point generation), `0x140a7f150` (trigonometric arc point generation), `0x140a7fc30` (stroke path), `0x140a7f8e0` (fill path), and `0x140a688a0` (emit a textured quad). Most colored shape cases gate on a nonzero top byte of the command color. `0x140a7fc30` forwards to stroke geometry `0x140a80140`; `0x140a7f8e0` forwards to fill geometry `0x140a7e160`. Those descend into vertex/index buffer allocation and writes, not GL draw calls.

The converter has a 19th path for unknown numeric kinds: no case-specific geometry before moving to the next command. An incomplete buffer can stop conversion with capacity bits; it does not silently turn into a GL draw. The case dispatch and linked traversal are visible in the converter evidence above.

The UI draw caller invokes the converter once at `0x140a71cc4` and immediately loads the `glUnmapBuffer` pointer at `0x140a71cc9`; it does not branch on the converter return register before the later command walk. The converter's byte return encodes capacity state from the command, vertex, and index output buffers (bits `2`, `4`, and `8` in the decompilation), or `1` for invalid initial arguments. Thus the observed draw loop can consume whatever converted commands were produced before a capacity stop. This is the original binary's handling, not a claim that buffer exhaustion occurs in ordinary frames. REA `ev_ad209304a0b1e3d9ce73250523f0be0b533a57ffa37433b89d53a3d9236ce940`, `ev_2b357f519fe7a5348b5a800538846f94df8cbad2a079187e676cc861758872c2`, instructions `ev_8a6f4c264bb8f17eca43c315ef9a73b1474b80b80d33e75597762902c8d19e58`, `ev_763e178de82528bdfba0ec1ae4e1c3d97040f8a6696ba22e15c5116c2d12dc2b`.

## Descendant behavior and boundaries

`0x140a7f960` appends XY data to the path buffer, creating a full-range clip record if none exists (REA `ev_8d3344558c9a2b16fb9d6b516cffccbbebb492c40a8434e197ab2e3b9f78b073`). The clip-record builder `0x140a685b0` can grow its backing buffer through allocator/free callbacks stored in the buffer object (REA `ev_460f4c73152f36611cfbeefea6c37a781d42f2466ac01a7ebc2d1f27dc2ed600`). `0x140a7fa60` emits rectangle corners or rounded corner segments (REA `ev_1027bd48221b1edf5444c7ed7a392ba6df1c5f7ffc10d561a26e3f78bea0f72b`). `0x140a7f150` advances trigonometric arc points (REA `ev_7f761635a2a9e55f10bab1d36ba350250d1dac254a26d468f5a14dfd98d5a1d4`).

For the observed UI draw's successfully mapped vertex and index buffers, `0x140a71760` zeroes each stack buffer object and sets mode `+0x38` to `0`, backing pointer `+0x40` to the mapped GL buffer, and capacities `0x80000`/`0x20000` before calling the converter. `0x140a60850` enters its stored allocator/free callback growth branch only when mode `+0x38` is `1` and those pointers are present. Thus this particular mapped-buffer conversion does not invoke the growth callbacks; it can report capacity exhaustion instead. This does not classify other dynamic command or atlas buffers. REA draw `ev_6b5e1be5df3d0ec1c19e05d9f5114d2a9453a5c0bd89c9f09f1a3012d4826278`, reserve helper `ev_576b0c3c184f25f6ffdf9783b9fa486f0583cf04bbd9f0e3e84780b87b3bbe61`.

The global UI command buffer is the distinct dynamic case. Device creator `0x140a6f9d0` zeroes its object at `0x1414299d8`, sets mode `+0x38` (`0x141429a10`) to `1`, directly allocates an initial `0x1000` bytes through `0x140a6c550` at `0x140a6fa6d`, and installs that same allocation callback at `+0x28` (`0x141429a00`) plus free callback `0x140a6c890` at `+0x30` (`0x141429a08`). On capacity growth, reserve helper `0x140a60850` reads the installed allocator at `0x140a60920`, calls it at `0x140a609db`, copies old bytes, and conditionally invokes the installed free callback at `0x140a60a06`. The allocator wrapper reaches CRT `_malloc_base` and Windows `HeapAlloc`; growth therefore performs conditional CPU allocation and copy, not GL work. This identifies the callbacks for this installed global buffer; other buffer instances still require their own setup evidence. REA device creator `ev_faee64a092bd08c0f8a48f20e46fa3e4718facf1914d4368cd7004c1f12ad9d7`, setup instructions `ev_2bd7b2050ccdb4878d73085596fb1c848c8ae7d39b44d75e4b2464a5d4e78a39`, `ev_5038bdd2b73d9ade1816086e3fe30a290d3f011f267b91a42ef7373e8951dd40`, `ev_293e221d65c6b3a11260447eb4fa5e0312ea1ea6656800069e1b2619ff3907dc`, `ev_4351672b478e766e8a66f25bc77d3b97daf68f61080d505a822c1674467f9fe8`; reserve instructions `ev_ce13ba049befa01bcd7d73b089f8d91da62bea225aa37f511aec5209083719b1`, `ev_7646821810b9ed32616a2a7dddee6902a1050c74d3be517a97e3d11ce80cf9ba`.

Stroke helper `0x140a7fc30` dispatches to `0x140a80140` (REA `ev_bbb116c2aa45fbd72ba4744ffd5b60c051421473387f4651280aad0e52439a60`, `ev_00e95f761e27ff2cda402cd9251fad1900ce00deb485d80c31742f5c2766e089`). Fill helper `0x140a7f8e0` dispatches to `0x140a7e160` (REA `ev_aa3c16e2cd0bd6830a45121f1e0c7258d844853db4d2bcfc73e60630e0731fb0`, `ev_980292811eefe60e214553c122feed31a1f490a96cc0d19325a063e3c3fa6ed9`). Both geometry functions allocate vertex and index storage and write per-vertex attributes. They have branches for shape closure, line thickness, joins, and anti-alias settings. Buffer helper `0x140a60850` reserves aligned bytes, optionally invokes allocator/free callbacks on growth (REA `ev_576b0c3c184f25f6ffdf9783b9fa486f0583cf04bbd9f0e3e84780b87b3bbe61`). `0x140a684c0` reserves index data and increments command/global index counts (REA `ev_30ee3f5b07d452a23bf047f2be5d3490430a57df110638c88f48dbc58417e064`). Vertex writer `0x140a69500` walks the configured attribute layout and delegates typed values to `0x140a69850`/`0x140a695b0` (REA `ev_8101f1d71d3fa987f57f20e13031cebe5d9e6156b7178117814d3442b5b54967`). These are still conversion work before the GL draw boundary.

The colored-quad helper `0x140a7eb70` allocates four vertices and six indices and writes the four corner colors (REA `ev_0c35aac0b11c3c3c385e8539610ed1249c13452fd684872b4b632695119e08d6`). The textured-quad helper `0x140a688a0` does the same for one color/UV texture rectangle (REA `ev_4031626fc1ae2932fc9d3274bc46d9d1d6057b8e8eeb76046be9c4ec39bf506f`). `0x140a919a0` decodes UTF-8 code points, including its invalid-sequence sentinel (REA `ev_28ed287eb7953403f6b35f89454d951e83ec5d703e1ea9166600d00615304a08`).

The font callback for the observed baked-atlas route is now resolved. `nk_sdl_refresh_config` (`0x140a70d90`) builds font entries through `0x140a824b0`, bakes them through `0x140a82f20`, uploads the atlas through `0x140a6fe10`, and publishes the active font view as baked-entry pointer `+8` at `0x141429c20`. During baking, `0x140a82f20` writes the text-width function `0x140a6ba50` at baked-entry `+0x18` and glyph function `0x140a6b9a0` at `+0x20`. Relative to the published `+8` view, these are callback slots `+0x10` and `+0x18`. The kind-16 producer `0x140a81600` measures text through the former and stores that font view in its command; converter `0x140a7de20` invokes the latter at view slot `+0x18` for each decoded glyph. `0x140a6b9a0` scales glyph bounds, advance, and UV coordinates using a glyph record selected by `0x140a840c0`; the selector scans configured codepoint ranges and returns a fallback glyph when absent. This binds the previously targetless glyph call for baked fonts. Other font-view producers or substitutions are not established by this edge.

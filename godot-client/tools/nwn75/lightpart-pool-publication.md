# NWN-75 original mesh relighting pool publication gates

Pinned installed `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This [ledger](lightpart-pool-publication-ledger.json) narrows the shared pool route from `Scene::LightPartTriMesh` `0x1400da970`. The [BSP light callbacks](scene-bsp-light-callbacks.md) establish two callers: `LightNodeMeshes` at `0x1400da64f` after a full-dynamic-lighting mode change, and `LightNodeTile` at `0x1400da8ff` for queued static-light nodes in non-full-dynamic mode. The [geometry/draw boundary](geometry-and-draw-boundary.md) already maps the overall relighting loop; this supplement separates its four pool releases by lock mode and identifies which can reach GL.

`LightPartTriMesh` rejects missing mesh data or unsuitable render hints. In non-full-dynamic mode it requests/resizes the color pool and, for render hints `2` or `3`, an optional bump-direction pool, then marks the primitive for rebuild. It locks the source position pool (`geometry+0x280`) at `0x1400dab55` and source normal pool (`geometry+0x298`) at `0x1400dab6e` with `R9D=8`; it locks output color (`Part+0x98`) at `0x1400dab83` and optional output bump (`Part+0xb0`) at `0x1400daba6` with `R9D=1`. `GLRender::LockPool` `0x1400b4aa0` writes that mode byte to pool descriptor `+0x11` at `0x1400b4aba` for a valid token; a sentinel `-1` token instead returns a raw offset. The per-vertex/light color and bump computations write CPU pool memory. REA relighting `ev_cb426a7c87fdacdfa7c64ec288930463d36e55b83636183481abe6081bb40606`, lock body `ev_bdb5e45aed03bf964d0a183c0ed5c6b6d31eb1890c7f59f7bc39bb8a202a17ba`.

The four corresponding `RenderInterface::UnlockPool` `0x1400bf3d0` calls are output bump `0x1400db26e`, output color `0x1400db282`, source positions `0x1400db2a0`, and source normals `0x1400db2be`. The pinned call setup passes `(pool ID, 0xffffffff, 0)` each time. `GLRender::UnlockPool` `0x1400bbad0` remaps registers to helper `0x1400bbaf0` as `(manager, pool ID, 0xffffffff, 0)`. The helper rejects sentinel/invalid pool IDs, zero request size, zero pool length, and a descriptor mode byte whose `+0x11 & 0x18` is nonzero before its GL branch. Therefore valid source pools locked with mode `8` **exit before GL buffer operations** at these two release sites. Valid color and optional bump pools locked with mode `1` pass this particular mode gate and **may** publish; their allocation, GPU-backed and dirty state select the later calls. The original input's final zero is an offset, not a no-upload flag. REA wrapper `ev_2bfe9d4aaf6e1752de5f7ec3e6a2982167327b34d9793c4fdb882dfbfbe59e75`, helper `ev_1f419d8f1c259c3e858798205ae5140de9198499fa4f2e2577aebc524ab8df12`.

On an admitted output-pool branch, helper `0x1400bbaf0` can call `RenderInterface::BindBuffer` at `0x1400bbb95` and loader-resolved `glGenBuffers` at `0x1400bbb5d`, `glBufferData` at `0x1400bbbd4/0x1400bbc40/0x1400bbc93`, or `glBufferSubData` at `0x1400bbc0b/0x1400bbc6b`. The buffer path differs for first allocation, dynamic orphan/update and static storage; no one GL site is guaranteed by a relighting call. The original pointer loader maps `glGenBuffers`, `glBindBuffer`, `glBufferData`, and `glBufferSubData` at globals `0x141442470/0x141442440/0x141442448/0x141442450`, as recorded in [GL extension pointers](gl-extension-pointers.json). Later primitive rebuild and ordinary mesh draw form a separate VDO/draw route in [primitive preparation](primitive-vdo-preparation.md). This branch establishes a potential upload from output relighting pools and no upload from the two source-read releases; it does not measure whether either caller, optional bump pool, or pool-state gate is active in a live frame.

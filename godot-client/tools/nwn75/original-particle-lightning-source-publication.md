## Model/resource admission and emitter mode

`NewCAurObject` `0x1400931f0` obtains a model through `FindModel` or `LoadModel` `0x1400a0130` and builds its Part tree with `CreateInstanceTreeR` `0x14008dab0`. `LoadModel` calls `IODispatcher::ReadSync` `0x140079e40` at `0x1400a016b`. Its text branch reads resource lines and calls `FuncInterp` at `0x140079f35`; its compiled-data branch calls `FUN_140079d50` `0x140079d50` to copy resource chunks and reconstruct a `MaxTree` through `FUN_140079f90` `0x140079f90`. `Model::InternalParseField` `0x14009ff50` recognizes `node` and calls `ParseNode` `0x1400a0d90` at `0x1400a00ff`. `ParseNode` recognizes `emitter`, calls `MdlNodeEmitter::MdlNodeEmitter` `0x1400875a0` at `0x1400a0e94`, passes each line up to `endnode` to its installed ParseField function at `0x1400a109f`, and calls its PostProcess at `0x1400a10b3`. Thus the parser does not skip later authored fields. ## Segment count and timing data

The text parser registers `birthrate`, `birthratekey`, and `birthratebezierkey` at `0x14009b677/0x14009b6b5/0x14009b6f3` as controller entries targeting Part offset `0x74`. Likewise `lightningDelay` and its key/bezier forms at `0x14009d32b/0x14009d369/0x14009d3a7` target `0xec`; `lightningRadius` at `0x14009d437/0x14009d475/0x14009d4b3` targets `0xf0`; `lightningScale` at `0x14009cdd7/0x14009ce15/0x14009ce53` targets `0xf4`. `MdlNodeEmitter::MdlNodeEmitter` installs `MdlNodeEmitterControl` into node `+0x18`. When `AnimateHierarchy` selects this controller for an active run, `MdlNodeEmitter::InternalControl` `0x140052400` admits an emitter Part, calls `MdlNode::InternalControl` `0x140051c50`, and then recalculates radius. The base control samples the saved float keys and blends into `Part + controller offset`; this is the producer of Lightning's `PartEmitter+0x74` count and `+0xec` interval. `LightningEmitter::Update` `0x140065290` converts `+0x74` to an integer segment count and compares timer `+0x1c8` with `+0xec`. `PartEmitter::PartEmitter` `0x140060420` explicitly initializes `+0x74=0`, `+0xec=0`, and `+0xf0/+0xf4=0` before controller publication. These are instance defaults, not evidence that any live authored emitter remains at zero. ## Referenced target Gob and terminal effects

An authored `reference` node's `refModel` line is parsed at `MdlNodeReference::InternalParseField` `0x14009e620` (string reference `0x14009e698`) into node `+0xa0`; `reattachable` goes to `+0xe0`. Its `InternalCreateInstance` `0x140091af0` constructs a PartReference carrying the source node at `+0x8`. After the model Part tree is built, `CreateReferenceObjects` `0x14008db90` recursively checks each Part's virtual `+0x70=AsPartReference`, calls `NewCAurObject` for the admitted node's `refModel` at `0x14008dbe3`, stores the new Gob at PartReference `+0x68` at `0x14008dbee`, and calls that Gob's virtual `+0x98=AttachToObject` with owner Gob and reference Part name at `0x14008dc0e`. `NewCAurObject` raises `_EmitterTarget` through Gob `DoEvent` after its reference objects have been built; `Gob::Append` `0x14008c0c0` also creates references for the appended Part tree and raises that event at `0x14008c1f8`. `LightningEmitter::Initialize` registers `SetEmitterTarget` `0x1400643c0` for `_EmitterTarget` on its owner Gob. `Gob::DoEvent` `0x140050d50` scans its callback list backward, matches the event name case-insensitively and invokes the registered function field `+0x20`. `SetEmitterTarget` walks emitter child Parts, accepts the first Reference view, and copies its referenced Gob `+0x68` into emitter `+0x1c0`. It samples target `Gob::GetPosition` `0x140048530`, a CPU leaf that copies Gob position `+0xa8..+0xb0`, then writes CPU target distance/direction/origin state. With no admitted reference it calls `Gob::DeregisterCallback` `0x140050cb0`, which removes and frees the matching callback record. Neither event callback nor these terminal Gob methods directly issues GL. This particular target is an owned referenced Gob whose attachment, recursive model creation and destructor are mapped in [non-emitter animation](original-scene-animation-nonemitter.md); its later visibility and draw depend on Scene membership and the common model/draw path. The Lightning update uses `+0x1c0`, `+0x74`, `+0xec/+0xf0/+0xf4` for CPU particle list/geometry writes and can call `RecursiveFractal`; only Scene's later selected render callback can reach `RenderInterface::RenderVertexStreamData` and conditional `glDrawArrays`. A missing target or zero integer count instead recycles live particles to the CPU reuse list. Runtime event ordering, exact authored model names and controller values, reference success, and actual GL draw remain open.

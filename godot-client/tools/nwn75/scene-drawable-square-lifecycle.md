# NWN-75: drawable-square queue producer and lifetime

Scope: installed `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This closes the queue ownership frontier left by [auxiliary passes](scene-auxiliary-passes.md) and its [19-site direct-call census](scene-optional-pass-callsite-census.md). It does not infer a live frame's queue size.

## Producer and removal

The only analyzed direct caller of `AurAddDrawableSquare` `0x1400a4df0` is `FUN_1406f02c0` at `0x1406f0bde`. Its body handles a left-mouse-down path: it first offers the event to `CGuiMan::HandleLMouseDown`, checks client/input mode and a current scene, branches on hit tests and modal keys, and on one admitted path transforms four corner positions through Camera/matrix helpers. It passes those twelve position floats and packed color `0xff00ffff` to `AurAddDrawableSquare`, retaining the returned handle at input object `+0x464` and an active flag at `+0x468`. The exact user-visible mode is not established by this one path. The same body removes an old active square before replacement at `0x1406f0968` and removes an active square on an alternate mouse-down path at `0x1406f0914`. Evidence: `ev_b6c392372ea74e7dd3d6ea71a5925d7e7d4ea8b508b8bcd987200efd55c56654`, incoming refs `ev_4dda2aac9c694decc8747b1652255c15104bfb90f8002608940559d1b5fa5112`.

`AurAddDrawableSquare` requests a 0x40-byte pool allocation (`RenderInterface::RequestPool` `0x1400beee0` at `0x1400a4e17`), locks it at `0x1400a4e2b`, writes four 16-byte packed-color/XYZ vertices, unlocks the full allocation at `0x1400a4e91`, then appends that pool handle through `RenderInterface::AddSquareToRender` `0x1400be7f0` at `0x1400a4e9a`. The interface is a tail jump to `GLRender::AddSquareToRender` `0x1400ad660`. This appends the handle to process-global `_cm_listSquaresToRender` with count `0x141408610`, doubling the handle-array capacity (starting at 16) through `_realloc_base` only when full. It does not deduplicate handles. Evidence: `ev_de5614dfc556bbc8d76d65e495df506c41aaff7a80068893d5117124e64293dd`, `ev_bd9842e69635bec5daec8b36bb403f99c04598dab637cd12330cc737ae43f29c`.

`AurRemoveDrawableSquare` `0x1400a4fe0` first removes the handle from the render queue at `0x1400a4fe8`, then tail-jumps to `RenderInterface::DeletePool` `0x1400be990` at `0x1400a4ff4`. Its queue wrapper jumps to `GLRender::RemoveSquareToRender` `0x1400b5510`: it finds the handle and shifts later 4-byte entries left while decrementing count. At 17 or more handles it temporarily swaps the queried handle with the final entry to make the search bounded, then restores before the same removal. There is no per-render queue clear in the draw body. The only analyzed direct remove callers are the two mouse-down sites above and the left-mouse-up path `FUN_1406f0d80` at `0x1406f105a`; the latter checks input object `+0x154` and active-square flag `+0x468`, clears the flag and removes the retained handle. Other dynamic or external callers remain possible. ## Frame consumer and GL boundary

`Scene::RenderSinglePass` calls global `RenderDrawableSquares` `0x1400cdef0` in its final pass. That wrapper sets a white color, disables selected states, calls `RenderInterface::RenderDrawableSquares` `0x1400beeb0` at `0x1400ce030`, and restores two states. The interface tail-jumps to `GLRender::RenderDrawableSquares` `0x1400b5880`. The GL body caches a stream token in `0x14140ab08`; it requests or grows exact attributes `(capacity,0,5)` only if the token is missing or its vertex capacity is below `4 × queue_count`. It then locks the stream, copies four 16-byte vertices from each retained pool handle in queue order into contiguous stream memory, commits `4 × queue_count` vertices at `0x1400b5985`, and tail-jumps to `GLRender::RenderVertexStreamData` `0x1400b5c20` at `0x1400b59ab` with primitive `6` and that count. The stream uses no element capacity, so the admitted GL route reaches imported `glDrawArrays` `0x1400b5d66`. Repeated frames re-copy and re-commit each still-active square; the original pool keeps the authored four vertices until explicit removal. This is observed work, not a measured bottleneck. Evidence: `ev_eb4e15b6f520cd0fad11bd1f5243014dca3d2c7480b6130fe80df78771a43cfa`, `ev_b0c0fc5f6298a40a78b37327ae350e79d300bdee50a5b0a5c0779523049d2673`, draw boundary `ev_faed7a96ea930f48e2170d7800f7dc1d4110c2b5267b35fe6813a21dee29899a`.

The wrapper and GL body contain no queue-count-zero exit. With zero squares and a nonnull stream token, `CommitVertexData` forwards zero bytes and the pool's `UnlockPool` skips buffer publication, but `RenderVertexStreamData` still selects the stream/program and calls `glDrawArrays(..., count=0)`. This same lower-level zero-count behavior was identified in the [highlight branch](scene-highlight-texture-and-stream.md). On the first zero-square frame, the token request can occur; the static path alone does not establish whether allocation succeeds. Evidence: `ev_b0c0fc5f6298a40a78b37327ae350e79d300bdee50a5b0a5c0779523049d2673`, `ev_e83d601a6cdb6ddff4c4c13c508896de862ad8a24d41171019061c15c2a086e8`, `ev_faed7a96ea930f48e2170d7800f7dc1d4110c2b5267b35fe6813a21dee29899a`.

The handle list is freed/zeroed in process cleanup `FUN_140d78550` `0x140d78550`; it is not reset on every render. Exact runtime square counts, external producers and GPU driver cost remain open. Evidence: `ev_e050ef6dc5ed1b77cd9edee6ad991350c1ad72458dabcccb6ebafd8dd00e57bd`.

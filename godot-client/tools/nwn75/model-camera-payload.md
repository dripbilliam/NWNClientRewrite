# NWN-75: model Camera node and conditional view attachment

Pinned original `nwmain.exe` SHA-256: `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This supplement distinguishes an authored model `camera` node from the active `Camera`/`CAurCamera` view object. It traces text and binary payload to `PartCamera`, controller update, a conditional attachment bridge, and the actual view/Scene boundary. Exact sites and REA IDs are in `model-camera-payload-ledger.json`.

## Text and binary model node

`ParseNode` `0x1400a0d90` selects `MdlNodeCamera::MdlNodeCamera` `0x1400874c0` for text `camera` at `0x1400a0e59`. The constructor first builds a base `MdlNode`, sets kind `9`, and installs Camera parse/control/conjoin/CreateInstance fields `+0x8/+0x18/+0x20/+0x28`. The parse wrapper `0x140092660` tail-jumps via `MdlNodeCamera::InternalParseField` `0x140099e10` to the shared `MdlNode::InternalParseField` `0x140099650`. The Camera subtype adds no separate text parser body. The shared parser accepts position, orientation and scale single/key/bezier controllers into node `+0x78/+0x88`; `inheritcolor` parses into `+0x30`; `parent` resolves a model-node name and updates parent/child links. It also scans `wirecolor` into temporary stack storage; no publication of that local value is visible in this body. A first-token length of at least `0x400` reaches range-check failure. `model-name-parser-tree.md` covers the outer text node loop and nesting.

Binary reader `FUN_14007abe0` compares kind at source `+0x6c` against constant `9` from pinned data `0x140d86858`, allocates a `0xa0` node, copies source `+0x18/+0x1c` to node `+0x30/+0x34`, source `+0x20..+0x3f` to node `+0x38..+0x57`, and retains kind in node `+0x98`. Shared reader `FUN_14007b6c0` loads binary child offsets/count from `+0x48/+0x4c`, controller records from `+0x54/+0x58`, and controller float data from `+0x60/+0x64`, all relative to the binary data base when present. It remaps authored controller destination offsets for the runtime `MdlNode` layout. The Camera binary branch then installs the same parse/control/conjoin/CreateInstance targets as text. No Camera-only binary tail beyond the common node fields and controllers appears in this branch.

## Typed Part and control

`CreateInstanceTreeR` `0x14008dab0` calls node `+0x28`, resolving for this subtype to `MdlNodeCameraCreateInstance` `0x1400925d0`. It allocates a `0x68` base Part, stores the model-node pointer at Part `+0x8`, and installs the `PartCamera` vtable `0x140d88108`. Its inherited `Part::Draw` `0x1400a1c60` immediately returns, so the model Camera node has no direct geometry draw in this Part path.

`MdlNodeCameraControl` `0x1400925c0` reaches `MdlNodeCamera::InternalControl` `0x1400523b0`. Its Part virtual `+0x50` call resolves on the constructed `PartCamera` vtable to `PartCamera::AsPartCamera` `0x14008c3e0`, which returns self; the caller does not use that return. It then tail-transfers to `MdlNode::InternalControl` `0x140051c50`. That base body evaluates authored controller records and blends floats, vectors or quaternions into their recorded Part offsets. Thus the normal model control path updates a Part pose; it does not itself set the active view transform. The surrounding animation traversal is mapped in `original-scene-animation-nonemitter.md`.

## Conditional attachment to the active view

A separate `Camera` object can be attached to a chosen Part. `Camera::AttachToPart` `0x140057820` forwards to `Gob::AttachToPart` `0x14008c6f0`, which asks the chosen Part for its world position/orientation at virtual `+0x18`, creates an attachment behavior according to mode `0..3`, installs it on the Camera's Gob subobject, and sets its Scene. `Camera::AttachToObject` similarly forwards to `Gob::AttachToObject` `0x14008c540`; a null name chooses a root Part, while a name uses Gob virtual `+0x230` to resolve a Part before constructing an attachment behavior. Either route can select a `PartCamera` only if the caller supplies that Part or its name; a concrete authored-camera selection callsite has not been found here.

When an attachment behavior is active, `CAurBehaviorAttach::Control` `0x140054cb0` first updates dependencies and confirms it is still the owner's behavior. If its target and referenced Part remain present, it calls that Part's virtual `+0x18=GetWorld` at `0x140054db4`, writing the owner Gob position/orientation. The Camera object's Gob subobject begins at Camera `+8`, so its Gob position at `+0xa8` is Camera `+0xb0` and orientation at Gob `+0xb4` is Camera `+0xbc`. `Camera::RenderScene` `0x14005a5d0` reads those pose fields, calls `RenderInterface::SetViewTransform` at `0x14005ae0a`, sets `CurrentCamera`, and calls its attached Scene virtual `+0x18` at `0x14005b208`, resolving to `Scene::Render` `0x1400cc730`. It requires Camera Scene `+0x90` and passes viewport/visibility gates; `camera-entry.md` maps the remaining projection and render sequence. This is the actual view boundary, conditional on a live Camera object and a selected attachment Part.

## Open boundaries

- The analyzed Camera attachment methods accept a caller-selected Part or name. This supplement does not prove that a particular game or GUI path selects an authored `PartCamera` rather than another Part, nor that a given model Camera controls the active view.
- `Gob::AttachToObject` virtual `+0x230` name resolution, behavior mode subclasses, and base model controller formats are delegated to existing attachment/animation maps. Other runtime producers of Camera pose remain possible.
- Malformed binary controller offsets/counts, unresolved parent names and text parser failure paths are outside the normal-path static evidence. No frame frequency or performance cost is inferred.

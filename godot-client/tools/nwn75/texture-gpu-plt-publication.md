# GPU PLT palette publication branch

Pinned original `nwmain.exe` SHA-256: `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. The [ledger](texture-gpu-plt-publication-ledger.json) expands the conditional GPU palette path in `CAurTextureBasic::glImageBasic` `0x1400ee1b0` (REA `ev_6777a01a4f84262d4ab2615740bedc94f4ada8b876baf70f51518525885ebfb1`). The ordinary 2D/cube route remains in [texture publication](texture-publication-per-frame.md). The palette route requires a nonnull image `+0x58`, `g_bGeneratePLTOnGPU != 0`, image kind `+0x84 == 4`, and nonnull palette-selection data `+0x48`; failed gates either choose ordinary publication or leave texture ID zero. It is resource publication, not a required draw on each scene frame.

On first admitted use, a global `palettetexbasic` receives a new 0xf0-byte `CAurTextureBasic` named `masterPalette`, configured as a 256-wide image with `paletteheight` rows. The body copies `paletteimage` into its CPU raster and calls its `+0xe8=CAurTexture::glImage` at `0x1400ee821`. `CAurTexture::glImage` `0x1400ee130` resolves a Basic object through `+0x10/+0x8` and calls `glImageBasic` at `0x1400ee16d` (REA `ev_b2e85194d6b4aa14cefdd0f1e6976bc998fd394dd10df86b3e26f3215c2b706f`). The master palette has ordinary image kind, so this nested publication takes the non-PLT texture path; it does not recurse into palette generation under the observed field assignments.

With a valid master-palette texture ID, the path binds it to unit 1, allocates a destination texture ID on unit 0, defines an empty destination with `DirectCreateTexture`, creates or reuses a palette-index texture, and uploads the source index image to it with a second `DirectCreateTexture`. Those wrappers reach `GLRender::DirectCreateTexture` and imported `glTexImage2D` as mapped in [framebuffer effects](framebuffer-effects.md). It saves and changes the viewport, disables two render states, then lazily obtains a shared four-vertex VDO, fills its static data, and commits it. It lazily generates and binds a shared FBO. A thread-local guarded static initializes a shared `vs_pltgen`/`fs_pltgen` custom shader program via `GetCustomShaderProgram`; the [shader branch](shader-program-branch.md) maps compilation/link to GL. Each admitted palette render sets that program and per-scheme float coordinates from node `+0x48/+0xd4` and `paletteheight`, attaches the destination texture to the FBO, submits the shared four-vertex VDO, binds the default FBO, optionally generates destination mipmaps, restores viewport and render states. `RenderVertexData` reaches the existing [conditional GL draw boundary](geometry-and-draw-boundary.md); FBO generation/bind/attachment and mipmap extension targets are mapped in [framebuffer effects](framebuffer-effects.md).

The shared palette texture, quad, FBO and shader have explicit null/zero first-use gates; the per-destination texture setup and offscreen draw require the branch's image/palette conditions. Static code does not establish actual texture counts, cache state, caller thread identity, frequency, driver time or whether an Arelith asset chooses this route. Other image formats and malformed palette data remain separate paths.

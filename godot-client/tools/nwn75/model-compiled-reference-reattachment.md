## Reattachment branch and CPU leaves

The only analyzed symbol matching `Reattach` is `Gob::ReattachReference` `0x140093b50`. Its direct caller list is empty; data references at `0x140d81590`, `0x140d83068` and `0x140d88b50` expose it as a virtual target, but do not identify a live caller or call frequency. When entered, it starts from the Gob's Part root `+0x90`, allocates a 16-entry CPU work stack through `_realloc_base` at `0x140093b9a`, traverses child Part pointers, and checks each virtual `+0x70=AsPartReference` at `0x140093bc9`. It requires Reference node type bits `0x11` at `0x140093bdc..0x140093be5`, nonzero source `+0xe0` at `0x140093bf5`, and an existing referenced Gob at Part `+0x68` at `0x140093c02`. A Reference with `reattachable=0` is skipped by this branch even though its initial referenced Gob can still have been created. Evidence `ev_8ce7b37de71f1d3406e1e0acccb9ce169a9d693f3fb7f4308579dbdeea0cdca2`.

For an admitted Part, the function calls the referenced Gob's virtual `+0x98=AttachToObject`: with a nonnull new owner/name at `0x140093c29`, or with the current owner and Part name at `0x140093c53` when the new owner is null. It then gets the referenced Gob's position through virtual `+0xc0` at `0x140093c61`, subtracts the parent position `+0xa8..+0xb0`, computes a rotation arc from the current facing vector to that displacement at `0x140093d39`, multiplies it by the current quaternion at `0x140093d4c`, and writes the resulting quaternion to owner Gob `+0xb4..+0xc0` at `0x140093d54`. `RotationArc` `0x14022e1c0` calls `Vector::Normalize` twice and a conditional float-square-root helper `0x140c7d6d8`; its finite ordinary arm uses the `SQRT` intrinsic, while exceptional input enters a CRT math-error helper. Quaternion `operator*` `0x14022ab00` performs scalar CPU multiplication. Work-stack shift/growth and free are CRT CPU-memory leaves. These reattachment and pose operations do not issue GL. Later world visibility and Part/Scene draw are separate, already mapped consumers; the static path does not establish that a particular frame executes them. **Ownership and limits.** The decoder owns a CPU MdlNode and creates Parts; `CreateReferenceObjects` owns a separate referenced Gob through PartReference `+0x68`; reattachment mutates Gob attachment and orientation using a temporary CPU work stack. No worker-thread handoff appears in these bodies. Calling-thread identity, live binary/text resource choice, virtual reattachment caller, authored flag/name, failure behavior for malformed or allocation-failed inputs, and frame frequency remain unresolved.

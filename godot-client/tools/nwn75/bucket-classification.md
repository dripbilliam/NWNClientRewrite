# NWN-75: original draw-bucket population

Status: partial original-binary map. The pinned `nwmain.exe` SHA-256 is `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. The primary source here is the stored REA/Ghidra body of `Scene::AddPartsToDrawBuckets` `0x1400c38f0`, evidence `ev_9b2776e75e9df7689deec134df0f62a5416d96a73218bc317ec5a36294648eb3` in `tools/native_parity/visibility/evidence/native-presentation-procedures-v2.json`. These are static branches, not measured per-frame frequencies.

`AddPartsToDrawBuckets` resets `DrawBucketManager` at `Scene+0x208`. It first takes `AurTextureGetOrdering()` and visits a special ordering slot `-1`, then each listed texture-ordering key. The accessor simply returns `_TextureIndices`; pending-texture publication rebuilds it after sorting static `CAurTextureBasic` objects by their parsed `alphamean` float in descending order, as mapped in [texture acquisition](texture-acquisition.md). Within each key it walks `_meshbuckets` before `_fadebuckets`. A null Part or a failed `PartTriMesh::IsPartRenderable` check is skipped, except that `g_nRenderPartBBox` or `g_nRenderPartPivots` admits a Part for debug drawing. For a Part with a vertex primitive at `+0x90`, it copies a newly formed local transform to primitive `+0x18` when the primitive's stored flags/owner do not qualify for the simpler path. These arrays are produced upstream by the BSP/visibility traversal; this function does not itself determine their membership.

`Scene::AddPartsToDrawBuckets` calls `DrawBucketManager::Reset` `0x1400dced0` at `0x1400c3a47`. Reset visits 16 groups of three DrawItem lists (48 total) and clears only their logical counts; it has no child calls and does not free their backing arrays. `DrawBucketManager::AddPartToBucket` `0x1400d75a0` selects one of these lists at index `itemType * 3 + variant`, then tail-jumps to `CExoArrayList<DrawItem>::Add` `0x1400d7520` at `0x1400d75b7`. Add writes the eight-byte item pointer and increments count. It calls CRT `_realloc_base` only when count equals capacity, growing a zero-capacity list to 16 entries or otherwise doubling capacity. Thus an ordinary within-capacity draw-item append is CPU pointer/count work with no allocation or GL call. Evidence: Reset `ev_5635403f921af6d478e8b1a333eb096b7750bcc2d292ecaaa271865eb999fbab`, incoming call `ev_b405bda08bc81db4360d46fef0e180dc0fc85bb11917803a4448cc6325b674c5`, bucket selector `ev_be929629581a2b9e85bcb28b997781374ebd3321a392e13ae1d3b0b4afcd79dc`, list Add `ev_37092f0285950646e25b825c4bde49f73ee3fdefc0e3710e81065ddda576f136`.

## Mesh/fade input producer

The BSP traversal callback `0x1400dc140` supplies two paths. When there is no current scene or its `+0x1e0` flag is zero, it calls `ProcessTriMeshParts` `0x1400dc900` for the node's TriMesh list. With a current scene and that flag nonzero, it instead admits the node's single Part at `+0x90` to `AddPartToMeshBuckets` `0x1400d76e0` after the observed primitive marker update. The callback is evidence `ev_45e32deb3c08e2049d65115dfbffa713fea199a454c49b479334e1e1653ddc01`; the same two calls appear in the stored callback body at `tools/native_parity/visibility/evidence/native-tile-fog-callback-setter-v1.json`.

`ProcessTriMeshParts` has a fade-specific route when `Scene::geomFadeEnabled == 4`, or when it equals `1` and scene `+0x1a0 == 2`. In mode `4`, a Part with `+0xac == 1` goes to `AddPartToFadeBuckets` `0x1400d75d0` even before an outside test; TileData state `+0xc0` may also add the tile to fade-out and scene lists. In mode `1`, that Part uses TileData at `+0xa0`: state `+0xc0`, a camera-plane test, `PartOutside` `0x1400dbfe0`, and tile fade value `+0x70` choose fade versus mesh admission. The route can add TileData uniquely to fade-in/out lists and the scene list at `+0x1a8`. Outside the special tile path, a Part admitted by `PartOutside` goes to `AddPartToMeshBuckets` `0x1400d76e0`. This is input classification before the draw-bucket pass, not another draw. Source: stored original function body `ev_10aa641352c528a4ec8f32ce458acb8c2fb3e139841736fa161b4c64b2bd1d10` in `tools/native_parity/visibility/evidence/native-door-inside-static-registration-v1.json`.

`PartOutside` walks the supplied clipping planes against Part bounds `+0x68/+0x74` through `BoxAbovePlane` `0x14022b350`. The global `DAT_14140afcc` rotates the first plane tested; on the first rejecting plane, it stores that plane index for the next test and returns outside `1`, otherwise returns `0`. This is a CPU visibility test with a previous-rejecting-plane hint, not a GL call. REA `ev_99d7d24d2715788dad7a39e5cd5135e9c21e27a71346b666d5e51e3609bd6c48`.

`AddPartToFadeBuckets` admits only a Part whose TileData `+0x70` fade value is positive. It gets the material texture TID, grows `_fadebuckets` to at least `max(5000, TID+1)` slots, then appends the Part to that TID's fade list. It also appends the Part to `_meshshadowbucket` unless the Part's node at `Part+0x8` has field `+0x224 == 4`. Thus a fading Part can still enter the mesh-shadow source, under a different gate from the regular mesh path. REA `ev_404675e57241d29f832425fdbcc6c5bcdc0b7ede7d1cd28cb0df4fcef186b4df`.

`AddPartToMeshBuckets` first tests Part virtual `+0x98=AsPartDanglyMesh`; the base TriMesh vtable `0x140d88308` points at the null return `0x140061670`, while the DanglyMesh vtable `0x140d88698` points at self-return override `0x14008c3f0`. When a DanglyMesh is returned, the function invokes its virtual `+0xd0=PartDanglyMesh::Animate` `0x14004ef50` with `DeltaT`; original PE pointer bytes at `0x140d88768` establish that target, and REA body `ev_e4b9ecb5125e389bc1c0a1c230dda2953e7315537ee962e02e7dda3fe5b4c6bd` supplies its name and behavior below. It then gets the material texture TID, ensures at least `max(5000, TID+1)` slots, appends the Part to that TID's `_meshbuckets` list, and appends the same Part to `_meshshadowbucket`, growing that array as needed. The function itself has no shadow-enable gate; later use is gated downstream. Source: stored original body `ev_ec8551f3642f9e5fbbbb270937191abd6492e31acb4a055b9f77fdb1a2d16e32` in `tools/native_parity/visibility/evidence/native-presentation-procedures-v2.json`; Part type-test identities are also in `model-instance-branch.md`. Exported `AddPartToCapBuckets` `0x1400d75c0` is a separate direct append to `capbuckets` (`ev_f858f736793abcc74b1586e8f8aff997fab55d1119b45ccf2e4a0087f5f974fd`); no internal caller of that wrapper is established, but the fading handlers below append to the same list directly.

The analyzed `AddPartToCapBuckets` wrapper has no incoming internal code call edge. Its data reference at `0x1410d6688` is exactly the PE **export address table** entry for ordinal `5105`, name `?AddPartToCapBuckets@@YAXPEAVPartTriMesh@@@Z`: the export directory's AddressOfFunctions array begins at `0x1410d16c8`, and index `5104` contains RVA `0x000d75c0`. It is export metadata, not a Scene dispatch table or proof of a call. An external caller remains possible. The normal internal cap-list producers are `HandleFadingInBucket` `0x1400d9670` and `HandleFadingOutBucket` `0x1400d9ab0`, which append directly from two node lists under their fade gates. Their exact stores and the bucket-7 consumer are in [cap-bucket lifecycle](cap-bucket-lifecycle.md). The PE export entry can be reproduced with `inspect-pe-exports.cjs` against the pinned image; prior REA entry `ev_b6ebd8cebb479ea867ec0469885c4fecfc76d48a4c30c839634320d619017e17` identifies its file offset.

The capacity-growth path is concrete. `CExoArrayList<Bucket>::SetSize` `0x1400de510` frees and clears a zero-size array; for a positive size it calls `Allocate` `0x1400d7ae0` and writes the logical count. `Allocate` runs only when requested size exceeds capacity: it allocates a new 16-byte-per-Bucket array, constructs its elements, transfers each old inner Part-pointer list by resizing and copying its pointers, then destroys and frees the old Bucket array. `CExoArrayList<PartTriMesh*>::SetSize` `0x14006dde0` reaches CRT realloc only when the inner list needs more capacity; zero size frees it. Thus texture TID growth can allocate/copy many Bucket records and their inner lists, while ordinary append within capacity does not take this path. `Bucket::Bucket` `0x1400d6c70` only zeroes its two fields; `Bucket::~Bucket` `0x1400d6f70` frees its inner pointer list. The constructor/destructor run through CRT vector iterators, with their addresses passed as callback operands, not direct CALL targets. Evidence: REA `ev_bd2a97b5f77cf748cc349b7a2c6818275297620358115948ad5a0e0437f562e0`, `ev_5bd8232423165226a1111a284ebc4420004cb65b5b8b6a84f15d3436890a4ff4`, `ev_55ba014cbd1c7bcbb25c1beaa0a8d7026b58ba7a3a8daa24fb0ac26550fc6562`, `ev_51ce069f439d4e323c96f566a8eb306ff63c7ac9dbecbaa0ea06e404a646d77d`, `ev_09c521bab9f47ff9b31e17f398ecf433f9924307a71a5c27c95f032367916ca5`.

Both mesh and fade producers call `Material::GetTextureTID` `0x1400834b0` → `AurTextureGetTID` `0x1400e8ba0`. The latter follows texture virtual `+0x10` to the referenced texture, compares it with the null texture singleton, then uses that referenced object's virtual `+0x8` to read its TID at returned data `+0x6c`; null/absent texture yields TID `0`. This is the key that indexes the producer arrays and the later `AurTextureGetOrdering` walk. The constructor-backed virtual targets, exact callsites and base-object caveat are in [texture TID bucket-key continuation](texture-tid-bucket-key-consumer.md). REA `ev_47a294a94751d0f928c53277526b51bfb074ed0749e16fb20d1b36bdf77c2014`, `ev_cdd47dafb6861908c9cf9a448ac5ff9d307f4495c6962016174e14b8dbdaf7b7`.

The DanglyMesh animation call is therefore part of visible mesh-bucket production. Its body first requires a current scene whose virtual `+0x280=Scene::IsAnimating` returns true. It clamps the passed delta to `[0.0125, 0.035]`, obtains the Part world transform through virtual `+0x18=GetWorld`, and requires a valid Dangly vertex primitive/dynamic item. It locks a vertex pool, obtains its dynamic item data, generates the velocity array once when absent, and, for accepted movement, updates per-vertex positions and velocities using authored stiffness/damping and the Scene wind vector. It then unlocks the pool, commits the dynamic item and records prior transform; `Part::Animate` follows in the accepted branch. Large movement or absent/invalid state skips the vertex update. The exact inner [velocity, wind and dynamic-pool continuation](dangly-animation-dynamic-publication.md) is now mapped. This is CPU vertex simulation plus dynamic buffer publication during bucket preparation, not merely a material selection. Evidence: `PartDanglyMesh::Animate` `ev_e4b9ecb5125e389bc1c0a1c230dda2953e7315537ee962e02e7dda3fe5b4c6bd`.

`GenerateVelocityArray` allocates `12 × vertex_count` bytes from model data `+0x284`, constructs/zeros one Vector per vertex, and stores the array at Dangly primitive `+0xa0`. It is called only when that pointer was null in this animation body (REA `ev_93ce29c4ff2f2a215787600c6b544cdfcbf0d2a8d0335fc3d16353824552694b`). `RenderInterface::LockPool` returns a CPU pointer into the selected pool and writes its usage byte; it is not itself a GL map call (REA `ev_9d3dfd5e`). The first `UnlockPool` call from Dangly animation requests a full span with size `0xffffffff`, offset `0`. `VertexDataObject::CommitItemDynamicData` then computes the dynamic item's byte count/offset and calls `UnlockPool` again for that range (REA `ev_fa2f64ab`). `RenderInterface::UnlockPool` `0x1400bf3d0` jumps to `GLRender::UnlockPool` `0x1400bbad0`, which tails to `0x1400bbaf0` with the global pool manager (REA `ev_0110ad9e`, `ev_242ce51b`). That pool implementation may create/bind a GL buffer, allocate/orphan it, or issue `glBufferSubData` according to pool flags and prior state; these are conditional publication paths, not proof that two GL uploads happen for every Dangly Part (REA `ev_e83d601a`).

All five targetless calls in `PartDanglyMesh::Animate` now have pinned virtual targets. The two Tracy-enabled name reads at `0x14004f12e/0x14004f29a` call DanglyMesh `+0x8=Part::Name` `0x140062450` (REA `ev_84e01885`). The main gate at `0x14004f47a` calls Scene `+0x280=Scene::IsAnimating` `0x1400cafe0`; `0x14004f4fa` calls DanglyMesh `+0x18=Part::GetWorld` `0x14008f870`. The primitive call at `0x14004f525` is `VertexPrimitiveDangly+0x20=AsVertexPrimitiveDangly` `0x1400aba10`: its constructor `0x1400aaf80` installs vtable `0x140d8ac58`, whose slot bytes resolve that target (REA constructor `ev_5d5ace76`). The wind service and dynamic pool/commit descendants are named direct calls; the CPU vertex loop and those descendants remain open for deeper traversal.

The static mesh and fade arrays can each add the same Part more than once by the explicit extra submission; a record in one source array does not prove the same Part is in the other array.

After the texture-keyed arrays, admitted `capbuckets` Parts are submitted to bucket `7`. Static shadow Parts use bucket `9` or `10`: `shadowfliporder` chooses the initial side, then eight AABB corners are tested against the camera plane and may choose the opposite side. Mesh shadow Parts use the analogous `11` or `12` selection and clear their primitive `+0x78` marker after submission. Non-null `_staticbeambucket` entries are submitted to `0xf`. These shadow and beam buckets are later consumed by the distinct shadow/beam passes in `shadows-and-dynamic.md`.

The function then sorts `_gobbucket` with comparator address `0x1400c9bd0`; its [original flag and float ordering](gob-sort-branch.md) is now decoded. It asks Scene virtual `+0x2a8` for its shadow Gob, and calls `Gob::ProcessGob` on each entry. Only a Gob with nonzero `+0x1a4` and positive `+0x108` enters the render-Parts branch. It takes adjusted position/orientation/scale, pushes a render matrix, and walks behavior-attachment ancestors, multiplying inherited scale and optionally synchronizing hierarchies. Shadow eligibility checks the Gob/model flags, camera and Scene state, attachment status, and `maxshadowdist`. Eligible Gobs choose dynamic shadow bucket `13` or `14` by a sphere/plane test with `shadowfliporder`; ineligible ones pass `-1`. It then calls `Scene::AddPartsTreeToDrawBuckets` `0x1400c4620` with that shadow choice and pops the matrix. The tree's per-Part classification is a separate descendant mapped in `geometry-and-draw-boundary.md`; this document does not close that path.

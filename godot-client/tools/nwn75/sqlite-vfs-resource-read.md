# NWN-75: original SQLite pager and Win32 read boundary

Pinned original `nwmain.exe` SHA-256: `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. Addresses are PE virtual addresses. This is a bounded static descendant of the [manifest resource lookup](manifest-resource-lookup.md) when its prepared SELECT reaches `sqlite3_step` `0x1405b27b0`, plus the corresponding NWSync database-open ancestor. It identifies the default VFS dispatch and a possible engine-to-OS read route with no-I/O gates. It does **not** establish that a particular manifest query takes the sampled VDBE opcode, misses cache or reads a file on every step. The [companion ledger](sqlite-vfs-resource-read-ledger.json) distinguishes direct sites from computed slots.

## Statement to pager

`sqlite3_step` rejects null/finalized statements with misuse logging. With a valid statement it calls `0x1406319d0` at `0x1405b2851`, and can repeat at `0x1405b28a4` after reset/reprepare on schema change. `0x1406319d0` executes the VDBE body `0x140637d70` at `0x140631acd`. A conditional VDBE branch calls B-tree page routine `0x1405c8d30` at `0x14063c9bd`. That routine validates the requested page number and invokes the pager's stored page-fetch function at slot `+0x110` (first observed site `0x1405c8dae`). The opcode, page number and planner choice for either manifest SELECT remain runtime dependent. `0x1405de3e0` first fetches a page object from its page cache. If the page already has data and the caller did not force a refresh, it returns without reading the VFS. ## Default VFS and Win32 leaf

On successful Win32 VFS open, `0x1405a8a10` stores I/O-method pointer `0x140e07430` in the file object if its VFS override at `+0x20` is null; otherwise it stores the override's first pointer. Pinned table bytes at `0x140e07430` give version 3, close `0x1405a5c60` at `+0x8`, and `xRead=0x1405a5d00` at `+0x10`. A second table at `0x140e074d0` has the same first three fields, but its publication to this file route is not established here. ## Open boundary

The static shard constructor does not request a custom VFS and the built-in default object has no I/O-method override. The remaining VFS frontier is a runtime `file:` URI with `vfs=` after URI mode is enabled, or a prior registration/reordering of the process-wide VFS list through SQLite's exposed registration API; the pinned binary has no direct call into `sqlite3_vfs_register` from application code, but the function is exposed through SQLite's API table and dynamic extension behavior is not disproven. A selected custom VFS object's `xOpen`/`xRead` targets would require runtime object identity or additional producer evidence. The SQLite opcode chosen for each manifest SELECT, page-cache contents, WAL state, mapped-region coverage and runtime errors also remain unproven. Consequently this is a default-path identification, not an asserted per-query I/O cost.

# Original GUI direct-call connector audit

These eight pinned-byte candidates are actual direct calls in the original binary (`3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`). Their site-backed [ledger](gui-disconnected-connectors-ledger.json) joins already mapped descendants; it adds no new active-frame count.

`CGuiPanel::Activate` `0x1401fbe70` calls `CSceneView::CSceneView` `0x1400cb1c0` at `0x1401fc00a` only when panel mode `+0xb0 != 1` and its scene view `+0xb8` is absent; that view is then assigned to `+0xb8`. Later, after a root model is present and scene/panel admission succeeds, the same activation body registers the panel for updates at `0x1401fc180 → CGuiObject::RegisterUpdate 0x1401fb540`. Registration itself checks object flag `0x40` to prevent duplicate list insertion. Both are activation work, not unconditional work every GUI frame. REA `ev_49e23dbea8c4760a97be0996f8dff4366a1cca119e9e820fadee0d9aa0634586`, register body `ev_7a6a19b3c84cd50e79def3015639417016ab68534519e9db6d0639d94f3ff845`.

`CGuiPanel::LoadLayoutFileModelsAndTags` `0x1401feba0` calls `RecursiveLoadLayoutFileModelAndTag` `0x1401ff120` at `0x1401fecdc` in the GFF-loaded branch. If its `CResGFF+0x100` value is zero, the body instead creates `GUI_EMPTY` and skips this recursion. A nonnull recursive root can assign its model to panel `+0x10` and attach the panel. REA `ev_8ac1d4666706e7ee3b4b0a1adfcf2810fa46c2ba06dd4918970c95132ab8fb89`.

`FUN_1406e3370` calls `CAuroraStringWrapper::SetText` `0x1401fb890` at `0x1406e374f` for the area loadscreen tip label at `loadscreen+0x2c8`. The branch requires app state `+0x10 != 1`, app state `+0x14 != 1`, nonnull loadscreen at owner `+0x448`, and app subtype `+0x4` equal to 1 or 3, selecting string IDs `0x102b0` or `0x102bb`. The other callsite `0x1406e3418` belongs to the separate app-state-1 branch. The call changes label content; actual rendering still needs panel/model visibility and the established label/text path. REA `ev_91bcff48541555d2a5da308e4225d8fe0d0ea63119a5dae9698db2b6a4b822f9`.

The `CGuiAreaLoadscreen` factory `FUN_140836f60` constructs the panel and four embedded widgets. After it loads the `LOAD_SCREEN` GFF layout, four unconditional calls within that constructor import widget layout data: `0x140837035` for `LoadBar` at panel `+0x120`, `0x140837057` for `TitleLabel` at `+0x1b0`, `0x14083706d` for `DescLabel` at `+0x248`, and `0x14083708b` for `TipLabel` at `+0x2e8`, all targeting `CGuiObject::ImportLayoutData 0x1401fe0b0`. The routine removes `LoadBar` from the panel after import and ORs flag 4 at `+0x2f0` before the Tip import. Import's own named-tag/data gates determine whether each acquires model and text. REA `ev_7857f863aa2e610142292f805b7df428b8813baa572e579c0aeb61478c0dbbdf`, import `ev_e6e9de01e521e79bc8521ddca974b494f681f27181b8dfffefa55ce7ae41ffcd`.

All calls execute on their current GUI/client caller thread. Nothing in these eight edges itself starts a worker or issues GL. Descendant draw and teardown ownership remains in [legacy panel activation](legacy-panel-activation.md), [loadscreen GUI owner](loadscreen-gui-owner.md), and [legacy GUI draw ownership](legacy-gui-draw-ownership.md). Runtime panel activation, GFF content, and visible model/text output are still data dependent.

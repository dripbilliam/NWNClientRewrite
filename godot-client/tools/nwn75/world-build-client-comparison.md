# Original world flow versus the current Godot client

Source review: 2026-11-12. The [original lifecycle](world-build-frame-lifecycle.md) is for installed `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. Client claims below refer to the current workspace source, not a frozen accepted executable. The [older bounded comparison](../native-render-gap/bounded-original-client-comparison.md) has Tracy timings from a different client source snapshot. This is a structural comparison, not a matched FPS result.

| Stage | Original client | Current Godot client | Consequence or open question |
| --- | --- | --- | --- |
| Area build | Area entry constructs tile records, shared Models, per-tile Parts, static bins, BSP membership and neighbors. | `AreaStream` decodes the definition in `WorkerThreadPool`, requests unique models through `AssetService`, then creates templates and places tile `Node3D`/mesh trees on the main thread under a shared publication budget. | Both retain built tile geometry. Our asset and scene conversion has extra stages, but much of it is off-thread or limited to entry/publication. It can cause hitches; it does not by itself explain a steady FPS gap after loading. |
| Persistent world | `Scene` owns a Gob array, typed BSP node lists, static mesh/fade bins, lights and draw managers. Shared Model data survives individual Gobs. | `LiveWorld` retains desired/installed/instance dictionaries; `AreaStream` retains tile placements and a collision query index; each admitted tile/object is a Godot node tree. `ResourcePool` caches templates, meshes, textures and materials, with bounded **bindings** and live references surviving binding eviction. | Our world is represented in both script state and Godot's scene/rendering state. That is an ownership difference, not proof of duplicate draw work. |
| Visibility and admission | Each BSP Scene render traverses visible nodes, tests bounds, resets 48 logical draw lists, and refills them from persistent static candidates and visible Gobs. | The explicit `NativeSceneVisibility` path handles received reveal/fade state, not camera frustum admission. Godot's renderer owns ordinary geometry culling and pass submission for the resident `MeshInstance3D`/`MultiMeshInstance3D` resources. The separate query index serves physical queries. | There is no one-to-one script equivalent of the native BSP/bucket pass. We cannot rank the two culling/submission schemes without matched visible-instance, draw and CPU/GPU counts. |
| Static draw grouping | Static candidates are keyed by texture for ordered bucket admission; Parts are drawn through typed passes. This does not imply one GL draw for an entire bucket. | Normal terrain uses individual placed model trees: `LiveWorld.open` explicitly sets `terrain.use_terrain_batches=false`. `AreaStream.static_scenery_mode` defaults to `individual`; `batched`/`merged` require flags. Base scenery merging is also opt-in. Godot may apply its own automatic instancing. | Current source does **not** default to the 4×4 terrain `MultiMesh` path described as available in the older comparison. Individual node/submission cost is a concrete candidate, but neither actual draws nor savings from an optional mode have been established here. |
| Frame updates | `Scene::Animate` scans Scene Gobs under a GUI animation gate, with deeper behavior/Part/skin gates. Camera and Scene changes can invalidate BSP membership; static tile trees stay built. | `LiveWorld._process` advances motion, stream/adoption/readiness and applies poses for `motion.objects`, skipping static objects in the regular pose loop and writing transforms only when changed. `ModelRigs._process` walks rig entities, advances selected animated models, attachments and skins. `NativeSceneVisibility.advance` services active fades. | Our script callbacks and Godot renderer both do recurring work, as expected. The rig loop can still visit entries with skin each frame; the native also animates and skins, so a matched object-level census is needed before calling that waste. |
| Resources and state | Texture publication is pending gated; static Model/Part data persists; GL state and shader uniforms have dirty/cache checks. | Shared `ResourcePool` resources and template reuse persist; tile `AreaStream._process` returns after completion except pending static-group publication. Godot owns material state and GPU uploads. | No evidence that either client rebuilds all loaded geometry every frame. Cache eviction and first-use upload can cause later repeated preparation, but require an identity and timing census. |

## Measurements and interpretation

The older frozen Arelith Tracy capture reported, in its 100–110 s window, a **18.69 ms** mean frame interval, **3.20 ms** `LiveWorld` CPU zone, **1.29 ms** rig callbacks, and **5.30 ms** render-thread CPU zone; the latter overlaps main-thread time and contains the viewport pass. It did not measure GPU execution or the original client's CPU/GPU costs. Its source differs from this workspace, including pose and template paths. [Trace comparison](../native-render-gap/bounded-original-client-comparison.md).

The current evidence supports two focused hypotheses: cost of many resident individual Godot mesh/scene instances during draw admission, and recurring script actor/rig work on the main thread. It does **not** prove either causes the reported native/client FPS ratio. The next discriminating capture should record, in the same view and frame interval, visible geometry instances, actual draws/material changes, world/rig callback times, render-thread and GPU times, and loading/publication activity. In the native client, count per-view BSP candidates, visible Parts/Gobs, bucket entries and actual GL draws if instrumentation becomes available. This separates scene construction hitches from sustained frame cost and avoids treating a viewport slot as another world redraw.

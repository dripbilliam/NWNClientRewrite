## Scene-owned input and lifetime

`Scene::AddLinesToRender` `0x1400c3410` is Scene vtable `0x140d8dd30+0x138` (`0x140d8de68`). It receives three by-value parallel lists: `Vector` positions, unsigned colors and integer endpoint indices. It averages input positions. If Scene BSP `+0x188` exists, it calls `SceneBSPGetTileData` `0x1400dd7b0` at `0x1400c34f5` for that center and adds the selected TileData `+0x50` height to each input position's Z. The body assumes a valid TileData pointer on this admitted BSP path. It deep-copies the adjusted positions into the next outer list at Scene `+0xc0`, colors into `+0xd0`, and indices into `+0xe0`. Each outer list has a pointer, count and capacity; it grows only when full, starting at 16. The three outer counts at `+0xc8/+0xd8/+0xe8` advance together. It frees the input by-value list buffers after copying; the Scene owns its copies. `Scene::ClearLinesToRender` `0x1400c5a70` is Scene vtable `+0x140` (`0x140d8de70`). It sets the three outer counts to zero without freeing their retained storage. `Scene::~Scene` `0x1400c1c20` destroys all three nested lists and their backing arrays. Neither Add nor Clear has an analyzed direct code caller: Ghidra incoming references are the vtable entries and metadata/data pointers. A caller through the virtual Scene interface, an external module, or a different computed path remains possible. Therefore the runtime producer, how often Clear is invoked and whether groups persist across frames remain open. The draw body itself does not clear the lists. ## Frame consumer

`Scene::RenderSinglePass` calls `Scene::RenderLines` `0x1400cf4c0` in its final phase. The method returns immediately when Scene `+0xc8` is zero. For positive group count it stages line render state, then first traverses each group's index list at Scene `+0xe0`, counting **two vertices for each nonnegative endpoint index**; negative indices are skipped. An unrolled eight-index loop is only a counting optimization, with a scalar remainder. It lazily requests/grows a shared stream token `0x14140af60` for `(capacity,0,5)` when missing or when capacity `0x14128ed1c` is smaller than that vertex count. On a cache hit, it reuses the stream. In a second traversal, each nonnegative index produces a line from the corresponding list position to the referenced endpoint: both positions come from that group's `Vector` list at Scene `+0xc0`, and both colors from its parallel color list at `+0xd0`. It writes two 16-byte color/XYZ vertices per admitted index in group order. Evidence: `ev_7d22fc87f3e7e485494a347fbd6e6b4465aea076f35f2c5b3283bcf5f1ebe519`.

The method commits the counted vertices through `VertexStreamDataObject::CommitVertexData` `0x1400bd5d0` at `0x1400cf8a0`, then calls `RenderInterface::RenderVertexStreamData` `0x1400beed0` at `0x1400cf8b6` with primitive `1` and that count. The shared stream renderer reaches imported `glDrawArrays` for this unindexed stream. The wrappers restore selected state afterward. With positive group count but no nonnegative index, there is no second-loop geometry; `UnlockPool` skips zero-byte GPU publication, but nonnull stream state can still reach a zero-count GL draw as in the [highlight](scene-highlight-texture-and-stream.md) and [drawable-square](scene-drawable-square-lifecycle.md) branches. The outer zero-group gate avoids all of this work.

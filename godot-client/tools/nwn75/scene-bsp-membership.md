# NWN-75: original scene BSP membership branch

Pinned original `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This records static original-binary control and data paths; it does not establish how often a particular authored Part type occurs. The complete render tree remains open.

`SceneBSPAddPart` `0x1400dcfd0` is reached from recursive `Scene::ListSpecialPartsR` `0x1400cb010` at `0x1400cb04b/0x1400cb070` for Light/Emitter Parts, from `BSPCreateStaticProjections` `0x1400d7f00` at `0x1400d831e`, and from `AurPartTriggerCreate` `0x1400ef450` at `0x1400ef927`. It returns without insertion when Scene+0x188 has no BSP. Otherwise it classifies the input by Part virtual slots, in order, and places it in the fitted node's payload at `BSPNode+0x70`:

`PartShadow::AsPartShadow` `0x1400d7c80`, selected by the Shadow subtype at virtual `+0x80`, is a four-byte `MOV RAX,RCX; RET` leaf that returns the Shadow Part itself. It is a positive subtype gate, with no child call or GL operation in the leaf. REA `ev_d9146924832824cca9f718260d40870fce26795502848961489372afd61a2377`.

If a nonnull Model is supplied, the final branch also calls `Model::AddRef`; the recursive Light/Emitter caller supplies null. The producer/consumer wind route is in [animation and emitter](animation-and-emitter.md). `SceneBSPRemovePart` `0x1400dd950` is called by recursive `Scene::UnlistSpecialParts` `0x1400d4e80` for Light/Emitter Parts. Under a present BSP it tests Part `+0x48`, `+0x68`, `+0x78` with shadow/beam subtype, `+0x90`, `+0x58`, then `+0xa8`, and uses `BSPSearch` plus matching typed-array removal or clears the single AABB entry. The Light branch additionally calls `LightManager+0x28=RemoveLight` `0x1400802d0`; that method removes the light from all its classification/effect arrays. The shown removal body does not itself call WindManager unregister; that later destructor route is below. Evidence: REA `ev_76d87e90`, LightManager `ev_77648ee4`, original LightManager vtable `0x140d85f70` slots `ev_bba6a2f6`/`ev_cde99f98`.

These helpers prepare scene/BSP lists consumed by later culling, lighting and the [bucket collection and draw route](geometry-and-draw-boundary.md). The polymorphic Part type gates and later resource cleanup remain open in the branch ledger; this document does not treat membership as an external API boundary.

The placement/search internals are now bounded at the immediate helper level. `BSPFitSphere` `0x140229690` iteratively evaluates the input center against each node plane; it stays at a straddling node when the signed distance lies within the radius, otherwise follows child `+0x10` or `+0x18` until a leaf marker. Its complete original body has no child calls or GL work (`ev_9a61b070145122da5000cea8a2fc46ea178a79e4fe5c7b846c663a757f71bff1`). `BSPFitBox` `0x1402295a0` recursively tests the box against the plane and negated plane through `BoxAbovePlane` `0x14022b350`, with the observed `-0.02` tolerance, returning the first node that cannot be placed wholly on one side. `BoxAbovePlane` picks an AABB extreme by each plane-normal sign and computes a dot product plus offset; it has no callees. `BSPSearch` `0x140229980` first invokes its supplied membership predicate, then visits near and far children by the point's plane sign until a predicate accepts a node or both descendants fail. These are CPU tree walks without direct GL calls. Evidence: REA `ev_e2ba6c92`, `ev_70c16209`, `ev_2eb20255`, `ev_0451769a`.

The callback addresses supplied by the removal callers are decoded instructions even where Ghidra did not define separate functions. Each rejects a null BSP node and then tests membership in the node payload: AABB `0x1400dbc80` compares the single `+0x90` pointer; emitter `0x1400dbca0` tails to emitter-array `Contains` `0x1400c69d0` at payload+0x30; Gob `0x1400dbcc0` tails to Gob-array `Contains` `0x14008cff0` at +0x10; light `0x1400dbce0` tails to light-array `Contains` `0x14007dd30` at +0x0; generic Part `0x1400dbd00` tails to `Contains` `0x1400d8e00` at +0x60; projection `0x1400dbd20` checks shadow/beam arrays at +0x40/+0x50; TriMesh `0x1400dbd80` tails to `Contains` `0x1400aba40` at +0x20; trigger `0x1400dbda0` tails to `Contains` `0x1400d8f80` at +0x70. The callback target is passed as an address to `BSPSearch`; none invokes GL. Evidence: REA instruction reads `ev_2198c53d`, `ev_f3f5f74a`, `ev_f1476a9f`, `ev_dbb1a310`, `ev_b8e7c171`, `ev_32ce8304`, `ev_9777cc02`, `ev_ef2c5d57`, `ev_7f33e022`, `ev_431aa896`, `ev_08533301`, `ev_e50f5555`, `ev_15a0417e`; projection body `ev_c9b21aee`.

Wind-affected emitter deregistration is a later lifetime route, not an explicit call in `SceneBSPRemovePart`. `PartEmitter::~PartEmitter` `0x1400608e0` calls `WindManager::DeregisterWindyEmitter` `0x1400f1450` at `0x140060ad2` when emitter+0x1f8 points to a WindManager. Deregistration finds the emitter in WindManager+0x860, removes it from the growable array, and shifts later entries; the destructor also clears its Scene-linked index at emitter+0x200 and destroys active/reusable particles. With an owner it calls `Scene::RemoveFromSceneManager` `0x1400cc4d0`, which tests Part+0x68/0xa8 and removes an emitter from the global emitter bucket or a trigger from the global trigger bucket. The exact ordering between scene removal and emitter destruction depends on callers and remains open. Evidence: REA `ev_566f6161`, `ev_685f8a55`, `ev_76f1fd9c`, `ev_068b81da`.

The moving-frame placement route is `ManageSceneBSP` `0x1400db320` → `SceneBSPUpdatePart` `0x1400dde10` at `0x1400db78e/0x1400db864`. Under a nonnull Scene BSP it classifies the Part in the same priority order as AddPart. For Light, AABB, TriMesh, projection shadow/beam, emitter, trigger and generic Part it computes the new fitting node; if that node already contains the same Part it leaves the list unchanged. Otherwise it uses `BSPSearch` with the typed membership predicate above, removes a found old entry, and adds to the new node's typed list. AABB uses its single payload+0x90 slot. The `Model*` parameter is present but is not used by the decompiled update body. This is CPU list maintenance before visibility and bucket collection; no GL call appears. `SceneBSPUpdateGob` `0x1400ddd60` uses the same fit/Contains/search/remove/add pattern on the Gob list at payload+0x10, with the Gob's prior position used for the old-node search. REA has no direct incoming call edge for UpdateGob, so its callsite/reachability remains open. Evidence: REA `ev_ffc91938`, `ev_a8f60cf5`, `ev_77013778`, incoming `ev_6f043bca`.

The moving-frame `SceneBSPUpdatePart` body now has a full immediate direct-call census in `branch-ledger.json`, including typed `Contains`, `Remove` and `Add` sites for seven Part families.

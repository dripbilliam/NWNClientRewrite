## Part survival through tile preparation

`MdlNodeDanglyMeshCreateInstance` `0x140092760`, reached through model-node `+0x28` on `CreateInstanceTreeR` traversal, allocates a `0xe0` PartTriMesh-derived object, installs `PartDanglyMesh::vftable` `0x140d88698`, initializes dynamic fields and copies model node `+0x224` to Part `+0xac`. `PartInitMaterial` selects `VertexPrimitiveDangly` through its positive `AsPartDanglyMesh` test. The authored subtype, instance slot and material setup are mapped in [Dangly payload](model-dangly-payload.md). This connector concerns a Dangly Part that is actually present in a tile model; authored tile usage and live subtype mix are unmeasured.

`Scene::SpawnTile` `0x1400d41a0` creates the instance tree or a named `a` Gob, calls `CollapsePartTree` at `0x1400d4457`, and calls `ProcessStaticParts` at `0x1400d451c` on the collapsed list. For a Dangly Part, virtual `+0x58=AsPartTriMesh` returns self (table slot `0x140d886f0`). `ProcessStaticParts` moves model class `+0x224==2` to TileData `+0x90`, class `4` to `+0xb0`, and removes either from the residual list. Other classes remain only if face count `+0xb8` and vertex count `+0x284` are positive; an empty Part is destroyed. These conditions are the first static-tile admission gate. Evidence: `ev_0cdf2929555a1f88661105867841e26d91aadf548ff94fea7b7b57e660b9f172`, `ev_37fb30c927647447004135ecdb127d880eb9d31c04a25f9f871c9c9dc4792731`, subtype slot bytes `ev_35bda94e53ee6ec4f78b852b743fc8282723354b7e25c4c0e2f77a11ba62c65a`.

`SpawnTile` may call `CombineParts` `0x1400c5f30` before BSP insertion when the residual list has an eligible Model not previously combined. Its `CreatePartBuckets` `0x1400c6a50` tests Part `+0x58=AsPartTriMesh`, `+0x98=AsPartDanglyMesh` at `0x1400c6ba0`, and `+0x90=AsPartAABB`. A positive Dangly result branches at `0x1400c6bf9/0x1400c6bfc` to the separate output-list append at `0x1400c7096..0x1400c70ef`, instead of the merge-group path. `CombineParts` copies that list back to the residual Part list and only merges eligible groups afterward. Thus this optional combine does **not** change the identity of a surviving Dangly Part. This does not prove every authored Dangly survived the earlier static filter. Evidence: `ev_84e7dac8ae31a0f3d1459a879aa6a1c4ee23e4677bbab380ceb83744f392c74b`, branch bytes `ev_327f457a42605c4e76075db5a880004229ad2f6bbaa27da3ef27fd51260087ca`, `ev_1cd6af717371187c1d2a2331e0344ebf89df57b1958b922576eb8e5d20047929`.

## BSP, visibility, animation and draw

`SpawnTile` passes the surviving residual list to `SceneBSPAddTileData` `0x1400dd340` at `0x1400d474b`. With Scene BSP present, that helper tests Light, AABB and then TriMesh virtual subtypes. For Dangly table `+0x90=AsPartAABB` points to null-returning `Part::AsPartAABB` `0x140061630`, while `+0x58=AsPartTriMesh` points to self-returning `0x14008c4e0`. The positive TriMesh branch calls `BSPFitBox` at `0x1400dd4a0` and appends the Part to fitted node payload TriMesh list `+0x20/+0x28` at `0x1400dd4b0`. The helper increments a nonnull owner Model reference for each listed Part. The Scene stores the TileData separately at the tile-position node payload `+0x98`. Evidence: `ev_4ab185511a1832552f2aab60acf7a36d2dfd7188a71056b6fc7eb5b2967e83c2`, table bytes `ev_dc2d85b25186767258e74a2d0f482e1d88ff5759630b9c2a7a40545a656cb246`, `ev_35bda94e53ee6ec4f78b852b743fc8282723354b7e25c4c0e2f77a11ba62c65a`.

On visible BSP traversal, callback `FUN_1400dc140` calls `ProcessTriMeshParts` `0x1400dc900` at `0x1400dc4c3` when the Scene AABB debug flag `+0x1e0` is absent. The function walks the node's TriMesh list, performs `PartOutside` camera-plane culling and, depending on geometry fade state, may send a Part to `AddPartToFadeBuckets` at `0x1400dc9f5/0x1400dcb37` or to `AddPartToMeshBuckets` at `0x1400dcb67/0x1400dcbea`. The fade branch does not call Dangly animation in that helper; the mesh branch does. With `+0x1e0` enabled, this callback instead processes the single AABB payload and skips `ProcessTriMeshParts` on that node. Evidence: `ev_901383e0bdf24fe1d003abad9331df48ef421084ca94a06c5f73821df1e1e22b`, `ev_6ffd0bdf31263657054952aa640abb39bebbc157b8cb13a8129003b9d65c7664`, direct sites `ev_7173493dd60a31bca79d84623ba1d3662d9f37133d71c072d3dbbaa149dccb7d`.

`AddPartToMeshBuckets` `0x1400d76e0` calls Part virtual `+0x98=AsPartDanglyMesh` at `0x1400d76f0`. For table `0x140d88698`, the slot at `0x140d88730` returns self (`0x14008c3f0`); the positive branch calls `+0xd0=PartDanglyMesh::Animate` `0x14004ef50` at `0x1400d7709` with `DeltaT` **before** `Material::GetTextureTID` and the `_meshbuckets` append. `Animate` itself requires an animating current Scene and valid dynamic primitive, then conditionally updates vertices and commits dynamic pool data. The mesh-bucket append occurs whether or not that inner update produces vertex changes. A later `Scene::AddPartsToDrawBuckets` renderability/material gate may create a DrawItem; `Scene::RenderDrawBucket` Part `+0xc8` at `0x1400cd8d1` resolves from the Dangly table to `PartDanglyMesh::Draw` `0x1400a22d0`, with its own active/source-mesh conditions before the shared GL leaf. These are static conditional edges, not a measured per-frame frequency or a claim that one Dangly Part animates twice. Evidence: bucket `ev_ec8551f3642f9e5fbbbb270937191abd6492e31acb4a055b9f77fdb1a2d16e32`, vtable slots `ev_5ff792bfb8909b877c22bdb66965c68e12e9a4980bc077dbff1c2f62cb286b72`, `ev_b2fdb37c99b2147771180e2bdffcbc95a5a81184dfa3653c60af1fc2a82096f1`, `ev_f02ac16bda5529b3810a85428b838eb8ec4a54419532a4ef4a656b95f47e8f98`.

`Scene::DeleteTile` calls `SceneBSPRemoveTiledata` `0x1400ddc50`; that helper removes each residual Part through `SceneBSPRemovePart`, decrements Model refs, destroys Parts and clears TileData. The Dangly subtype enters the TriMesh removal branch (its `AsPartAABB` is null), removing its pointer from the fitted BSP TriMesh list. Dynamic pool/primitive cleanup is mapped in the existing non-emitter animation and Part lifetime notes. The exact lifetime of a Part diverted to the class-2 or class-4 TileData lists is outside this connector.

# Original mesh primitive and VDO preparation

Pinned original `nwmain.exe` SHA-256: `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This follows the ordinary TriMesh, AnimMesh and DanglyMesh `Draw` calls into shared primitive setup, then the VDO state selection immediately before a GL draw. These bodies contain preparation branches, so their existence does not imply they rebuild on every frame.

`VertexPrimitiveFlat::SetupArrays` `0x1400abca0` returns immediately when primitive flag `+0x64` is set, VDO pointer `+0x58` exists, and dirty flag `+0x84` is clear. Otherwise it classifies the Flat/Anim/Dangly/Skin primitive subtype, gets its TriMesh Part and model node, removes any existing VDO item, and calls shared `SetupProjectionArrays` through virtual `+0x38`. It then sums authored mesh counts/indices and, for nonzero geometry, computes attribute masks, gets a type-1 VDO by attributes at `0x1400ac0a6`, adds an item, obtains element/static/dynamic item storage, locks required source pools, and copies/transforms attributes and indices. `MdlNodeTriMesh::CalculateTangentSpaceBasis` is called within the rebuild mesh loop at `0x1400abd97`. The result commits element data at `0x1400acbe6` and conditional static/dynamic data at `0x1400acbff/0x1400acc1b`; those commits join the existing conditional buffer upload path. Success and empty-geometry exits set `+0x64=1` and `+0x84=0`. The body has 54 direct and six computed callsites; subtype candidates expand the computed sites into nine site-backed ledger edges. The type-1 VDO manager `0x1400bd8b0` scans its object list for a matching type and static/dynamic attribute masks. It asks `RenderInterface` for maximum vertex and index counts to reject a candidate that would overflow, reuses a compatible token, or allocates and `Build`s a new VDO at `0x1400bda42`, reusing a vacant list slot or growing the list. The maximum-count interface wrappers `0x1400bedc0/0x1400bedb0` forward to GL methods `0x1400b3e40/0x1400b3e10`; each uses imported `glGetIntegerv` only while its cached value is `-1`, at `0x1400b3e5b/0x1400b3e2b`. `VertexDataObject::Build` `0x1400bd0c0` calculates static/dynamic vertex strides from attribute masks. For type 1 it creates an element pool; type 2 uses a shared stream element pool created only on first use. Nonzero static/dynamic strides create corresponding vertex pools. Each new pool is requested, locked, and unlocked through RenderInterface, so publication is conditional on pool creation and the shared GL pool implementation. `VertexDataObject::AddItem` `0x1400bce50` can `Repack` when dead space crosses its threshold, doubles inadequate element or vertex capacity, resizes and unlocks affected pools, then appends item offset/count records. `Repack` `0x1400be180` locks present element/static/dynamic pools, moves live item data, and unlocks them; its CPU copy helper `0x140c417f0` remains a separately identified CRT/runtime subtree. `GLRender::SetVertexDataObject` `0x1400ba770` returns when the requested VDO is already selected. For a null VDO it binds the default VAO. For an existing VDO VAO it binds that VAO and conditionally changes the element buffer. For a VDO without a VAO it calls `glGenVertexArrays`, stores the new handle, binds it, binds the element buffer, and visits two static/dynamic attribute masks. A present attribute calls `glVertexAttribPointer` using the packed layout offsets; afterward `SetClientStates` configures enabled attributes. Five direct `GLRender::BindBuffer` sites and one `SetClientStates` site, plus four VAO and fourteen vertex pointer extension calls, are now exact site-backed ledger edges. `GLRender::SetClientStates` `0x1400b6a40` walks fourteen attribute slots for a new VAO, calling loader-resolved `glEnableVertexAttribArray` for selected mask bits or `glDisableVertexAttribArray` for unselected bits. It is invoked after first-use VAO configuration, not on the early already-selected VDO return.

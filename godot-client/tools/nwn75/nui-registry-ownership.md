# NWN-75 original Nui registry and content ownership

Scope: installed `nwmain.exe`, SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. Addresses are original image VAs. This records static original-binary and retained REA evidence only; no live registry population, frequency, or client comparison is inferred.

## Identifier registry and lifetime

`Nui::Window::RenderAll` `0x1406c4b20` reads the `unordered_map<string, weak_ptr<Nui::Window>>` registry's head/list pointer at `0x141422c08` and its hash bucket state at `0x141422c48`, `0x141422c58`, and `0x141422c70`. These are offsets in the same global container rooted at `0x141422c00`: original RIP-relative instructions at `0x1406c4eba` read the head, `0x1406c4c83` reads bucket state, and `0x1406c4d27`/`0x1406c4d32` read mask/vector state. The global constructor around `0x14001a160` initializes the head and the bucket portion. This identifies the static registry object, not a list of active instances. `RenderAll` traverses it under its UI-enable gate, removes closed/dying entries, initializes a surviving active window once through virtual `+0x40` at `0x1406c511a`, and calls update/render/open handling under their respective gates. REA `ev_74d8d73453f582b8c256a0045e8858e65c2aa3a509fd2f4eefec94eae3f35817`, `ev_fdd4a2429d1f0bc34d80bd3dadc79ae2cbe7531002b9758ca8a00086277d1cbe`, `ev_75101c46db8fe527f673a2bc4ee7f55f305ad291320da94ce352c6dd2c02fb47`.

The pinned base `Nui::Window` constructor body is at `0x1406c0d80` (`.pdata` through `0x1406c12ff`): its instruction at `0x1406c0dc9` loads vtable `0x140e2cfa0`, and it touches the separate global at `0x141422b90` while establishing window state. Fifteen direct E8 caller sites in the pinned PE include constructors later installing derived Nui vtables. The constructor does not itself directly reference the identifier registry addresses above. This constrains registration to subsequent owner/factory paths rather than proving every constructed object is inserted.

The base destructor at `0x1406c1a10` (`.pdata` through `0x1406c1e6a`) reloads the base vtable and directly references the registry root/head. The pinned `.rdata` source strings reached by its instructions include `~Window` and `s_by_identifier.find(m_identifier) != s_by_identifier.end()`; its body finds/erases the matching registry entry and releases content. Numerous derived destructor thunks call this body, including the known `JsonWindow` destructor. The retained original `RenderAll` indirect-callsite audit separately marks `0x1406c4cdf` as a stale-entry callback through virtual `+0x10` on an object at entry `+0x78`, before registry removal; 13 other targetless calls in the loop are atomic-refcount-gated destruction/deallocation, and `0x1406c511a` is initialization. These are lifetime work, not command producers. The concrete callback class at `0x1406c4cdf` and per-entry refcount ownership still require closure. REA destructor `ev_0b6a392fa57a2e828e4e54f6916ba8cf95c5538c10cf74010c67ef55003aa6a8`, derived destructor/vtable `ev_cbe2368ed4b55140b6354aeb3d55d1aabcb330ee7df05d6a2f163025ac997f33`; per-callsite classifications are in `nui-renderall-indirect-callsites.json`.

The generic map `operator[]` at `0x140700210` (`.pdata` through `0x1407002d8`) receives the registry root and an identifier key. It compares the lookup result with the head/sentinel and, on a missing key, allocates/inserts a node through `0x1406fd8d0`/`0x1406fe2a0` before returning the mapped `weak_ptr` pair at node `+0x30`. An operator call alone does not prove the key was absent or that a live window was newly published. REA `ev_57a11fd49fba11ec1e5f675266882f6e0222329532ae123ed409159c5c1cc178`.

The JSON-specific path `0x140768070`, reached from `enable_make<Nui::JSON::JsonWindow>` constructor `0x1407a5f20`, probes the same map by identifier. On a missing key, `0x1407682d0` allocates a node with the string key and zeroed weak-pointer fields at node `+0x30`/`+0x38`; the caller increments count at `0x141422c10` at `0x14076813b` and calls `0x1406fe2a0` at `0x140768163` to hash/link/rebucket the node. The latter uses an FNV hash, checks duplicate keys and handles rehash. The JSON path then attempts to lock/cast any existing nonempty weak pointer to `JsonWindow`. **This method alone inserts an empty map entry**; the same enclosing `enable_make` body later publishes its constructed window through `operator[]` at `0x1407a668c` and stores the weak-pointer pair. The only explicit count increment/decrement references found in the REA xref census are `0x14076813b` and base destructor `0x1406c1ba6`; other accesses through register-passed map pointers may exist. REA JSON path `ev_4e8930b3a7ee78b5b3bed8b948d92233da8d580a791c2932d565a2c126917bf0`, node constructor `ev_29c4c316daac480141404bd370e167cfe07d5e1aa864cb8de3540e1feafc395f`, placement helper `ev_26db66d14a25f05279fd396afd8024024cd898912f2708f91f4c4f8818234267`, count xrefs `ev_e07ff0b87609c7801d47e29ceb951827098d0dfa431e1f6f1093ae4e9b8df730`.

A direct-call census of pinned `.text` found **31** E8 callsites to `0x140700210`. Every one is followed by a conditional increment of the new weak control block and stores of both object and control pointers into the returned mapped pair, then release of the prior control block. The full 31-row [operator callsite ledger](nui-registry-operator-calls.json) records each exact callsite, containing `.pdata` function, 96 original post-call bytes, and any window vtable referenced in that body. All 31 are **live weak-pointer publication paths when their constructed owner is non-null**; none of these direct callsites is lookup-only or has an unresolved post-call store pattern. This is a static direct-call census, not a frame's registry population, and indirect calls remain outside its scope. One independently decompiled example is `0x140700620`: it constructs a `Nui::Debug::Selector` in a shared owner, takes the identifier at object `+0xd0`, calls `operator[]` at `0x140700711`, and writes object/control pointers to the returned weak pair while incrementing its weak count (REA `ev_0236c73b57962b87a5ddc9b92ddd62a2ae55f6fc0e94f57a76aa4cd082f9332b`). The co-located vtable entries in the ledger are type clues, not full pointer-flow proofs for the other thirty publisher bodies.

The separate `0x140830810` route is a registry lookup/update by identifier, not a proved insertion. It is called by several programmatic Nui window factories, including the QueryDialog path; its presence in a constructor does not itself establish a new map node. REA `ev_cf677c9562fe3c16a555463a3b615a7e4cbcc178d11bc3bf74209a8512ce5bf0`.

At outer-loop shutdown, `SDL_main` calls `0x1406c39f0`, which walks still-live registered windows and copies geometry/state through `0x1406c7900`, then persists selected properties through `0x1406c3bc0` and `CExoConfig::Commit`. This is a persistence walk after the update loop, not evidence that these windows were all active in a measured frame. REA `ev_833c7aa9adb229ef33dd413c495d7c0f61fbec645c741d6268e78b62f252dd65`, `ev_ae131fdfc271674c158e7c586d9d1b7268a0f8f6b1dc50c4b6f24900c0d804fa`, `ev_589a2751dca14233602482aff9dc3e3a12d7d677926132ea65c84be6351d0a03`.

## Known class to content bridge

For classes with a base render route, `Nui::Window::Render` `0x1406c44e0` reads a non-null content pointer at window `+0x108` and calls its virtual `+0x20` at `0x1406c4a88` (REA `ev_daabb01e3b637193b6eafc330825d4cbb65b3affd3c3ac9e9de6028146e8097b`). The shared installer `0x14074c0b0` accepts a layout object: it preserves an already-`LayoutGroup` object at `+0x108` with owner `+0x110`, or wraps a non-group child in `SingleGroup` through `0x14094b830`/`0x140952a10`. The verified `LayoutGroup` and `SingleGroup` vtables both resolve content `+0x20` to `0x140950d90`; other group subclasses may override it. Thus a call to the installer proves a content-owner bridge, while the exact virtual target is conditional on the supplied concrete layout type. REA `ev_2f28694d29789d72db7d1c593570250dcb5a3d78b7908452ea8256ebe0f4801a`, `ev_f54583d451dab0323abec3d97c94dd3f5f6c361c82ab8ba41b74b4b6b2fc5eb1`, `ev_2842970a03db56d8e33e907d5f5555f03e356543f5d28b25402b343da74da4ab`.

## Remaining exact edges

1. Prove the dynamic window type and strong owner lifetime for the other thirty direct `operator[]` publication bodies beyond the decompiled `Debug::Selector` example. The 31 post-call byte patterns are classified, but co-located vtable references do not by themselves prove the published pointer's dynamic type. Audit indirect/unknown publishers separately if evidence reveals them.
2. Finish the `0x1406c1a10` removal helper sequence and `RenderAll` stale-entry callback `0x1406c4cdf`, including destruction targets and iterator validity. The static destructor marker and indirect-call audit establish lifecycle branches but not every concrete object type.
3. For each content-installer caller, trace the object passed into `0x14074c0b0` to its concrete layout vtable. The bridge proves a `SingleGroup` target for the non-group branch; other accepted group subclasses and child callbacks require a fuller census.
4. Establish which registered windows are active/visible in a specific runtime scene and their owning OS thread only with runtime evidence. Constructor and vtable references alone cannot establish this.

# Text AnimMesh sample arrays to dynamic vertex item

Pinned original `nwmain.exe` SHA-256: `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. The [ledger](model-text-animmesh-sample-publication-ledger.json) follows text `animverts` and `animtverts` from [AnimMesh fields](model-text-skin-animmesh.md) through `MdlNodeAnimMesh::InternalPostProcess` `0x1400a9220` (REA `ev_1811cf3eb9dc1ad020c421f383a9e4b7744b28989650347e60fb64e46775bc3a`) and the already identified runtime `InternalControl` `0x140051e60` (REA `ev_bcf2badaad40f0de3fa7eba98f6d6bf594b1ccff7c76c742579b4b34bd60b07a`). Both are CPU-side paths until the conditional VDO commit enters shared pool publication. Their caller context and active counts remain dynamic.

The postprocess rebuilds only when node vertex count `+0x284` starts at zero. It calls shared `ProcessVerts` and derives position sample count from authored `+0x2d8` divided by base postprocess vertex count; it allocates a sampled-normal Vector array at `+0x2f0/+0x2f8`. For each sample and source face/corner, it scans faces for matching vertex and smoothing-group membership, accumulates cross-product normals from sampled positions at `+0x2d0`, normalizes them and stores them in that array. It then extends node bounds over all sampled positions. Division by zero and malformed array lengths are not resolved by this normal path.

After its [sample-sensitive vertex deduplication](model-text-animmesh-vertex-dedup.md), neighbor/index builders and the [shared base vertex streams](model-text-trimesh-vertex-streams.md), positive generated position sample count `+0x310` allocates node `+0x300` for `3 × sample_count × generated_vertex_count` floats. Positive UV sample count `+0x314` allocates node `+0x308` for `2 × sample_count × generated_vertex_count` floats. For each generated `NodeVertexAnim`, five static `AsNodeVertexAnim` calls at `0x1400a9745/0x1400a975f/0x1400a977b/0x1400a97c3/0x1400a97df` read its sampled position list `+0x70` and sampled UV list `+0x80` into those two contiguous arrays. Tangent calculation and temporary generated-vertex cleanup follow. These two persistent arrays are ordinary CPU allocations in this function; it does not request an extra sample pool here. The compiled AnimMesh variant copies equivalent arrays from serialized offsets, as recorded in [binary subtype payload](model-binary-skin-animmesh-payload.md).

At animation control, a nonpositive blend weight returns early. Otherwise `InternalControl` divides animation time by sample period `+0x2c8` and clamps or interpolates neighboring sample indices. With a valid AnimMesh primitive and VDO dynamic item, `GetItemDynamicData` `0x1400bd7a0` at `0x140051f32` locks the item. The control loop reads node `+0x300/+0x308` and, for each generated vertex, blends position and UV values into the dynamic item with the supplied weight when a value differs. Only a changed item calls `CommitItemDynamicData` `0x1400bd540` at `0x14005233d`; that tail-jumps to `RenderInterface::UnlockPool` for the conditional GL buffer path. The Part subtype check and base node controller follow. The sampled-normal array `+0x2f0` is constructed here, but this specific control body does not read it; any other consumer needs separate evidence.

The site-backed path distinguishes model-construction sample copying from per-control-time dynamic writes. It does not establish that a particular animation, mesh, VDO item or GL upload is active in a frame, nor does it establish a worker handoff or OS-thread identity.

# NWN-75 original Nuklear resource lifecycle continuation

Scope: installed `nwmain.exe`, SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. Addresses are image VAs. This extends [Nuklear resource lifecycle](nuklear-resource-lifecycle.md) with exact handle references and the context/shutdown boundary. It is static original-binary evidence, not runtime frequency.

## Single UI device setup and shutdown chain

`SDL_main` `0x140046340` calls `SDL_GL_CreateContext` `0x140ab15d0` at `0x140046b7d` after creating the window and stores the returned pointer at `0x1412df948`. Its setup path calls `0x140a70a50` at `0x140046da5`; that calls the UI device creator `0x140a6f9d0` once and then font refresh `0x140a70d90`. The original REA incoming-call census for `0x140a6f9d0` contains only `0x140a70a50`, whose only incoming direct caller is `SDL_main`. The single direct `SDL_GL_CreateContext` caller is also `SDL_main`. At loop exit, `SDL_main` calls UI teardown `0x140a71ef0` before `RenderInterface::Shutdown(1)`, app-manager destruction and conditional `SDL_Quit()`. Its direct-call census shows no call to `SDL_GL_DeleteContext` `0x140ab15e0`, and the pinned `.text` RIP scan has only the store at `0x140046b82` referencing context global `0x1412df948`. These facts establish the observed direct lifecycle, not how the dynamically loaded SDL module retires a context on `SDL_Quit` or whether an indirect unobserved context path exists. REA `SDL_main` `ev_833c7aa9adb229ef33dd413c495d7c0f61fbec645c741d6268e78b62f252dd65`, UI creator `ev_faee64a092bd08c0f8a48f20e46fa3e4718facf1914d4368cd7004c1f12ad9d7`, setup `ev_69754b1afedf071d1d8718ad7ae8156dce2239821b089bba015e3ef8e299e361`, delete-context thunk `ev_0e4e19c8e1a932a1f56b673ab308411c6fae5f3960e1be5472b56fa4caa7a56a`, UI teardown `ev_99a86cdf8f09714d1f82b6c183570759e149b1d501923fe6a990664630d52bed`.

`RenderInterface::Shutdown` `0x1400bf380`/`GLRender::Shutdown` `0x1400bb560` walks the renderer's custom-program list at `0x141404f40` and deletes those program IDs. The function has no read of the UI program, VAO, VBO/EBO or atlas globals; the UI teardown above owns deletion of the program/shaders/buffers/atlas. This prevents assigning a UI deletion to the generic custom-program cleanup. REA `ev_8a23fc5eed561c3b7d2fbab39c09253f54ba154f8242eb92b85c9448c18228ab`, `ev_a281e7a45e762e60488eeeb9ce6910bb61016ace68ec325862697cbdb50da3d8`.

## Two VAO API pointer sets and the missing delete

The binary resolves two `glDeleteVertexArrays`/`glGenVertexArrays` function-pointer pairs. `0x140b70e00` loads the pair into `0x141443f50/+0x141443f58` through `wglGetProcAddress`; the UI creator's read-only pointer-table cell `0x140ee4870` contains `0x141443f58`, and its `glGenVertexArrays` call is `0x140a6fd07`. `GLRender::ResetRenderStates` `0x1400b6050` and vertex-object setup `0x1400ba770`/`0x1400bacc0` also call `0x141443f58` to create **separate renderer VAOs**. Reset creates `m_VAODefault` only when zero, then binds it. REA loader `ev_725805f963a4cbd59b668c137be2c2a624ce413af95fba83fbb05b42a53d3748`, pointer-table bytes `ev_b61104826b8274471b358b9e897293513825692746da03f75b2590d90af0fbba`, reset `ev_753f31d018b6d13a4dd92c3a0cb353c8ae2602de030939ffd7dca50461e324aa`, vertex-object routines `ev_75d97b3e5130520f430e6c21f94976b0c4dfabed9578790c06af65a9cdec5a2a`, `ev_bae9b5bff5ac07495c2764495f240af3ad83df46761f74011e01445c7d2676cb`.

A separate extension loader stores `glDeleteVertexArrays` at `0x141442ce8` and `glGenVertexArrays` at `0x141442cf0`; these are **not** the cells used by the UI creator. The pinned executable-section scan finds only their loader stores for the delete cell `0x141442ce8` and the UI/generic-loader store at `0x140b70e2d` for delete cell `0x141443f50`. A saved `.rdata` pointer scan found no table entry to either delete cell; the nearby UI pointer table at `0x140ee4850` contains bind and generate cells, not delete. Ghidra's UI teardown body has no `glDeleteVertexArrays` call or read of UI VAO `0x141429a68`. This closes the **explicit original-binary deletion path as absent in the observed direct UI/renderer shutdown flow**. Indirectly computed use and destruction of the OpenGL context by SDL/driver remain outside this static proof. REA loader store `ev_2c6d358501941fa60ed7ac57263fcb4d6b4b654fac99baec46db67fce4032b12`, UI pointer table `ev_ea62d3fc41671992d371c34a383c718adc7b7500e57c304548a6e7c8db561af4`, UI teardown `ev_31fa676acca921352feeb7b86e05666bb07b19aadcc1fe805d5e19215edbb577`.

## Refresh and invalidation boundary

Draw `0x140a71760` calls `0x140a70d90`, but that refresh returns unless dirty byte `0x1412996e0` is nonzero. On dirty it rebuilds CPU font/atlas data and calls uploader `0x140a6fe10`. The uploader replaces only the atlas texture; there is no call to program/shader/VBO/EBO/VAO creator. A GUI-scale change, reshape, `Reload NUI`, and the broader client resource-reload action can set the dirty byte, as classified in the main lifecycle document. The broader action `0x1407cefa0` may call `RenderInterface::ReloadShaders` on its `param_2==0` branch and then sets the UI atlas dirty byte, but it does not call `SDL_GL_CreateContext`, `0x140a6f9d0` or `0x140a71ef0`; its `0x1406de740` call recalculates walkable material flags from `surfacemat.2da`, rather than clearing a GL/UI context. Thus the observed reload branch rebuilds generic renderer shaders and schedules Nuklear atlas refresh, without a proven UI device recreation. REA refresh `ev_27d673120a5dffd05d650a50a873aa339ed1664f665392bfa2a223413498697c`, uploader `ev_f2fd33c864a834637c5567bcf712bec0dfd667c21e1d0e2957119be88763d855`, resource action `ev_1ec8b22b9215a77cbfef902bb6fd2871ea8abb71adee6acfb9d12667797db8ab`, material recalculation `ev_fa1d241e95014a4f7419620337970eb56a4a13d3fd78a62ceffb4631a13f77d5`.

The remaining original-only boundary is the dynamically loaded SDL implementation behind `SDL_Quit` and any indirect/extension-mediated VAO deletion or context recreation not represented in the observed direct call/reference censuses. Neither a UI VAO delete nor UI device re-create during `Reload NUI` is established.

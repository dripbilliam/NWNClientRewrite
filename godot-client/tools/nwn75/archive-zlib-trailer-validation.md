# NWN-75: compressed resource zlib trailer validation

Pinned installed `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. The [XRES source-1/source-2 branch](archive-zlib-fast-decode-ownership.md), [stored-block path](archive-zlib-stored-block.md) and [slow Huffman output](archive-zlib-slow-huffman-output.md) reach decoded bytes. This note closes the distinct final checksum/length admission of the shared inflater before those bytes can become a serviced resource buffer. It does not imply a particular compressed archive entry is loaded in a frame.

`ZlibCompressionProvider::DecompressBuffer 0x1401a9dd0` selects `z_uncompress 0x1405a3f70` for an admitted algorithm-1 XRES payload; the wrapper calls `z_inflate 0x14059e390` at `0x1405a4033` until a nonzero status, then calls `z_inflateEnd` at `0x1405a4072`. `z_uncompress` returns success zero only when the inflater reports stream-end status `1`. The provider marks the decoded `DataBlock` used only after that success, and the archive service still requires its own expected-length match before invoking the destination `CRes` serviced hook. Source class, XRES/inner version, DEFLATE block, actual bytes and allocation remain conditional. Evidence: `ev_abdd5efc519165cad10cd4f2bd64706c397027250d33b066f99da604e2af1c0c`, `ev_489fd0a7edbbae6faaddfb919ceb23d91226acc8b2548afc30ab67fcf0125f9e`.

After the final block, `z_inflate` reaches trailer state `0x3f4e` at `0x14059f887`. When wrapper checking is enabled, it collects 32 trailer bits, resuming later if input is exhausted. If checksum accumulation is enabled and new output exists, `0x14059f8e3` calls `z_crc32 0x1405989c0` for the gzip-style mode or `0x14059f8ea` calls `z_adler32 0x140597cc0` for the zlib-style mode, using the newly produced output range; the returned checksum is stored in inflater and stream state. The CRC wrapper tail-jumps to table-based `crc32_little 0x1405983f0` for nonnull data; the Adler wrapper tail-jumps to `z_adler32_z 0x140597cf0`. Both are CPU arithmetic leaves. The trailer comparison at `0x14059f938` reverses byte order for the Adler case; a mismatch sets error state `0x3f51` and `incorrect data check` at `0x14059f93e`–`0x14059f94a`. Evidence: inflater `ev_eb7daa06a1219313e952b690a5c28e961d648e531aaa115f89354cb53319c1c5`, CRC `ev_5c2c4c55b3a42673274a0de6e1896dcdacbacc5590545232c540a62f779cc169` and `ev_4643cc6117932710fbd8303185c304e8519e65f1df6cfaf903ba1360a681dd0a`, Adler `ev_f3232ad8400b858070b33fe08e89bd7cce8c0f31125e468445409cd7dad20265` and `ev_0b942f5c64cf36f7d1f68bb153745f5543f49c12834ed1e81c4f9cc1bb1eb22b`.

On matching data checksum, state `0x3f4f` at `0x14059f95d` checks a further 32-bit uncompressed-length trailer only when the wrapper mode is nonzero and the gzip-style flag is set. Comparison at `0x14059f997` against accumulated output length `+0x24` rejects a mismatch with `incorrect length check` and state `0x3f51`; input exhaustion remains resumable. Otherwise the inflater enters `0x3f50` at `0x14059f9e1` and returns stream-end `1` through `0x14059f9e9`. The common return path also updates the rolling CRC/Adler on newly produced output at `0x14059fa3d/0x14059fa44` when wrapper checking and new bytes permit. Error state `0x3f51` returns `-3` at `0x14059f9f4`. These gates precede resource publication; no GL draw or upload occurs in the trailer branch. Evidence: `ev_eb7daa06a1219313e952b690a5c28e961d648e531aaa115f89354cb53319c1c5` and original instruction sites above.

External/runtime boundaries remain the selected archive/source, input bytes, checksum mode, whether the stream is valid, the later exact-size check and whether a model/texture/shader consumer subsequently draws. The linked service and renderer notes cover those separate conditional stages.

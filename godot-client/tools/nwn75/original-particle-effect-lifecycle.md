Original `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. Addresses are original PE virtual addresses. ## Source-selected callbacks and target registration

`PartEmitter::Initialize` `0x140061d80` sets per-instance movement callback `+0x170` to `moveParticleStandard` `0x140068010`. An authored point-to-point flag registers `SetEmitterTarget` `0x1400643c0` on owner Gob `+0x50` and selects `moveParticleP2PGrav` `0x140067340` or `moveParticleP2PBezier` `0x140066940`; it also creates/loads its Material. `LightningEmitter::Initialize` `0x140061d30` calls the base initializer, forces its lifespan field to one, and registers the target callback (`ev_3905f9c842ca12afc35eb75262ef0cd7f3c3c00c111e7fe9567cdee463bb828d`, `ev_e8af235aa56fb1af75fae151f4c35397d3a2da9daacd9726d65058b60332b1ce`). The three movement callback bodies are `ev_efff8e57f1f0a30996dfa11402071aedfc1e4fbc034f0cf375b9f83a393c59e2`, `ev_501e440560f6d850b4a9cc296e0232c24ed26c36a1a2c3c12567851d69ce0780`, and `ev_aef1d38f4ca73f80523ae2c577b91d967a1bf3305d8bf14b81f7c77628802d91`. Their CPU `Scene::GetWindVector` and virtual `Scene::HitCheck` branches are detailed in the scene animation/emitter document.

`SetEmitterTarget` scans child Parts for a `PartReference` and stores its referenced Gob at emitter `+0x1c0`. It updates target distance and, only for a LightningEmitter, target-relative vector fields. If no reference is admitted, it calls owner `Gob::DeregisterCallback` `0x140050cb0` for the stored callback handle (`ev_1e1fd58dab597943b3885b95431c700892f4fcb761dd583b1a146433418a4005`, `ev_2fabb0877f7ef8cb143f6ed112fa11eb3fd7221255a033da9b49766e92d86c79`). ## Particle and emitter teardown

### Attached Chunky model source and bounded Part family

`ChunkyParticle::ChunkyParticle` `0x1400602b0` passes the **authored emitter model name** at `MdlNodeEmitter+0x158` to `NewCAurObject` `0x1400931f0` at `0x140060340`, with an empty Gob name and null stream. This takes the named-resource route: with LOD disabled it calls `FindModel` `0x140098cd0`; with LOD enabled it first demands optional composite resource type `0x81e`, parses up to three model names if present, and calls `FindModel` for those names, falling back to the original name when the resource cannot be demanded. It does not use the supplied-stream `LoadModel` path for this constructor call. A failed model lookup returns no attached Gob. Evidence constructor `ev_a835c7c30c035c6d53c1f634d31e77e7825f252efc92bccc6a08a310d2e47917`, object factory `ev_f456a590b87bf33093742cf8df2e8e3f9803908ba96690c150afdc9f60a001f5`.

With a model result, `NewCAurObject` constructs a Gob, creates root Part trees for the base and optional LOD models through `CreateInstanceTreeR` `0x14008dab0`, creates reference objects, raises `_EmitterTarget`, and recursively initializes materials. `CreateInstanceTreeR` calls the model node's stored `+0x28` creation function. The constructor-backed family is AABB, AnimMesh, Camera, DanglyMesh, Emitter, Light, Reference, Skin, TriMesh, Trigger and base MdlNode; the exact descendant is selected by the loaded model tree, as detailed in [model instance construction](model-instance-branch.md). Thus the attached-model route has a concrete producer and bounded code family, while the **asset name, node mix, and behavior attachment of a particular effect remain content-dependent**. The resulting Gob is stored at `Particle+0x78` and attached to `currentscene` through its virtual `+0x90`, which is the source of the ordinary Scene geometry branch when `RenderNothing` suppresses emitter quads. Evidence `ev_f456a590b87bf33093742cf8df2e8e3f9803908ba96690c150afdc9f60a001f5`, `ev_a835c7c30c035c6d53c1f634d31e77e7825f252efc92bccc6a08a310d2e47917`, `ev_25a7501b`.

The created Gob is the base class from `Gob::Gob` `0x1400869d0`, which installs vtable `0x140d88a00`; original PE slot `+0x90` at `0x140d88a90` contains `Gob::AttachToScene` `0x1400c5780`. This resolves the constructor, reuse and expiry virtual attach/detach calls to that concrete target for this producer (`ev_4b850bfe919c55ffc18fcba39695646d75a74f85c353b99fed06eabb2a785b5b`, pinned vtable bytes). A different Gob subclass introduced by other code is outside this constructor path.

`PartEmitter::~PartEmitter` `0x1400608e0` destructs every live and reusable particle through virtual `+0x0`, deregisters itself from an attached `WindManager`, removes its Part from the Scene manager, destroys its Material and frees both particle arrays before the base Part destructor (`ev_685f8a55b2bd1907918b8f68f9eec2d05218f6950e81a981bef1650e4338e920`). The ordinary `Particle` destructor `0x140060e50` frees only the particle; the `ChunkyParticle` destructor `0x140060cf0` first invokes the attached Gob's destructor, then frees the particle (`ev_8de555de2b33392ea0ba5a0ad120d1263548be3e2a4c95cda2a0181b825b1252`, `ev_c4e41a63ff96b2a2b27e05c7aefcd8a4eea1a991935139899c3b4eea1d06cfa5`). `ChunkyParticle::ChunkyParticle` `0x1400602b0` creates the attached Gob and calls its `AttachToScene` virtual when present (`ev_813d762b4648ac8a2f38e9a61fc1dc0447cf5db0f6a0bc5cac960c029b6f76d2`). Reinitialization `0x1400663d0` reattaches it, scales it and plays `impact` (`ev_65645e3fdedf1bc0e299e49d0f38911da109e38bf8004db95233c840fd213747`). Expiry `chkParticleLife` `0x140065f10` detaches the Gob but retains the particle in the reuse list (`ev_c28d619fc7cca31615ed3b62a1836ad0c34598e9086dc8545fd21a2d92e35a3a`).

`Scene::RemoveFromSceneManager` `0x1400cc4d0` removes a qualifying emitter from the global emitter bucket (`ev_068b81da594a86f00798bbed1b6685545f6ad232e5f721d25ec946c0517cf125`), and `WindManager::DeregisterWindyEmitter` `0x1400f1450` removes the registered emitter from its wind list (`ev_76f1fd9ca452a3cc675fc005c416500cdde2c67f7331a516b3cd81692ccc4c6d`). `Gob::AttachToScene` `0x1400c5780` calls `Gob::SetScene` `0x140095250`, which removes/adds the child to Scene membership when its pointer changes (`ev_59a27eca9979c6ac9a91a8016fd807444610412e3af0c3f721d631d0baa4a8cb`, `ev_643830a77c06dfc50804134d4969249c53b6633d7f12508994ddf59720aae7aa`). Lower BSP membership and behavior-hook descendants belong to the common Scene/Gob lifecycle tree. `Gob::~Gob` `0x1400889c0` destructs its root Part tree and then frees every stored callback object in Gob `+0x460/+0x468` (`ev_37bcbeae15c0111245807ce8d3fb05b12e4c30559d96a9201268069213a32210`). This establishes eventual callback-list cleanup on Gob destruction; `PartEmitter::~PartEmitter` itself does not show an owner `DeregisterCallback` call.

### Owner callbacks and behavior teardown

`MdlNodeEmitter::InternalCreateInstance` `0x1400621f0` stores the owner Gob at emitter `+0x50`; Explosion also registers `Detonate` on that Gob before emitter initialization. `PartEmitter::Initialize` registers `SetEmitterTarget` for authored point-to-point behavior and stores its `CallBack*` at `+0x128`; Lightning initialization registers the same event again. `Gob::RegisterCallBack` `0x140052a30` allocates a 0x30-byte record with event name, function at `+0x20` and context at `+0x28`, then appends it to Gob `+0x460/+0x468`. `NewCAurObject` raises `_EmitterTarget` after building its model instance tree; when no child `PartReference` is admitted, `SetEmitterTarget` calls `Gob::DeregisterCallback` `0x140050cb0`, which removes and frees the matching record. `Detonate` `0x140061a30` only sets ExplosionEmitter `+0x108`; the matching event reaches it through `Gob::DoEvent` `0x140050d50`. Owner `Gob::~Gob` emits `Dying` before clearing animation, removing Scene membership, destroying behavior and root Part, and freeing callback records. `Part::~Part` recursively invokes child Part virtual destructors, so a child emitter enters the PartEmitter teardown above. `Gob::SetScene` invokes installed behavior virtual `+0x10` before Scene removal/addition; base `CAurBehavior::SetScene` `0x140056e90` is a CPU no-op. An installed Attach behavior's destructor `0x140054390` removes its child attachment and deregisters six target-Gob handles before `CAurBehavior::~CAurBehavior` `0x140054290` removes dependency registrations. These are admitted owner/attached-model behavior branches, not proof that any particular Chunky model installs Attach. Authored Part/behavior subtype populations and unrelated `Dying` callback registrations remain dynamic. Evidence: `ev_8be076b23fb4a47b58187e2fe02d0b07551d54ff748762b8e92e61dcee9bc01a`, `ev_69ca0b06070b147a269ca42a20aee71fd673cf9434c72c8362d0fee960716b69`, `ev_88f142c8fac0a5b7ef80bac56b3cd5543e7b1281e81e29ec9a5cbf08d7c1b9d9`, `ev_28a6db585ee861d0a06c10a6679b3853b3f0825f3eb664abb1d2adca950b1781`, `ev_0110930fd2b93d4764c8a505a2f3f109fc6efd75d258363543b65f662396f76a`, `ev_77b350dee89a2079e8422c5a65d54ed7708abeab1460d1782652caa127aa9184`, `ev_fd66696c6ecf7eecd2709b8f529448ce878612c33c9360c2decc570cb4c6f5d2`.

The remaining `Dying` callback frontier is at a concrete runtime data edge: `Gob::RegisterCallBack` `0x140052a30` stores its caller-supplied function at `CallBack+0x20` and context at `+0x28`, then appends that record to Gob `+0x460/+0x468`. `Gob::DoEvent` `0x140050d50` walks those records backward; empty or `*` names match any event, otherwise `_stricmp` compares the requested name, and the computed call at `0x140050e38` invokes the stored function with the supplied event data or stored context. `Gob::~Gob` supplies `Dying`, but the original executable cannot assign a single callee to every such record without the runtime registrations and loaded model/behavior content. The known particle registrations are `_EmitterTarget` and `Detonate` above; other registrations remain an explicit dynamic boundary rather than an unnamed static call. Evidence `ev_96b7c3e3c0874383ecc02b30dcf1875f2eb4bb1d81583a3d58f5b72dedf9923e`, `ev_cf0861cb88a08df86b58fc54e3a6e4480ef37a39a0c39d893fd61a8efe31fbef`, `ev_37bcbeae15c0111245807ce8d3fb05b12e4c30559d96a9201268069213a32210`.

## Optional diagnostic drawing

Normal emitter and `RenderNothing` callbacks may call `PartEmitter::RenderBoundingSphere` `0x140062870` only when the debug sphere flag is enabled. It calls `RenderInterface::DrawSphereBound` `0x1400bea80` and `DrawCrosshair` `0x1400bea40` (`ev_009250097dea15eb193db9cb6296f14bc3b5bd497048498e7d0b95971b6cbc27`). `DrawSphereBound` forwards to `GLRender::DrawSphereBound` `0x1400b1f80`, which initializes static vertex data once and draws through `GLRender::RenderVertexData` `0x1400b59b0` (`ev_18e27ce486217df869ba9be0cd55f68f2748c3da6bb627f9fb472571bf640f23`, `ev_92b0e82c546f21d2bba8085a91a37c82cf91e91c5ef9601ac95f1e251ae0f216`). `DrawCrosshair` forwards to `GLRender::DrawCrosshair` `0x1400b18b0` → `GLRender::DrawLines` `0x1400b1d70`, which fills/commits a dynamic stream and calls `GLRender::RenderVertexStreamData` with line primitive `1`; that reaches imported `glDrawArrays` (`ev_1bf6bb0154bf2c6cbddf4b437e82eb4112f8217b0884f3e08915f1465593758d`, `ev_6217a1b6fb54b23cba044ba25983f762b10f42da398e76f813732e0784093104`, `ev_424c484aed98f344f61c3334876d27d164a6d1de566bc2785de8b248bc4d4188`). The optional debug gate prevents treating this path as normal particle work.

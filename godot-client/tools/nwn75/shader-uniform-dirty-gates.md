# NWN-75: original shader uniform dirty gates

Status: partial original-binary branch map. Installed `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. `GLRender::SetUniforms` `0x1400b8380` has retained REA evidence `ev_1a4116233c92836c24653152acff91f84c48e7899cc3e2c69a0d2729deec3431` (59,142 UTF-16 pseudocode units). [The GL callsite catalog](shader-uniform-gl-callsites.json) identifies all 129 computed `glUniform*` calls. [The fixed uniform location map](shader-uniform-location-map.json) connects 113 queried names to their per-program offsets in `ConnectShaderData`; dynamically formatted bone/light names and other assignments are separate. This map records gates; it does not infer their runtime frequency.

`GLRender::SetProgram` `0x1400b7a40` selects a custom or stock program, calls `glUseProgram` only when the program ID changes, then calls `SetUniforms` even when that ID was already bound (REA `ev_c2fa9ed1743a63b47c3b92d6a2cd636bdebff3734eddc2913bdeac583cee5a97`). Each program stores prior generation values and uniform locations. `SetUniforms` checks both the generation and nonnegative location before many uploads.

The `Scene+0x1b8` branch has an important nested shape. On a changed scene frame counter it uploads that counter and world time, sorts the two keyhole diameter bounds into min/max, then reads a point-source list through `currentscene+0x160`. It caps the source count at 128, packs positions, radius, duration, intensity and nonnegative time remaining into local arrays, and uploads only uniforms with valid locations. Inside this scene-frame branch, a separate comparison of the selected program's `+0x00` against `m_shaderConstantsi`'s second integer gates the area/global light controls, AO, contrast, depth of field, gamma, toon, bloom and target-shape uniform groups. This describes analyzed branch structure, not the number of wind sources or how often either generation changes at runtime.

### Texture-stage loop

At program connection, `ConnectShaderData` queries 16 sampler names into program `+0x1c84`: `texUnit0` through `texUnit10`, then `texFBColor`, `texFBDepth`, `texUnitEnvCube`, `texUnitEnv`, and `texUnitNoise`. It queries their corresponding `texture0Bound` through `texture10Bound`, then `texFBColorBound`, `texFBDepthBound`, `texEnvCubeBound`, `texEnvBound`, and `texNoiseBound` into `+0x1cc4`. After binding that program if needed, it assigns each valid sampler location its stage index 0–15 with `glUniform1i`. This is program-connection work, not a per-draw sampler assignment (REA `ev_bb08e2053006c0ce392c4712375821ca95e52b0686cd416bf4bc93574eab0517`).

After the fog generation check, `SetUniforms` walks exactly `0x10` texture stages on each call. It combines `m_bEnabledTextureStages`, each bound-texture handle, and a selected-program bitmask at `+0x1d08`. A stage whose desired active state differs from that cached bit flips the bit; if that stage's bound-flag uniform location in the `+0x1cc4` array is valid, it calls `glUniform1i` with 0 or 1. Unchanged stages do no uniform upload. Thus the 16-stage CPU check is an unconditional descendant of `SetProgram`'s uniform call, while texture-state GL uploads are change-gated. This is from the retained `SetUniforms` body and the pointer catalog; it does not establish call frequency in a gameplay frame.

Of the 113 fixed queried location fields in `ConnectShaderData`, 112 are referenced in the decompiled `SetUniforms` body. `materialFrontShininess` at program `+0xabc` is queried but has no `param_1 + 0xabc` reference in that body. This is a local static observation; it does not establish absence from other procedures or a runtime shader effect.

The 14 direct callees inside `SetUniforms` are non-GL helpers: `LightManager::GetMaxLights`, a `Vector4` constructor, `RenderInterface::GetColorSpaceFromSRGB`, three matrix/vector multiplication overloads, matrix `Inverse`, matrix `get3x3`, `memcmp`, a byte-copy routine at `0x140c417f0`, a floating-point power routine at `0x140c7c810`, thread-safe static initialization header/footer, and the security-cookie epilogue. The byte-copy routine's analyzed switch copies 0–7 bytes directly before larger-size paths; the power routine's analyzed body branches on floating-point exponent and magnitude. Their retained evidence is `ev_16d3100b6105925aa7c5178516d0446689195bc8f7cda5c461a3a05c1ba14dda` and `ev_137ebb604daf8bb19309391f09e36fba9006a8f9ac9ff890a77cde6c4c7845e4`. REA lists 129 targetless call instructions in `SetUniforms`, all separately identified by the GL callsite catalog linked above; no additional direct rendering callee is observed in this body. This classifies the immediate helper frontier, not every CRT/math instruction inside the helpers.

`RenderInterface::GetColorSpaceFromSRGB` reads global shader integer parameter 0 and, when nonzero, calls `color_pow` with exponent 2.2 before copying the Vector4 result. `color_pow` tests the first three channels and invokes the floating-point power routine only when a channel is positive and not 1; it leaves the fourth channel untouched. This is CPU color conversion before the gated material/global-color upload, not a GL call in the helper bodies (REA `ev_2e33eb796bf5885d50e3d5a9f01185af638b51ddc4f917068c188d438ffd1c62`, `ev_7446a08d681b44c1fab2845920e9cbca9717803ce6a5733cf1c4cac970e49b91`).

### Light and bone descendants

The light branch executes when its program generation `+0x0c` differs from global `0x1413d26fc` **or** the view-matrix generation changed. Four static 128-entry `Vector4` arrays are guarded by thread-safe one-time initialization. `LightManager::GetMaxLights` returns the configured maximum clamped to `0x80` (REA `ev_75b2ba993ef28490fe74a8746381f7613345709497ccb3743983a189810e0823`). `SetUniforms` walks up to that limit, copies data only for light entries whose active byte at `+0x44` is set, transforms one light vector through the current matrix, and packs five arrays/count for valid uniform locations. Those outputs use loader-identified `glUniform1i`, `glUniform4fv`, and `glUniform1fv`; separate area ambient/diffuse, direction and global ambient uniforms follow. This describes the original packing route, not how many lights Arelith activates.

When global generation `0x1413d2704` changes, `SetUniforms` updates the bone-enabled uniform from state bit `0x200000`. Under the enabled branch it compares each of 64 global 0x40-byte bone matrices against the selected program's cached copies. It copies changed matrices and, if any changed and the bone-array uniform location is valid, calls `glUniformMatrix4fv` once with a count ending at the highest changed slot. The analyzed loop is unrolled in groups of 16. These comparisons and uploads are conditional on this outer state generation gate, not unconditional every draw. The exact light and bone code is in retained SetUniforms evidence above; GL pointer identities are in the linked callsite catalog.

The preceding [light-state branch](lighting-state-branch.md) identifies `LightManager` selection and `RenderInterface::SetLightProperties`/`EnableLight`/`DisableLight`/area-light setters as producers of `0x1413d26fc`; they update cached GLRender light state and the dirty generation before this upload function. They do not call GL immediately.

### Custom parameter record loop

The `0x1413d2738` generation controls a per-program array at `PROG_FIXED+0x1ee8` with count at `+0x1ef0`; the analyzed loop advances by `0x6c` bytes per record. For record type 0 it compares a cached float payload at record `+0x4c` with a pending payload at `+0x5c` for `component_count × 4` bytes. A difference reaches `glUniform1f` for one component or `glUniform4fv` with vector count one for parser-admitted counts 2–4 when the location at record `+4` is valid, then copies the new payload into the cache. Type 1 compares cached/pending integer values at those offsets and reaches `glUniform1i` on change. Both branches can clear pending values and force the program's `+0x48` generation to `-1`, causing a later revisit. The type-0 reset predicate and source component counts are now instruction-backed in [custom shader parameter flow](shader-custom-parameter-flow.md). This is a registered-parameter route, not an upload of all records on every `SetUniforms` call.

Initialization/reload zeroing of the custom generation and the known in-image indexed-integer setter calls are traced in [custom shader parameter flow](shader-custom-parameter-flow.md). Later computed/indirect generation writers and nonmaterial custom records remain open. Decompiler-missing arguments at indirect `glUniform*` calls are not supplied by assumption.

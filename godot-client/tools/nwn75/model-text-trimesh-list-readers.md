# Text TriMesh list readers and face elements

Pinned original `nwmain.exe` SHA-256: `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. The [ledger](model-text-trimesh-list-readers-ledger.json) records the parser descendants. This continues the [shared text TriMesh field dispatcher](model-text-trimesh-fields.md) at its CPU list readers; it does not establish live model frequency.

`Parse<Vector>` `0x140097c90` (REA `ev_4d29859479236afaa5a0bf23907ee1305f9ee3d12c7c9d7c61355b09499c8ced`) supports three authoring forms. Without an integer count in the field line, it reads nonblank lines via `AurResGetNextLine` `0x14005dff0` until case-sensitive `endlist` after leading space/tab trimming, grows the 12-byte Vector array and scans three floats per line. A count alone sizes the array and reads that many nonblank float lines. A count plus marker reads `12 × count` raw bytes through `AurResGetData` `0x14005de20` and copies them into the CPU array. Its zero-count case frees prior storage. `Parse<Vector4>` `0x140097a00` (REA `ev_2b41acf6328284826ef2c12631572b0fbc1370c8e426c4a0163b280067b5040e`) has the same three modes with 16 bytes and four scanned floats per item.

`Parse<int>` `0x140096530` (REA `ev_5db7523996b7dcf806b575d279b195109edbce18d8bec6b2afbf0a006e23a216`) and `Parse<unsigned_int>` `0x140096790` (REA `ev_54b3571d0047f460d3728d64f5d19ee4acd9b1ce2de2fee77bc2c94f638925d9`) use the same no-count `endlist`, counted text-line, and counted raw-data branches at four bytes per element. Their text-line elements dispatch to scalar `Parse` `0x1400a0280` and `0x1400a0320`, respectively. Array sizing/growth stays CPU-side; the only resource edges are the line reader and byte-data reader. Count validation, null lines and allocation outcomes are separate malformed-input boundaries.

`Parse<MaxFace_PostProcess>` `0x140097250` (REA `ev_fc045200fe11fce6442f96e7a1ba91fbfc180faa4d5aac81608d233c6263ac51`) uses the same three modes but with 0x20-byte face records. Its no-count path reads to `endlist`, grows the face array and calls `Parse(face line, MaxFace_PostProcess&)` `0x1400a0810` for each element. The counted text mode sizes the array and calls that element parser on each nonblank line. The count-plus-marker mode reads `0x20 × count` raw bytes and copies them into the array. The element parser (REA `ev_e44dca0a4b068d7a2d4f751eebfb3de4f0440145ddef83add79679a9aaff348c`) first frees three existing element pointers if present, then allocates 0x30, 0x0c and 0x0c CPU blocks, clears them and scans eight integers from the face line: three into the first 0x0c block, one into face `+0x10`, three into the 0x30 block and one into face `+0x14`. The third allocated block at face `+0x18` receives zeros here; later postprocess use is outside this element reader. The raw-byte form bypasses this per-element parser, so its pointer fields require separate downstream interpretation. This note records the decompiled branches and does not assert malformed text or binary count safety.

All five readers stop at CPU list storage, `AurResGetNextLine`, `AurResGetData` or CRT allocation/copy/free. They do not request a render pool or GL call. The conditional text postprocess→vertex pool route is documented in the [model parser](model-name-parser-tree.md) and [geometry boundary](geometry-and-draw-boundary.md). Static function bodies do not prove the invoking OS thread, active authoring mode or list population.

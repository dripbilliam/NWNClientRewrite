This is the shared text-field continuation for ordinary TriMesh, AABB, DanglyMesh, Skin and AnimMesh parsers; subtype dispatch and binary construction are mapped separately in the [text subtype](model-text-skin-animmesh.md), [AABB](model-aabb-payload.md), [Dangly](model-dangly-payload.md) and [compiled mesh](model-binary-trimesh-pool-streams.md) branches.

## Line and geometry fields

`ParseNode` calls the typed node's parse virtual `+0x8` once per resource line until `endnode`. This TriMesh body lazily allocates a `0xb0`-byte `MdlNodeTriMesh_PostProcess` at node `+0x278`, then repeatedly extracts the line's first word into a global 0x400-byte buffer, checks the bound, and compares case-insensitively with each recognized token. It is CPU line parsing on the model load path; this function does not call a render pool or GL API. Unknown/shared lines ultimately go to `MdlNode::InternalParseField` `0x140099650`, mapped in [base-node fields](model-text-base-node-fields.md). The `0x400` bound failure terminates through `__report_rangecheckfailure` `0x140c11104` rather than a normal parse leaf.

`verts` goes into postprocess `+0x00`, `tverts`/`tverts1`/`tverts2`/`tverts3` into `+0x10/+0x20/+0x30/+0x40`, `colors` into `+0x50`, `normals` into `+0x80`, and `tangents` into `+0x60` as Vector4 values. `texindices1/2/3` use the MaxFace postprocess index readers. `faces` is special: it calls the MaxFace postprocess list reader only when that list's count is zero. If the postprocess face count is positive after the token checks, it sizes node face list `+0xb0` and copies one 32-bit field per 0x20-byte face entry into its `+0x10` slot. `mirrorlist` uses the integer-list parser. The readers' text-line and raw-data modes, element parsing and CPU allocation leaves are mapped in [text list readers](model-text-trimesh-list-readers.md); later conversion to vertex streams is in the [text model parser](model-name-parser-tree.md) and [geometry boundary](geometry-and-draw-boundary.md). The parser's unconditional-looking face copy is a static control-flow observation, not a measured frequency claim.

`bmin` and `bmax` parse three floats into node `+0xc0..+0xc8` and `+0xcc..+0xd4`. `vertexindicescount` parses an integer list into `+0x248`, and `leftoverfaces` parses an unsigned-int list into `+0x238`. The `vertexindices` token parses an outer count, sizes the pointer array at node `+0x228`, then for each outer entry reads a resource line containing an inner count, allocates four bytes per inner entry and consumes that many more lines through `AurResGetNextLine`, scanning one integer each. This is a nested resource-line and CPU-allocation leaf, with counts and validity determined by authored text. No render upload occurs in this parser. Text TriMesh postprocess later checks vertex count `+0x284`, performs [ProcessVerts CPU geometry](model-text-trimesh-processverts.md), builds neighbors and indices, and conditionally calls `GenerateVertexData`, which requests/locks/unlocks position, normal, color, tangent and UV pools; that downstream boundary is in [model parser](model-name-parser-tree.md) and [geometry boundary](geometry-and-draw-boundary.md).

## Material and controllers

`texture0`, `texture1`, and `texture2` scan names into node `+0x124`, `+0x164`, and `+0x1a4`. `bitmap` is a legacy texture-0 synonym: a nonempty value first clears 64 bytes at `+0x124`, then copies at most 63 bytes. `materialname` scans a name into `+0x1e4`. `renderhint` calls `SharedMaterial::ExtractRenderHint` `0x1400830c0` for a nonempty token and stores the result at `+0x120`. That helper maps case-insensitive `normalandspecmapped` to 2, `normaltangents` to 3, `none` to 1, and other strings to 0; it ends at CRT `_stricmp` with no resource or GL call (REA `ev_491842fc1b74c8af7ea934cc5d8b6f70f79da22dd452600183d2a80d4da51a18`). These are CPU name/hint fields; resource lookup, material creation and texture binding belong to later Part/material paths, not this parser.

`diffuse`, `ambient`, and `specular` each scan three floats into node `+0xe8/+0xf4/+0x100`; `shininess` goes to `+0x10c`. `shadow`, `beaming`, `render`, `transparencyhint`, and `tilefade` parse integers into `+0x110/+0x114/+0x118/+0x11c/+0x224`. `rotatetexture` parses a boolean at `+0x2b9`. `selfillumcolor` and `alpha` install single-value controllers with destination offsets `0x80` and `0xa8`; their `key` and `bezierkey` forms use generic or Bezier controller builders into node controller/value lists `+0x78/+0x88`. Their evaluation and draw-time material use continue in the [instance](model-instance-branch.md), [non-emitter animation](original-scene-animation-nonemitter.md) and [TriMesh draw](part-trimesh-draw.md) maps. The exact authored values, active subtype, selected material and frame draw remain dynamic.

All observed operations in this field parser run in the invoking resource-parse thread; static code alone does not prove which runtime thread invokes it. There is no worker enqueue in this body. Its direct children end at CPU parse/list/control/name state or `AurResGetNextLine`; conditional later pool publication and GL draw occur beyond this field parser. No runtime activation or costs are inferred.

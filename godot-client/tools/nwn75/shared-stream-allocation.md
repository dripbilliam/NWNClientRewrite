# NWN-75: original shared vertex-stream allocation path

Pinned original `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This branch is reached by highlight, lens-flare, shadow-plane, trigger-volume, debug-line/path and other stream draws when they request a `VertexStreamDataObject`. Its high fan-in is a static call-graph fact, not a measured frame cost. The exact direct sites are in `branch-ledger.json`.

`VertexDataObjectManager::GetVertexStreamDataObjectTokenByAttributes` `0x1400bdaf0` scans the process-global stream-object array `0x14140abe8` and returns an existing object only when requested vertex capacity, element capacity and attribute flags match the object's `+0x2c/+0x1c/+0x24` fields. This exact-match return performs no allocation in the analyzed body. On a miss it calls `operator_new` at `0x1400bdb4c`, initializes a 0x30-byte stream object, calls `VertexStreamDataObject::Build` `0x1400bd390` at `0x1400bdb9a`, and grows the manager pointer array through `_realloc_base` at `0x1400bdbe0` only when that array is full. REA `ev_3bdf3c95c2e4ea7932e5980e53d1350bc3d3d4fba5cc622e33a427b37e1dfe73`.

`Build` derives the vertex stride from the attribute mask and requests a vertex pool of `stride × vertex_capacity`. If element capacity is positive it first requests an element pool of `2 × element_capacity`. For each created pool it calls `RenderInterface::RequestPool`, `LockPool`, then `UnlockPool`: element sites `0x1400bd47c/0x1400bd48e/0x1400bd49d`, vertex sites `0x1400bd4bd/0x1400bd4cf/0x1400bd4ed`. The function itself has no direct GL API call; the shared unlock implementation may create or publish GL buffers under its pool-state gates. REA `ev_ca715a5dd0cfe44a017f182a340237c682541a3c720e0d145058e0fffc4e250c`.

`RenderInterface::RequestPool` jumps to `GLRender::RequestPool` `0x1400b5dc0`, whose `0x1400b5dce` call enters the shared pool allocator `0x1400b5de0`. That allocator returns sentinel `0xffffffff` for zero bytes; otherwise it updates pool-byte counters and either reuses a free slot or grows the descriptor/free-slot arrays before allocating CPU backing memory. Its seven direct CRT allocation/copy/free sites are in the ledger. There is no direct GL API in these two allocator bodies. REA wrapper body `ev_b8428a549dec0e42e7151e9ca7dd66ed747ab4d7dd159d0d737c84b37d896a59`, allocator `ev_7b3e65e51469cdd814281f346641a312ae5e977d98df4c9c3b38c1892989a788`.

`RenderInterface::LockPool` jumps to `GLRender::LockPool` `0x1400b4aa0`. A sentinel pool token returns the supplied offset as a pointer; otherwise it stores the lock-mode byte and returns the CPU backing pointer plus offset. It has no child call or direct GL API (REA `ev_f5b09061b47b332e579082e8f965998c21ce514392f6df0cc01d9b5aff8393c4`). `UnlockPool` jumps through `GLRender::UnlockPool` to shared `FUN_1400bbaf0`, whose conditional buffer creation/orphan/update reaches the GL extension pointers mapped in [primitive/VDO preparation](primitive-vdo-preparation.md) and [geometry/draw boundary](geometry-and-draw-boundary.md).

After allocation, callers fill CPU vertex/element memory through `GetVertexData`/`GetElementData`, commit byte ranges through `CommitVertexData`/`CommitElementData`, and submit through `RenderVertexStreamData`. Those stages and the indexed GL draw endpoint are mapped in [optional pass census](scene-optional-pass-callsite-census.md) and [auxiliary pass census](scene-auxiliary-callsite-census.md). A request on every optional draw does not imply a new stream or buffer on every frame: the exact-match lookup and pool state decide the work.

## Raw geometry to pool slots

The raw-geometry base supplied to `FUN_14007be10` is distinct from the principal model block. For each admitted stream the node slot initially holds a raw offset. The builder reads that offset, calls `RenderInterface::RequestPool` with the **address of the same slot** (the call can replace it with a pool handle), then `LockPool`, copies bytes from `raw base + saved offset`, and `UnlockPool`. This explains the serialized-offset to live-handle transition. The following table gives **every one of the 15 RequestPool/LockPool/UnlockPool triplets** in machine order. `V` is node `uint16 +0x284`; `F` is node `uint16 +0x286`. Sizes are bytes. All listed locks use mode `0x11` except slot `+0x290`, which uses mode `1`. Unlock uses `0xffffffff,0` at all fifteen sites. The numeric stream kinds are the RequestPool arguments, not inferred semantic names such as color or UV. Those names require a separate original consumer proof. Pool helpers `0x1400beee0/0x1400bee30/0x1400bf3d0` enter the shared pool manager; `UnlockPool` can reach pool implementation `0x1400bbaf0` and, under state/dirty gates, imported `glGenBuffers`, `glBindBuffer`, `glBufferData` or `glBufferSubData` via the mapped [geometry buffer boundary](geometry-and-draw-boundary.md). Source CPU bytes may therefore be published to a GL buffer during model load, but no GL draw occurs in this builder. The later Part and primitive routes decide visibility/material/VAO/draw. No worker handoff appears in the builder; it inherits its model-loader caller thread. Pool state, valid offsets, subtype mix, loaded model choice, whether each stream is present and eventual draw frequency remain dynamic.

The separate text `MdlNodeTriMesh::GenerateVertexData` `0x1400a7790` writes source vertex floats `0..2` into slot `+0x280` and floats `15..17` into slot `+0x298`, with the latter normalized by the binary post-load walk `FUN_140079500` `0x140079500`. `Scene::LightPartTriMesh` also locks `+0x280` as the source position pool and `+0x298` as the source normal pool. These independent consumers establish those two stream meanings. The text builder writes source float pairs `3/4`, `6/7`, `9/10` and `12/13` into `+0x288/+0x28c/+0x290/+0x294`, and packs floats `18..20` into `+0x29c`; they are consistent with four UV pairs and a vertex color, but this supplement retains numeric names for the other binary slots until their draw consumers are separately bound. `FUN_140079500` normalizes `+0x2ac` as another 3-vector but does not label its semantic role.

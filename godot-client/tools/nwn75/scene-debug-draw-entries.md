## Connected light-range circle

`Scene::RenderSinglePass` calls `LightManager::RenderLightRanges` `0x1400805a0` only when `g_nRenderLightRanges` is nonzero (entry documented in [lighting state](lighting-state-branch.md)). With a current Camera, the light manager draws a source-light crosshair at `0x14008079b` when color is nonzero, and active-light circles at `0x140080840/0x140080858` after color and positive-radius checks. Those physical sites replace the earlier unsited summary edges (LightManager body `ev_469e2e00ca2980bcfacfd47ab14ebddf6f11519581a4ca8020624790f634c3a7`). `RenderInterface::DrawCircleBound` `0x1400bea20` is an E9 jump thunk to `GLRender::DrawCircleBound` `0x1400b08f0` (`ev_ba3e569a8a387b53546195f8388f17a1bc17f37525d7b778b5a26baf6326514e`).

The GL body pushes a model matrix and translates to the requested center. Only while its cached circle VDO flag is clear does it obtain a 64-vertex token/item, run 32 unrolled calls to each of two scalar angle helpers, fill static vertex data and commit it. Camera-aligned and plain circles take separate matrix setup branches. It stages global color, render-state bits and matrix dirty generations, then calls `GLRender::RenderVertexData` at `0x1400b142e` with Aurora primitive mode 6. The latter reaches the established GL draw chain. The ledger includes all 75 literal CALL sites in this body, including the 64 one-time angle-helper sites; the large count is static code sites, not repeated per-frame calls. Full body `ev_2a2b687ba2bc6a5e1d2a2104124d22e71bb8c6e37532efc2864825feb5ef64f0`. No external GL call is direct in this circle body; publication/draw APIs occur in the VDO and `RenderVertexData` descendants.

## Standalone line and reset entries

`RenderInterface::DrawLine` `0x1400bea60` E9-jumps to `GLRender::DrawLine` `0x1400b1c90`. The GL body initializes a static two-Vector list once through thread-safe CRT static initialization, copies the supplied endpoints into it, then tail-jumps at `0x1400b1d1b` to `GLRender::DrawLines` `0x1400b1d70`. That shared helper stages color/state, obtains/commits a vertex stream as needed, and calls `GLRender::RenderVertexStreamData`; its other callers include crosshair variants already in [lighting state](lighting-state-branch.md). Wrapper `ev_84e3891f790329f1949ef91011e10c71a36c4410f8e8e9a56c52daf4058c8833`, DrawLine body `ev_548a93ded1fb4da2387fc1ddd6abfba4030ebc3d7a66413b462beb0669868f0e`, DrawLines `ev_709886c90964dbe86a160a949649a83109bcd197308bbd744a2c81d291281e34`. The DrawLine wrapper has metadata DATA references only in the analyzed incoming census, and the GL body has only that wrapper jump plus metadata DATA. This does not establish an ordinary internal caller for the one-line convenience entry; the shared DrawLines path is connected separately.

`GLRender::DrawReset` `0x1400b1f40` has no outgoing call or immediate GL API. It clears two cached enable-state bits when set, increments one dirty generation for the latter, and resets current custom program and render hint (`ev_917502fed3eef2ac6a9178e1616f7bbe4b0ffdbf38419b514666732e6b17cf94`). Its analyzed incoming references are metadata DATA only. It is a CPU state leaf with no proven internal code caller; a computed/external invocation remains possible.

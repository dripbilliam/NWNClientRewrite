# NWN-75: `.txi` texture-controller registration

Pinned original `nwmain.exe` SHA-256: `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This [ledger](texture-controller-parser-registration-ledger.json) connects authored texture fields to constructor-backed controller tables and corrects the distinction between a compiled controller and a parser-reachable one. It records static possibilities, not live texture counts or update frequency.

`CAurTextureBasic::Init` `0x1400ebe40` chooses a name, calls `AurResGet(name,".txi",...,true)`, then sends each returned `AurResGetNextLine` to `CAurTextureBasic::ParseField` `0x1400ecf20` at `0x1400ebfdc`. On exhaustion it frees the resource. The resource lookup and line loop are conditional. `AurTextureMessage` `0x1400e8d60` and console `texmessage` `0x1400eefd0` are two other direct callers of the same field parser, at `0x1400e8d98` and `0x1400ef079`; each resolves a Basic texture and queues it for refresh after parsing. They are alternate text inputs, not proof of `.txi` asset use. REA `ev_1ff7e2b7ad40c35c714050e7cefe9fe9f1133d141ccd73be27dee14ef4b00bea`, `ev_bfb341f7eb57e7f8481e05fc620e8c124810e3375c23b4ab120d2105e87235b9`, `ev_abd3a05615a858cf21f0dd35b851685d3a502bd2028e26ae52f0d25acf9c701e`, incoming references `ev_22dfcd2a11f1a5e427db4529ace3daded08043feb78374b3e5262a6b783ad42c`.

When `firstword` matches `proceduretype`, the parser reads its value. A nonempty value deletes any previous controller in Basic `+0x38`, clears the field, and compares against exactly five literals in the installed function body: `life`, `perlin`, `arturo`, `wave`, `cycle`. The literal bytes begin at `0x140d90ec8`; REA byte evidence `ev_6266dad045cbdbd8b476e8584980324569c2a4389cd26fce771a04c24b3b4c68`. A matching allocation can still fail, leaving a null field. An unrecognized nonempty value also leaves the field null. The five comparisons and stores are in `CAurTextureBasic::ParseField` `0x1400ecf20`, REA `ev_924661ecc6d7b28be1b098044f9e71e1c2b158997e4fd196a17c46d0c7a7ba28`.

After texture and font field handling, the parser reads Basic `+0x38` and, if nonnull, calls controller vtable `+0x18=ParseField` at `0x1400ed4d4`. Original vtable bytes resolve the five parser-selected targets to Life `0x1400e3d40`, Perlin `0x1400e3d30`, Arturo `0x1400e3c70`, Wave `0x1400e4470`, and CycleTID `0x1400e3ce0`. The specific controller receives every parsed line after installation; its own field recognition remains subtype-specific. The stored controller later reaches `Init` through `BuildAndStoreTexture` vslot `+0x10` at `0x1400eab2f` only under its image-mode/build gates; [build initialization](texture-controller-build-init.md) records those targets. Draw-time `CAurTexture::BindInUnit` conditionally tail-jumps through vslot `+0x8=Control` at `0x1400ea543` after TID binding, as traced in [controller runtime](texture-controller-runtime.md). Basic destruction invokes vslot zero at `0x1400e5261`, followed by the subtype and shared state release in [controller lifetime](texture-controller-lifetime.md). These are actual invocation sites, but each requires a nonnull controller and its respective state gate.

For a representative publication chain, Life `Init` `0x1400e3630` allocates image state at `0x1400e36b3`, seeds through CRT per-thread random at `0x1400e3722`, and copies pixels into Basic and controller images; REA `ev_948fd10c2f7fb9096c0625958fd2ffd4547e6727bdfd9528f657eb64b7e35452`. A later admitted Life `Control` `0x1400e1520` updates a temporary cellular image when enabled and at least five `texcurrentframe` ticks have passed, then invokes Basic virtual `+0xe8=CAurTexture::glImage` at `0x1400e1848`; the latter reaches `CAurTextureBasic::glImageBasic` and conditional GL upload. Life `Control` calls Basic `+0xf0=FreeImage` at `0x1400e1855` and frees its temporary output. Life's deleting destructor `0x1400e56b0` frees its `+0x58` state at `0x1400e56cd`, calls shared `TextureController::~TextureController` at `0x1400e56d5`, then conditionally sized-deletes the object. **Compiled-only boundary:** `WaterTextureController::WaterTextureController` `0x1400e08b0` writes vtable `0x140d90510` at `0x1400e08fd` (REA `ev_378085bca23a2e0ff65192783ff9d1307a47b3b270dcbfa4374918a2d7cb6dbc`). Its table contains `ParseField`, `Init`, `Control` and deleting-destructor targets, but the five-selector parser has no `water` comparison or constructor call. Incoming-reference analysis found only unwind/data references to `0x1400e08b0`, no direct code caller (REA `ev_fc36d7b32f6a039932cea82f2ef8721046b03a88a5034132537fbe3b47bdd184`). This does not rule out an indirect/external producer; it does **not** establish that a `.txi` `water` value can install Water in this binary. The existing Water body maps remain valid conditional compiled-code branches, separate from the proven parser-reachable five.

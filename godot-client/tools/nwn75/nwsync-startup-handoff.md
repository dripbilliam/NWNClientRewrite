# NWN-75: original NWSync startup and resource-demand handoff

Scope: pinned installed `nwmain.exe`, SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This branch explains when the original resource manager starts its NWSync worker and how a later manifest resource demand can wait for it. It is a static call and ownership map, not a measured wait duration or a claim that every frame demands a manifest resource. [Exact edges](nwsync-startup-handoff-ledger.json) are separate from the [manifest byte lookup](manifest-resource-lookup.md).

Client inner-runtime initialization `0x1406e3c80` constructs `CExoResMan` at `0x1406e3eaf`; server `CServerExoAppInternal::StartServices` `0x14056c950` also constructs one at `0x14056cb33` when client/server mode is 2. The resource-manager constructor `0x14018d6f0` creates its embedded `NWSync::CNWSync` at `+0x60` at callsite `0x14018d768`. `CNWSync::CNWSync` `0x1401b0810` clears its internal pointer and ready byte, then calls helper `0x1401b04a0`. That helper creates a thread through `_Thrd_start` at `0x1401b0597`, waits for the launch pad to signal startup, and installs the thread handle at `CNWSync+0x10`. The previously mapped launch-pad vtable `0x140da8118` enters worker `0x1401b0f00`. Evidence: client init `ev_34cff70119652b759670aa44d6fca8883543bd8c6dd10f7ed8a79b604f0b94b5`, server init `ev_d6ff51f4b3c50e3818ecbeee1a6f5c44b2f2db00e71309323bf925d0cf594c00`, manager constructor `ev_c2521bc2348d3fe6b1b6695901831663ab4651b44fd96ca8d7358bd17af313b7`, CNWSync constructor `ev_850c7940e5b485ea907098bded83840949fccfaad24b23803083b3f398514f66`, launch helper `ev_64e301f99b6151ce48da7d215d132ca38f8acfef6e89873692512ac4e1f8acc1`, launch pad `ev_5340fc411a5cd38f11c8ab91318ad77fa2fb4c08058d5560d490a65f766fea98`.

The worker `0x1401b0f00` constructs `CNWSyncInternal` `0x1401ba420` and publishes its pointer to `CNWSync+0`, then sets the ready byte at `+8`. Internal construction opens or allocates a platform storage shard via `0x1401d0cf0`, creates a `SQLiteStorageProvider`, runs `SetupExistingShards` `0x1401c5240`, and installs that provider at `CNWSyncInternal+0x20`. `OpenOrAllocateStorageShard` checks candidate files with imported `GetFileAttributesA` and may allocate a new shard; `SetupExistingShards` enumerates stored shards and prepares SQLite statements. The [shard discovery and hash-index continuation](nwsync-shard-discovery-and-hash-index.md) follows file/path probes, conditional migrations, metadata reconciliation and resident SHA1 set publication. The provider installation is the constructor-backed basis for the `+0x28=Fetch` target in [manifest resource lookup](manifest-resource-lookup.md). Evidence: worker `ev_195def23e3fcec9908a9f7bdf9dddf366caf6ede1c442452359c85b0a3fd61a4`, internal constructor `ev_6a626a45a04de9867ec43eca6d049942a17e256e68379432a6c1d8049f0ecf6b`, shard allocation `ev_dfbdc2ff31cc2eeca9d239682393cb6523e03ae79953ee3756a325bc7f758b00`, setup retained `ev_ec340d766cd4825a0e8c8b39502df5181be13b04364262c723603a0dd534f44c`.

A class-5 resource demand reaches `CNWSync::GetResrefData` `0x1401b1860`. It first calls `EnsureReady` at `0x1401b188a`, then the internal lookup at `0x1401b18a6`. `EnsureReady` reads the ready byte. If it is clear, it calls `std::thread::join` at `0x1401b14a0`; that wrapper reaches CRT `_Thrd_join` at `0x1401b495a`. `_Thrd_join` calls imported `KERNEL32.DLL::WaitForSingleObjectEx` at `0x140be6849` with infinite timeout, then gets the exit code and closes the handle if successful. If the ready byte is already set, `EnsureReady` returns without the join. This is a concrete **possible synchronous worker-completion wait** on the resource-demand caller thread; its frequency and duration are unknown. Evidence: wrapper `ev_0220b12eaa9ddcffe8f40551c28404469933188aa0ebb6fa5c756bbe6c43c385`, readiness `ev_7ff28da6e9ef4710794c9d1997496ae947088e177deadeca7cc086c08a7f261b`, thread join `ev_9faf880d54cfc083dea56a33e4cbea6fffef7d3e6c3d64b9c105e2a4c44791b4`, CRT join `ev_351f7caa478dece4185a9ca4d6ea3766b8f461e496f55fcbd3568f458bf2380e`.

Open: runtime shard/database and migration-definition choices, deeper SQLite/VFS modes, active class-5 selection, and whether an actual rendered frame first accesses NWSync before the ready byte is set. Static code shows the possible wait, not an observed stall. The [original thread ownership](original-thread-ownership.md) distinguishes this worker from the frame's synchronous Scene/GL path.

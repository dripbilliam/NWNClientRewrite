# NWN-75 server resource-override and refresh branch

Pinned installed `nwmain.exe` SHA-256 `3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`. This traces a connected server-message route that can change later material/texture resource selection or trigger asset refresh. It is conditional packet work, not an ordinary frame draw or a measured cost.

The connected server-message dispatcher `0x1407a41a0` calls `0x1407ab2f0` at `0x1407a4a96` for major **`0x34`** after message existence, read-buffer and connected-client checks. Minor **1** reads an action byte, type and source resref. Action `S` reads a replacement resref, checks message overflow, then calls `CExoResMan::AddOverride` `0x14018e8e0`; action `C` checks overflow and calls `RemoveOverride` `0x140191a50`. Type `0x7d1` fans the same source/replacement pair out over resource types 3, `0x7f1`, `0x819`, 6, 1, `0x818` and `0x7e6`, followed by `SharedMaterial::RefreshSharedMaterial` `0x140085020` and `AurResetTexture` `0x1400e5f30`. Other types use a single override map operation without those two refresh calls. `AddOverride`/`RemoveOverride` key the map with lowercase `resref.extension`, as used by [key selection](resource-key-selection-object-ownership.md); the map changes future `GetKeyEntry` lookups, while the following refreshes affect already cached objects. An optional GUI owner can also receive `0x14085fda0` to replace matching icon references; it conditionally constructs a new `CGuiIcon` and calls virtual model/GUI methods, whose active targets remain dynamic. `SharedMaterial::RefreshSharedMaterial` searches its shared-material registry. If no shared entry is found, it may obtain one and refresh matching unshared `Material` records; if one is found, an active dependent count can defer refresh. Otherwise it removes that shared entry, clears and reinitializes referenced materials' textures, then destroys the old shared material. `Material::InitializeTextures` resolves names into texture references as mapped in [model instance material loading](model-instance-branch.md); this refresh body does not itself submit GL. REA `ev_4fdf4d530283817d81a322a6962d6844e9e2e0f3efe20433d1b09b86accf94d3`.

`AurResetTexture` scans `_m_OrderedTextureList` for the named Basic texture. A miss returns. On a match it invokes virtual `+0xf0` (the constructor-backed Basic candidate is `CAurTextureBasic::FreeImage`), resets build flags and, when GL texture IDs exist, calls `RenderInterface::DeleteTextures` `0x1400be9b0`. That direct tail thunk reaches `GLRender::DeleteTextures` `0x1400afe20`, which clears bound-texture caches and jumps through the imported `glDeleteTextures` cell at `0x1400b0018`. The reset then conditionally calls `CAurTextureBasic::BuildAndStoreTexture` `0x1400ea5e0` and `AurTextureBuildAndStoreAll` `0x1400e6910`. The latter processes its pending `_RefreshTextures` queue, sorts the static texture list and reconstructs ordering/ID arrays only when pending work exists; image demand, decode and upload descendants are already mapped in [texture acquisition](texture-acquisition.md) and [per-frame publication](texture-publication-per-frame.md). This is an explicit matched-name re-publication route with a GL deletion boundary, not a claim that every texture rebuilds.

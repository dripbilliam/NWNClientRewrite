## Bucket item dispatch

### Population before drawing

With a BSP present, `Scene::Render` first calls `ManageSceneBSP` `0x1400db320` (REA `ev_3e8c9791`). That function checks Scene BSP pointer `+0x188`, updates moving/static Part placement through `SceneBSPUpdatePart`, refreshes/reallocates mesh and fade bucket arrays when needed, traverses/approximates visibility from `CurrentCamera`, processes active bins, and runs fading-in/out bucket handlers. It calls `DoStaticLightBuckets` only in the non-full-dynamic-lighting branch and uses `BSPFitSphere`, `BSPSearch`, `BSPTraverse` and `BSPTraverseVolumeApprox` for placement/visibility. This produces cached bucket inputs consumed below. All ten computed call targets are identified below; BSP callback and helper descendants remain open.

`ManageSceneBSP` passes callback `0x1400dc140` to `BSPTraverseVolumeApprox` (REA `ev_45e32deb`). For each visited BSP node it adds present triangle meshes to texture-keyed mesh buckets, tests Gobs against camera planes before setting their visibility and LOD model, tests emitter bounding spheres before placing them in the emitter bucket, advances a node fade value, conditionally processes triangle meshes, and plane-culls shadow projections, triggers, beams and triangle bins into their respective buckets. The five computed sites in this callback are `0x1400dc203` Gob `+0x2e0=GetAdjustedOrientation` `0x14008e200`, `0x1400dc232` Gob `+0x2d8=GetAdjustedPosition` `0x14008e2c0`, `0x1400dc269` Gob `+0x2d0=GetAdjustedScale` `0x14008e390`, `0x1400dc2bd` Gob `+0x2a8=EnableInViewVolume` `0x14008de10`, and `0x1400dc3b5` emitter Part `+0x18=GetWorld` `0x14008f870`. Gob vtable `0x140d88a00`, base Part `0x140d87f08` and emitter Part `0x140d84400` match those slot targets; `PartEmitter::PartEmitter` `0x140060420` installs the emitter vtable (REA `ev_79437732`). The bucket and mesh processing helpers remain to traverse.

`BSPTraverseVolumeApprox` `0x140229dc0` invokes its callback on every visited node, then splits the plane list and recurses while its node/plane tests allow (REA `ev_efc35458`); `ManageSceneBSP` supplies `0x1400dc140` at `0x1400dba64`. Under `GrassIsEnabled && HasBins`, `BSPTraverse` `0x140229b70` invokes a second callback at each visited node and follows children according to signed plane distance and the far-radius threshold (REA `ev_9354d37b`); `ManageSceneBSP` supplies `CollectBins` `0x1400d87a0` at `0x1400dbaa5`. `CollectBins` (REA `ev_35648900`) adds each node triangle bin whose squared camera distance is below the far-radius-squared input to `g_pActiveBins` and advances `countactivebins`.

After that traversal `AurProcessActiveBins` `0x1400d7ce0` runs at `0x1400dbac0` (REA `ev_27021057`). It calls `CAurTriangleBin::BuildGrassPolys` `0x14006c910` for each active bin and `DestroyGrassPolys` `0x14006d7f0` for each formerly active bin absent from the new list. `BuildGrassPolys` only creates a list's vertex-data item when it has grass blades and no existing item; it calls `CAurTriangleList::CreateTriangleGrass` `0x14006cd70` per triangle with a positive grass count, then commits static and dynamic item data (REA `ev_a5c660b5`). `CreateTriangleGrass` seeds the original RNG from triangle coordinates, samples barycentric positions and orientations, optionally interpolates the source pool color, and writes six vertices per blade (REA `ev_90b6a076`). `DestroyGrassPolys` removes a previously created vertex-data item and clears the reference (REA `ev_e1bd0fe4`).

Those commits call `VertexDataObject::CommitItemStaticData` `0x1400bd5a0` or `CommitItemDynamicData` `0x1400bd540`, each of which calls `RenderInterface::UnlockPool` `0x1400bf3d0` → buffer implementation `0x1400bbaf0` (REA `ev_4818169a`, `ev_fa2f64ab`, `ev_0110ad9e`, `ev_e83d601a`). Depending on pool state, that implementation creates a buffer, binds it, allocates/orphans its storage, or uploads a range through extension pointers `0x141442470=glGenBuffers`, `0x141442440=glBindBuffer`, `0x141442448=glBufferData`, `0x141442450=glBufferSubData`. The original `wglGetProcAddress` loader `0x140b7a0f0` names all four (REA `ev_5da73fb2`). The grass draw path is separate in `scene-auxiliary-passes.md`.

When `g_bFullDynamicLighting` changes, `Scene::Render` walks the BSP twice through the callback-taking `BSPTraverse` overload `0x140229c60` (REA `ev_201d7eba`): at `0x1400ccce2` it supplies `LightNodeMeshes` `0x1400da420`, and at `0x1400cccf8` it supplies `LightBins` `0x1400da3d0`. That traversal invokes the callback on each node and recursively visits both child links. `LightNodeMeshes` gathers nearby lights for each node triangle mesh and calls `LightPartTriMesh` `0x1400da970`; `LightBins` calls `CAurTriangleBin::ReloadColor` `0x14006d950` for each node bin (REA `ev_c89f051f`, `ev_7d044305`). `ReloadColor` removes existing grass vertex items and calls `CAurTriangleList::BuildGrassPolys` on affected lists (REA `ev_0c8b2a5c`). Thus the lighting-mode switch can rebuild both mesh color buffers and grass data; the gate is a change in lighting mode, not each ordinary frame.

`LightPartTriMesh` `0x1400da970` checks mesh data and render hint. In non-full-dynamic mode it requests or resizes a vertex-color pool and, for render hints 2/3, an optional bump-direction pool, then marks the vertex primitive for rebuild. It obtains the Part world pose through virtual `+0x18=Part::GetWorld` `0x14008f870` at `0x1400dab41`, locks source position/normal and output color/bump pools, and runs a nested loop over each source vertex and each selected PartLight. For eligible lights it computes distance, attenuation and orientation, accumulates and clamps RGB, and, when the bump pool is active, normalizes a weighted direction. It writes packed vertex color and optional bump direction, unlocks the four pool slots, and invokes primitive virtual `+0x40=VertexPrimitive::ResetBlock` `0x1400abc90` at `0x1400db2ea`; the pinned Base/Flat/Skinned/Anim/Dangly primitive vtables all have that same empty target. The source position/normal locks use mode 8 and their releases stop before GL buffer calls; color and optional bump locks use mode 1, so their releases can publish buffers under later pool-state gates. The exact four sites and helper gate are in [mesh relighting pool publication](lightpart-pool-publication.md). In full-dynamic mode it deletes existing color/bump pools only when its prior-color flag is set and marks the primitive for rebuild. This is CPU mesh relighting and conditional output-buffer publication, gated by queued/static-light callers or lighting-mode change; the function itself has no direct GL draw. All 28 immediate direct/virtual callsites are recorded in the ledger. Full REA `ev_cb426a7c87fdacdfa7c64ec288930463d36e55b83636183481abe6081bb40606`.

There is also a queued static-light path during `ManageSceneBSP` in non-full-dynamic mode. `DoStaticLightBuckets` `0x1400d9330` (REA `ev_fda76727`) processes each queued BSP node through `LightNodeTile` `0x1400da6c0`; if any were queued, it traverses the scene BSP with the `LightBins` callback above, then clears the queue count. `LightNodeTile` (REA `ev_038925bf`) visits the node tile's Part list, uses virtual Part `+0x58=AsPartTriMesh` at `0x1400da75d`, gathers nearby lights for accepted TriMesh Parts, and calls the same `LightPartTriMesh` color/update path. `Scene::AddPartsTreeToDrawBuckets` `0x1400c4620` (REA `ev_72453337`) first rejects invisible Parts, pushes their local transform and scale, then recursively visits children in stored order and restores matrix and inherited light color. The dynamic Part classification is now explicit. Without a material, `PartTriMesh::GetIsOpaque` selects bucket `2` for opaque or `3` for translucent. With a material, bumpy/shiny plus `g_nEnableBumpyWater`, or `SharedMaterial.sample_framebuffer==2`, selects bucket `6`; otherwise material blending mode `2` selects additive bucket `4`; `sample_framebuffer==1` selects bucket `5`; otherwise `SharedMaterial.volumetric` selects bucket `5` **and** additionally submits the same Part to bucket `3` with item flag `2`. The remaining ordinary material case selects opaque `2` or translucent `3`. `SharedMaterial.twosided` sets item flag `1` on the main submission only when `volumetric` is false; otherwise it is `0`. The extra volumetric submission is a deliberate two-bucket path, not an inferred duplicate. The three `AddPartToBucket` sites are `0x1400c47a6` (volumetric extra), `0x1400c4801` (main), and `0x1400c4879` (shadow). REA `ev_7245333797a415fdd94c9cdf1b7512702927288fe071bae83702abdb27046e35`.

The supplied shadow-bucket index is honored when it is not `-1` and the material is neither bumpy/shiny nor `sample_framebuffer==2`; no material also passes that gate. ## Primitive and external draw boundary

The vertex/skin setup paths can request a render pool through `RenderInterface::RequestPool` `0x1400beee0`. It tail-jumps to `GLRender::RequestPool` `0x1400b5dc0`, which calls pool allocator `0x1400b5de0` against global descriptor state `0x14128ead8`. A zero-byte request returns sentinel `0xffffffff`; a nonzero request increments memory accounting, reuses a free descriptor when available, or grows the descriptor/free-index arrays, and allocates the requested CPU backing bytes. Growth reaches CRT `calloc`, `realloc`, memory copy and free; each nonzero request reaches CRT `malloc`. This body does not directly allocate a GL object or upload a GPU buffer. Those actions occur later through the documented pool unlock and vertex-object publication path. REA wrapper `ev_856f92cd024fca2431150bc957bdfc29a184b413ab62d9bb1f2185fb91f4b2a6`, GL entry `ev_bd5fccbdcab8e6e0993c519e7f8ae48b2c0cfe26cdcab829e01106b0d38ecdb4`, allocator `ev_bc984713bb00bcb4021643fd388323c61545a664327e1ddad1f465d8f506458d`.

`RenderInterface::ResizePool` `0x1400bef00` similarly tail-jumps to `GLRender::ResizePool` `0x1400b64a0`. For a valid pool ID it allocates new CPU backing bytes, copies the old byte count, frees the old allocation, updates memory accounting and marks descriptor byte `+0x18` zero. It makes no immediate GL call. REA wrapper `ev_3dd5912fc8944a4be868cf7ff8a7cb2f4b420a54ef4a457170d1a3f4fc3dcca7`, GL body `ev_9d28538c3052190bdbc60fe9a7fbad5c26960e5a70950329809b212ab5e9b4df`.

The high-fan-in `BSPFitSphere` `0x140229690` is an iterative CPU node-selector: it evaluates a center against each BSP plane, stops at a straddling node or leaf, and has no callees or GL work. It is a bounded terminal descendant for placement and visibility preparation, not a second rendering pass. Full REA `ev_e2ba6c92fbcf634cb43b73ab1adfc203942898a75a099e65bfcc1d2776a7e7b6`.

`PartTriMesh::Draw`, `PartAnimMesh::Draw`, and `PartDanglyMesh::Draw` test visibility/mesh/material data. A bumpy-shiny material with `g_nEnableBumpyWater` selects `RenderBumpyShiny` `0x1400a4560`, which selects a custom shader and calls `RenderFlat`. Otherwise an environment map may select `RenderEnvironmentMapped` `0x1400a45c0`, which also calls `RenderFlat`; the plain branch calls `RenderFlat` `0x1400a4710` directly. Evidence: REA `ev_9cb03728`, `ev_af0dc0ec`, `ev_6edb2032`, `ev_eef624b1`, `ev_ce56d943`, `ev_f31ed1c5`.

`RenderFlat` checks that a vertex-data object exists, obtains render hint and mesh primitive type, handles depth, alpha and lighting flags, then sends element offset/size to `RenderInterface::RenderVertexData` `0x1400beec0` (REA `ev_fd1063f9`). That function chooses a GL shader variant from vertex attributes and enabled states, sets the current vertex object and program, then reaches:

* indexed modes 1 and 2: function pointer `DAT_1414431f8`, loaded by `wglGetProcAddress("glDrawElementsBaseVertex")` in `FUN_140b6e8b0` at `0x140b6e8b0` (REA `ev_62301279`);
* nonindexed mode: imported `glDrawArrays`.

`RenderInterface::RenderVertexStreamData` `0x1400beed0` (REA `ev_9682f759`) similarly chooses a shader/program and reaches imported `glDrawArrays` or `glDrawElements` according to stream index data. These are external graphics API boundaries; GL driver execution lies outside this binary.

Before these draw calls, `GLRender::SetVertexDataObject` `0x1400ba770` (REA `ev_75d97b3e`) and `GLRender::SetVertexStreamDataObject` `0x1400bacc0` (REA `ev_bae9b5bf`) avoid reselecting the current object, bind/create a VAO as needed, bind buffer objects, and set enabled attributes from object flags. Their function pointers are loaded through `wglGetProcAddress`: `DAT_141443f48=glBindVertexArray`, `DAT_141443f58=glGenVertexArrays` in `FUN_140b70e00` (REA `ev_725805f9`); `DAT_141442440=glBindBuffer` in `FUN_140b7a0f0` (REA `ev_d89e70c9`); `DAT_1414427b0=glVertexAttribPointer` in `FUN_140b7a350` (REA `ev_bffd0435`). `GLRender::SetProgram` `0x1400b7a40` (REA `ev_c2fa9ed1`) conditionally binds a custom or selected built-in shader program using `DAT_141442680=glUseProgram`, loaded in the same extension function. These establish additional external API boundaries for vertex state and program selection. The shader compile/uniform descendant tree remains open.

Material texture binding has another concrete API leaf. `Material::BindAllStandardTextures` `0x140082630` (REA `ev_fca11e33`) checks texture validity, material slots and controller state, then binds standard textures through CAurTexture virtual `+0x100=CAurTexture::BindInUnit` `0x1400ea490` (`CAurTexture::vftable` `0x140d90c70`, constructor `0x1400e4cc0`, REA `ev_305d2861`). `CAurTexture::BindInUnit` calls `AurTextureBindTIDInUnit` `0x1400e6870` or `RenderInterface::SetActiveTextureAndBind` `0x1400befc0` (REA `ev_32be466f`, `ev_6606a9c2`, `ev_af59e6d9`). The latter caches enabled stages and bound texture IDs; on a changed stage it uses `DAT_141442150=glActiveTexture` loaded by `wglGetProcAddress` in `FUN_140b79580` (REA `ev_a2f09667`), then calls imported `glBindTexture` for 2D or cube-map target. This branch reaches external API calls but texture upload and shader uniform descendants remain open.

The separate `RenderInterface::BindTexture` `0x1400be8c0` is a tail jump to `GLRender::BindTexture` `0x1400ada30`. A zero texture ID clears the active stage's enabled bit and returns. A nonzero ID sets that bit; for stages below 16 it compares the requested target and ID against the cached pair, calling imported `OPENGL32.DLL::glBindTexture` only when they differ. Target value `4` binds `GL_TEXTURE_2D` (`0x0de1`) at `0x1400ada94`; value `0xe` binds `GL_TEXTURE_CUBE_MAP` (`0x8513`) at `0x1400adabd`. Other values do not call GL in this body. It then records the changed target and ID in `m_boundTextures`. This is a render-state cache/API boundary, not evidence that every caller performs a driver call. REA wrapper `ev_ae976f4dc2b0d00c1ca2e837ff3b54aa2b07f4b498f5789de27cf367e742ac67`, GL body `ev_7cb118461bd9bd2be2454d7c355d43b0de1b10e77bc2bf3a4a01de2a3656948b`.

`PartSkin::Draw` enters `RenderSkinned` `0x1400e0410` and `ExecuteSkinGPU` `0x1400deb90` (REA `ev_6171b2e1`), which gathers bone transforms and calls `RenderInterface::SetBoneMatrix` for valid bone slots, enables skinning and then chooses flat or environment mapped primitive draw. This is a shader/GPU skin path, but its input bone-gather and state branches still need a full ledger. No runtime frequency or thread ownership is inferred here.

## Skybox geometry route

`Scene::RenderSkyBoxes` `0x1400d28f0` (REA `ev_42236e46`) skips the sky geometry block when scene byte `+0x4c` equals 1. Otherwise it sets a depth-free projection using current camera FOV and screen ratio, then conditionally renders up to three sky Gobs: the first indexed Gob when Scene `+0x44` is valid, a second when the blend fraction at `+0x40` is positive and Scene `+0x48` is valid, and a separate Gob at Scene `+0x38` when nonnull. The indexed pair receive blend alpha `1-fraction` and `fraction`; each object receives position through virtual slot `+0xb0` and is rendered through `+0x20`. `Gob::Gob` `0x1400869d0` references `Gob::vftable` `0x140d88a00`; original PE slots `+0xb0=Gob::SetPosition` `0x140095210`, `+0x20=Gob::Render` `0x1400a4280` (REA `ev_4b850bfe`, `ev_741ec2c2`).

`Gob::Render` `0x1400a4280` calls `Gob::ProcessGob`, applies transforms/fog state and enters `Gob::PartDraw` `0x1400a3440` (REA `ev_d98db872`, `ev_26045c9f`). `PartDraw` recursively traverses visible Part children in their stored order; each node's virtual `+0x58` supplies a TriMesh view and virtual `+0xc8` performs the subclass Draw operation above. This connects the skybox branch to the same primitive/external GL boundaries, subject to the actual sky Gob's Part types. When the Gob has an active fade value below one, `Gob::Render` temporarily enables and changes Scene fog around `PartDraw`; otherwise it draws directly. Its optional `param_1` sends a `propagaterender` event after draw.

All nine computed sites in `Gob::Render` resolve from the original Gob, behavior and Part vtables. `0x1400a42f5` and `0x1400a430f` call Gob `+0x298=DoEvent` `0x140050d50` for debug personal radius/path requests. `0x1400a4325`, `0x1400a4340`, `0x1400a435a` call Gob `+0x2e0=GetAdjustedOrientation` `0x14008e200`, `+0x2d8=GetAdjustedPosition` `0x14008e2c0`, `+0x2d0=GetAdjustedScale` `0x14008e390`. Attachment ancestry calls `0x1400a4373` behavior `+0x30=AsBehaviorAttach` (base `0x140054a60`, attach override `0x140054a70`), `0x1400a4382` attached Part `+0x30=GetAurObject` `0x140061af0`, then `0x1400a4393` parent Gob `+0xe0=GetVisualTransformData` `0x14008f860`; its LerpFloat scales the child Gob. `0x1400a4545` calls Gob `+0x298=DoEvent` for `propagaterender` when requested. These are the same original attachment and pose targets observed in `AddPartsToDrawBuckets`; event callback targets remain open.

## Scene without BSP

When `Scene::Render` takes its no-BSP branch, Scene virtual `+0x270` calls `Scene::RenderOnlyGobs` `0x1400cf9b0` (REA `ev_82cf91e9`). It sets color/depth state, checks for the named GUI model-view or compass scenes, and loops the Scene Gob array at `+0x130/+0x138`. The GUI-scene branch obtains nearest lights for each Gob before rendering; both branches call Gob virtual `+0x20=Gob::Render` `0x1400a4280` at Ghidra-unresolved callsites `0x1400cfb50` and `0x1400cfbdf`. This joins the same recursive Part Draw and OpenGL geometry path. The two callsite targets are derived from the constructor-backed Gob vtable, not from REA's static call reference alone.

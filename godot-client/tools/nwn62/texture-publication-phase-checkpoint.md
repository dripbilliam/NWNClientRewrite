# NWN-62: texture publication phase checkpoint (2026-11-12)

The private diagnostic source is `.cache/nwn62/texture-phase-probe-a/resource_pool.gd` (SHA-256 `9784edd1596bdd1ec1230ac7844643b4ee509b095b46592ffef4013b10218e8a`). It differs from the accepted `systems/native_render/resource_pool.gd` (SHA-256 `cb702ea11b45251078de8fa1b8cfd16a486f2dac030aabdd750a33a21e1f39b2`) only by timing and cache-key counters around texture misses. The staged original-scene selection in `.cache/nwn62/texture-phase-diagnostic-a/staged.json` pins the same accepted Core E engine and generation-2 recording, and confirms `resource_pool.gd` is the only changed production-source identity. `tools/nwn62/prepare-texture-phase-probe.cjs` and `stage-texture-phase-diagnostic.cjs` reproduce the private stage. The overlay passed an isolated Godot `--check-only` parse using `stage-texture-phase-parse.cjs`; the normal client source and executable were not modified.

The no-FPS diagnostic replay wrote `reports/nwn62-texture-phase-a.json` (SHA-256 `0732cfd6d83717106b62eabb733af7e8a943a6bcedb68c030fbb24719df15e6f`). Source and runtime remained pinned; 1,918 entities were installed and all 1,784 known base objects resolved with zero pending or failed objects. The driver returned `success=false` only under its ordinary engine/lifetime diagnostic policy: the engine log contains the known shader-cache-folder and root-certificate errors. This is useful phase evidence, not a clean acceptance run or an FPS comparison.

The pool created 625 textures, had 453 cache hits and evicted 113 bindings with a 512-entry binding limit. All 625 texture misses had **distinct SHA-256 keys**; the probe saw **zero creations after a prior eviction**. Raising that cache limit would not avoid a texture creation in this recorded scene. CPU raster pre-preparation was off. Of 25 misses over the probe's 0.5 ms reporting threshold, the maximum took **12.238 ms**: 0.003 ms validation, 0.020 ms Image preparation, **12.199 ms `ImageTexture.create_from_image`**, and 0.016 ms retention. That miss was a 64×128 RGBA8 image with one mip. The next largest recorded miss was 1.300 ms (1.253 ms in texture creation); typical larger 512×512 RGBA8 misses spent roughly 0.6–0.7 ms preparing the Image and 0.06–0.12 ms creating the texture. These values are for this one diagnostic replay, not a stable distribution.

In the separate live candidate Tracy export, the actual `prepare_texture` function zone (line 325) had 2,527 calls, 84 above 1 ms and two above 10 ms, with maxima 23.191 and 17.911 ms. The exporter also emits the caller-site zone at line 322 for each call; adding both doubles the count. That live trace did not split Image preparation from texture creation, so this offline run identifies a plausible expensive subphase but does **not** prove the two live stalls had the same subcall or asset.

The pinned Godot source shows `ImageTexture::create_from_image` calling `set_image`, which calls `RenderingServer::texture_2d_create`. Forward+ uses `RendererCompositorRD::can_create_resources_async() == true`; `RenderingServerDefault` therefore initializes this texture on the calling thread rather than pushing it to its command queue. `TextureStorage::texture_2d_initialize` validates the image and calls `RD::texture_create`. The 12.199 ms observation lies inside this chain; it is not yet attributed to validation, RID allocation, RD creation or a synchronization wait. The source makes worker-side texture creation a candidate to test, but does not alone prove `ImageTexture` resource construction and publication are safe across all lifecycle paths.

**Next gate:** use a private Forward+ worker-created texture fixture with readback and main-thread material publication, then a source-pinned candidate that prepares only eligible immutable textures off the main thread. Check cancellation, cache ownership, renderer/thread mode, visual output, loading latency and frame tails before considering promotion. Do not enlarge the cache or enable the existing CPU-only raster preparation based on this capture alone; neither addresses the measured 12.199 ms creation call. NWN-62 remains In Progress.

## Private worker creation preflight

`tools/nwn62/texture_worker_probe.gd` was staged alone as `.cache/nwn62/texture-worker-fixture-b/` (source SHA-256 `8e610db737ae3f1451cd03322dd89d95327eac6811fc3a2e9e7ffc5c572ea2ac`). A headless run reported no `RenderingDevice`, so it was **not** accepted as a Forward+ test. The graphical Vulkan/Forward+ run on the accepted Core E binary used the NVIDIA GeForce RTX 5070 Ti. A worker with thread ID 55 created a 64×128 RGBA8 `ImageTexture` while the main thread was ID 1; the returned RID and dimensions were valid and main-thread GPU readback bytes exactly matched the source Image. Worker creation itself took 40 µs in this small fixture. The process printed known user-cache/root-certificate environment diagnostics; the fixture result reported `success=true` and the process exited 0. This proves one cross-thread create/readback path works on this renderer, **not** concurrent uploads, cancellation, scene publication or performance. The private candidate must still cover those behaviors.

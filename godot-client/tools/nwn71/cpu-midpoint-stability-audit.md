# NWN-71 CPU midpoint shutdown audit

Status: source and saved-artifact review only. The option remains default-off. No production edit, GPU run, FPS comparison or claim that the crash is fixed.

## Frozen failure

The initial 256×256 Vulkan fixture receipt `.cache/nwn71/cpu-midpoint-a/fixture-runs/receipt.json` records OFF exit 0 and ON exit 3221225477 (`0xC0000005`). The ON report had already marked success, showed 14 gamma passes and one CPU midpoint upload, and saved a PNG byte-identical to OFF (`c460a180...`). The report was written **before** `effect.close(); world.free(); await process_frame; quit()`, so it proves neither those close operations nor process shutdown completed safely. ON stdout/engine log contain no stack, dump, GDScript error or RenderingDevice error. Stderr contains only the common separate-render-thread experimental warning and root-certificate warning. No crash dump is preserved in the fixture tree. Therefore the exception is located only to post-report teardown/shutdown, not to a specific RID or line.

The later six-run OFF/ON/ON/OFF/OFF/ON fixture sequence used fresh user-data folders and all exited 0 with identical pixels. Its source pin is gamma `8e60a4c3...`; the failing run used `63bcee2a...`. The archived file diff changes `set_postprocess` and `publish_postprocess_frame` to avoid an extra lock cycle on the **default OFF** path. For CPU midpoint ON, both versions calculate midpoint bytes and perform the same two lock windows in `publish_postprocess_frame`. The changed source is not a causal explanation for the one ON crash. Six clean repetitions narrow the observed failure rate but do not close stability acceptance.

## RID and render-thread ordering

`_render_callback`, optional `_prewarm_on_render_thread`, and `_release` execute on the render thread; the publishing thread only writes postprocess packets under `state_lock`. `close` sets `closed=true` before queuing `_release` with a bound self reference. Later callbacks return before RD use. `_release` frees per-view tone/image uniform bindings first, then gamma and tone pipelines/shaders, then optional midpoint binding/input/output RIDs. The CPU path allocates `midpoint_output` as a 16-byte storage buffer and binds it into the tone uniform set; the teardown frees that uniform set before the buffer. These source facts rule out an obvious concurrent script-level free during an active callback or a simple dependent-RID free-order inversion. They do **not** rule out commands still in flight on the GPU or a rendering-server shutdown race in the experimental separate-thread mode.

The fixture calls `effect.close()` immediately before freeing the world, waits one process frame and quits. `RenderingServer.call_on_render_thread` queues `_release`, but the saved artifact contains no callback completion marker, render-thread barrier or native stack. The precise relative completion of release, pending compute work and engine shutdown cannot be established retrospectively. A diagnostic run would need a completion marker and a native crash stack, plus repeated OFF/ON teardown under the same pinned source; that needs a new PC lease and should precede promotion. Until then, keep the CPU midpoint opt-in and do not attribute or dismiss the `0xC0000005`.

# NWN-61 entry menu split: access violation audit

The first valid graphical candidate replay (`reports/nwn61-menu-split-c-candidate-1.json`) exited with Windows code `3221225477` (`0xC0000005`). The report is a partial replay: timeline delivery and first-playable were false. The last accepted protocol message was generation 2, serial 48, at 4,981 ms. Area-ready had occurred at 4,345 ms, and the last world observation had resolved 55 of 1,784 known base instances. Thus the failure was during post-entry scenery streaming, after the first area and ACK, rather than during initial menu construction.

There is no native stack, minidump, shutdown report or relevant Windows Application Error 1000 event. The saved stderr contains the separate render-thread warning, shader-cache and certificate errors, and missing original resource warnings. The same diagnostic classes occur in the two completed controls and two completed candidate runs. The driver records a failed child process but no crashing module or instruction address.

The source audit covers only the changed menu path. The new owner tokens are checked before each step; completing or closing clears them. The page cannot build while setup requests are still being queued. The main menu wires modal ownership and prepared/finished signals before calling `finish_entry_configuration`. On cancellation it increments each asset service epoch, drops pending jobs and prevents stale completion callbacks; normal close joins running workers. The focused headless test in `.cache/nwn61/entry-menu-owner-split-c.json` passed 22/22 setup, request-order, signal and cancellation checks without a crash. This fixture uses fake missing assets and does not reproduce live scenery publication or GPU work.

**Classification: unattributed access violation.** The menu split changes request timing and therefore could affect a latent asynchronous lifetime defect, but the saved evidence does not identify a menu callback, a failing worker, or an engine stack. It cannot establish whether the candidate caused the crash. Both candidate and control staged artifacts remain intact. The candidate should remain unpromoted pending a bounded crash capture with a native stack or an otherwise reproducible source-level failure. No FPS result should be inferred from the failed leg.

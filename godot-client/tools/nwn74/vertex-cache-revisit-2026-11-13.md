# NWN-74 vertex-array cache revisit

The existing private Forward+ candidate (`.cache/nwn74/source-vertex-cache-i.cpp`, SHA-256 `05b7e8379000b331fbb26dedc9577b594eca7d09d7ea7872cbc54078b3837e74`) remains default-off and unmerged. Its 8,192-slot thread-local table is keyed by surface pointer, input mask, motion-vector flag and point-size flag, and expires each rasterizer frame. Dynamic mesh instances use the original lookup. A hit skips `MeshStorage::mesh_surface_get_vertex_arrays_and_format` and its surface lock/version scan. The dense-scene count receipt shows 206,760 hits per 120 frames, or 1,723 of 3,043 static lookups skipped per frame (56.6%). The matched small Vulkan fixture produced identical red/green pixel hashes with cache off/on.

The four-leg normal-client pair averaged 8.2541 ms OFF versus 8.2188 ms ON, a 0.0353 ms apparent improvement, but adjacent comparisons reversed direction. All four legs failed strict engine/lifetime diagnostic acceptance with matching fingerprints. The cache has no explicit invalidation if a static surface is destroyed and its pointer reused within one rasterizer frame. Static region updates keep buffer RIDs, but surface clear/remove can destroy cached vertex-array RIDs. The current evidence does not prove that such reuse cannot occur between passes.

Decision: retain the private candidate for a later lifecycle-specific gate. Do not merge it into accepted source or enable it by default from this review. No engine source, binary, FPS run or broad build was changed here. NWN-74 still needs a repeatable end-to-end render-thread reduction with strict acceptance.

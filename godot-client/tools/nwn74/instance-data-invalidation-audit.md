# NWN-74: Forward+ instance data reuse audit

Status: source-only assessment. No engine edit, build or FPS claim. Source is the private Tracy snapshot `render_forward_clustered.cpp` SHA-256 `FE8B102C6742D12F8A51A7312BFA8B72596277EE7D2F429FCE5C97D6E03846DD` and matching header SHA-256 `173DB11744B7CF8CFAC758D93D5F024B4275E38CCB662D3D4389845E3B0ACF0A`.

## Identity and invalidation

`_fill_instance_data` is called for opaque, motion, alpha and secondary lists, including each appended shadow pass. Its input is a `GeometryInstanceSurfaceDataCache *` and its owner. A surface cache retains a mesh `Surface *` until the geometry instance is marked dirty or freed. Mesh, material, particle and skeleton dependency notifications call `_mark_dirty`, which frees these surface caches before they can be rebuilt. Mesh clear/remove emits the mesh dependency notification. Vertex-region updates change buffer bytes but do not change the `Surface::format`, `aabb` or `uv_scale` metadata.

Only the mesh surface `format`, compressed `aabb` and `uv_scale` are invariant for this cache lifetime. They are read through three `_FORCE_INLINE_` getters that simply reinterpret the stored `Surface *` and return fields. A safe precomputation would store compressed AABB and UV data on the surface cache at `_geometry_instance_add_surface_with_material`, then copy them into each `InstanceData`. The format is already queried there for tangent validation. Surface-cache destruction supplies invalidation. It would add roughly 40–48 bytes per material/surface cache and still copy those bytes into the mapped instance buffer on every draw.

The whole 176-byte float-mode `InstanceData` is **not** invariant. `_fill_render_list` rewrites owner `flags_cache` for each pass; fade depends on that pass camera, and GI/lighting fields change with the visible lightmaps/probes. Motion processing can advance `prev_transform` or reset its status. Transform setters and lightmap changes also mutate its fields between frames. A cache keyed only by owner/surface or frame would emit stale flags, GI or motion data. Reuse of only the transposed transforms would require versioning all transform and previous-transform writes (including the motion-status update inside `_fill_render_list`) and a second 96-byte owner buffer in float mode. It still requires a full per-draw instance record copy and separate repeat/draw bookkeeping.

## Priority decision

The saved original-scene census has about 3,054 draws/frame across color, depth and shadow, versus 1,437 visible geometry owners. The **idealized** upper bound on avoided duplicate owner transform construction is roughly 1,600–1,700 pairs of 3x4 transposes/frame if every visible geometry owner appears at least once; actual reuse depends on multiple surfaces and shadow visibility. The surface metadata cache would avoid three trivial inline field loads per draw, not a mesh lookup or GPU upload. The current probe's 0.13 ms Forward+ list-fill counter measures `_fill_render_list`; it does **not** include `_fill_instance_data`, so it cannot bound this candidate's time. No dedicated `_fill_instance_data` timer exists. The prior vertex-array cache skipped 1,723 lookups/frame without a repeatable FPS gain. These observations do not justify another private build under the current PC lease. Keep this as a lower-priority, correctness-safe less-work opportunity; measure `_fill_instance_data` directly if a later trace indicates meaningful time, and pursue a larger measured draw-thread span or reduce actual draws under the separately scoped batching ticket.

# NWN-63 keyboard frame admission: current-source gate

The pinned original `nwmain.exe` (`3b7cb1252e0edb2ce22d7971f333aade027039ae30a45b4bc64732c3e6bec73a`) calls input coordinator `0x1406f14e0` at `0x1406db9f3`. Its `CExoInput::GetEvents` loop dispatches each queued event through `0x1406ed720`; after that loop the coordinator calls held-key tick `0x1406f1e40` at `0x1406f1ae7`. This is the retained read-only coordinator evidence in `.cache/nwn63/frame-admission-source-a/coordinator-evidence.json`. The static path establishes ordering, not physical OS repeat frequency or a live-server outcome.

The current client sets `nwn/private/keyboard_frame_admission` default true at both keyboard creation sites in `native_live_world.gd`. The owner calls `flush_input_frame()` once after protocol receive and before output. `systems/native_keyboard.gd` admits OS `_input` events into held state, coalesces dirty events at the owner boundary, and retains the 250 ms preview and 500 ms drive refresh rules. Public `key()` and `update_input()` remain synchronous. Release, focus loss, binding capture, and owner changes still cancel immediately. Explicit setting false selects the prior immediate OS-event path.

The current-source headless gate is `tools/nwn63/keyboard_frame_gate_test.gd`, run with `.tools/native-core/Godot_native_core_e_win64.exe --headless --path . --script res://tools/nwn63/keyboard_frame_gate_test.gd`. It passed 16/16 checks. Two actual `_input` W key-down events, including an echo, caused one drive and one `predict` callback at the frame boundary; the immediate fallback caused two. The second flush in the same frame caused no second solve. The held key still caused a preview at 250 ms and a wire refresh at 500 ms. Release sent stop immediately without a preview; a reentrant key admission waited for the next frame; a changed actor identity canceled without commanding the replacement. `Node.can_process()` remained true for the owner flush even though the keyboard's own `_process` was disabled.

This check found idle `flush_input_frame()` was calling `update_input()` on every empty frame, which called `stop()` and incremented the stop generation. It now returns when there are no held keys, admitted events, dirty/pending input, moving state, or prediction owner. An active owner or queued event still reaches the original validation and cancellation gates. This removes idle work and generation churn; it is not an additional measured path-solve or FPS saving.

The earlier matched graphical ABBA burst captured 119 previews/120 packets with immediate OS handling versus 60 previews/61 packets with admission, saving 59 of each across the burst. Burst median moved from about 12.108 to 10.4705 ms and p95 from about 13.0825 to 11.231 ms; whole steady mean moved about 0.121 ms. Evidence: `.cache/nwn63/frame-input-live-graphics-e/abba-review-b.json`. That capture predates this idle-only change and does not establish a new FPS result.

## Normal-client acceptance

1. Confirm the actual normal-client launch selects admission on initial world entry and after an area transition; confirm explicit false restores immediate handling without a stuck key.
2. With real mapped W/S, A/D, Q/E, and Shift input, verify held movement, turning, walking, opposing-key stop/resume, repeated key-down, and release. For same-frame repeated downs, inspect counters and require at most one preview/drive scheduling tick per owner frame; keep the 250/500 ms held cadence.
3. Verify focus loss, text entry, key-capture UI, actor change, and area transition stop the old actor promptly; late preview completions or ACKs must not rearm it. Reentrant event admission belongs to the next frame.
4. Compare keyboard movement, click-to-move, camera and scene output on Arelith. Click-to-move is a separate route; this change cannot establish its cost or parity. Check authoritative movement and sequence/ACK behavior, not only local prediction.
5. During a coordinated normal-client capture, inspect keyboard preview counts and frametime tails alongside collision/path spans. The current headless gate proves scheduling, while a live trace is required to claim a normal-client performance gain or close NWN-63.

# Native container inventory: core acceptance

Actual primary container status now opens the native inventory automatically.
A seven-by-five container repository replaces equipment while the player's
ten-by-six backpack remains below it. Native Previous/Next/Close controls use
the existing container request sender and reviewed low-byte page policy.
Player and container page selections remain independent. Both transfer
directions use the existing authoritative item-action sender; no local item
ownership or item creation is inferred from a successful send.

Container contexts have a separate monotonic serial. Status messages retire
old selections even when a chest ID is reused. In-flight page results cannot
change a replacement context. Late metadata cannot reopen a container the user
closed; a newer server context can open it. Authoritative page-count shrink
clamps the visible page. Alternate/associate containers stay separate.

## Installed PLT compatibility finding

The first successful transfer screenshots exposed missing Woodsman Outfit
icons. `ipm_chest050` is an installed 64-by-128 PLT with DWORD8=11; the existing
decoder rejected that header against its ten-palette limit. Read-only evidence
in `reports/container-installed-plt-v1.json` records 16,408 bytes, SHA256
`cb03c144be92f073622d5a24a7b9ba2521834c9473c3c852a9ba179ad72b5046`,
and only palette IDs 0,3,5,6 in its pixels. No original image bytes were saved.

`tools/plt-compatibility.mjs` adds an isolated-build adapter for this observed
header-11 variant only after validating dimensions, full pixel storage and
pixel palette IDs below ten. Pixel data/palette sampling are unchanged; other
unverified header variants and extra pixel layers remain rejected. Authored
tests prove byte-identical output to the existing header-10 path, unchanged
results for every previously accepted header value, bounds checks and source
identity. The original `src/bioware_plt.js`, working JS client and dist remain
unchanged. Build v25 records these identity checks.

External comparison: the [xoreos PLT loader](https://raw.githubusercontent.com/xoreos/xoreos/master/src/graphics/aurora/pltfile.cpp)
also uses ten palette images and constrains this header value. It does not
prove support for this installed variant. The compatibility decision here is
an inference from the actual installed asset, unchanged pixel semantics and
the successful original-icon render, not a fresh original-binary oracle or a
claim of complete PLT format parity. No external implementation was copied.

Failed/weak earlier evidence is preserved: v1 checked the acknowledgement in
normal rather than system chat; v2/v3 passed transfer checks but lacked a
mandatory icon assertion. Their screenshots/diagnostics exposed the decoder
failure. V4 requires the icons and passes after the isolated adapter.

## Remaining scope

Stores, associate/alternate repositories, container items nested within items,
concurrent users, item rejection/destruction, last-page transfers and pending
container jobs during actual transitions/reconnect still need native acceptance.
Container lid/open-close animation and full placeable animation/picking fidelity
are not proved by these UI checks. Physical mouse dragging end to end remains
distinct from the verified native drop callbacks. The remaining inventory,
character/map/journal/level-up/NUI/settings/audio checklist still applies.

The local server remains running; no Arelith connection occurred. The editor
was preserved. These functional room checks do not establish complete moving
world fidelity or sustained >=60 FPS performance. The migration goal is active.

Subsequent merchant-core acceptance is recorded in [NATIVE-STORES.md](NATIVE-STORES.md).
The store/failure/alternate-container limits above remain broader than that core.

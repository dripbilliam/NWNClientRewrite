# Multiplayer server content

2026-10-19. The character-record/inventory UI pass is waiting on this resource foundation. UI labels, descriptions, icons and rules must come from the connected server's selected content. No Arelith spell/class/race IDs or content URLs are embedded in this implementation.

Implemented `server-resources` → selected manifests and wire HAKs → alternate TLK → active decoder tables → character admission. A custom server does not need a locally installed campaign NWM: area state is already replicated by the server. An explicitly advertised NWM remains a required resource. Required failures prevent character upload and remain diagnosed; optional additional manifests obey their native flag and language filter.

`electron/nwsync_content.mjs` reads the advertised NSYM v3 catalog and deduplication mappings, downloads NSYC resources from its repository, verifies decompressed SHA1 and size, and atomically caches the original compressed objects. None, zlib and dictionary-free Zstandard are supported. HTTP work is bounded to four concurrent requests by default, with cancellation, progress and per-object limits. The cache is under application user data; it is never written into the original install. This private cache is a content-addressed directory, not a byte-for-byte replacement of the game's SQLite schema.

The original user profile's `nwsyncmeta.sqlite3` and `nwsyncdata_N.sqlite3` can be reused. `nwn-content-reader.exe` opens them with `SQLITE_OPEN_READONLY`; it also performs bounded Zstandard decompression outside Electron's event loop. This is our helper compiled from the existing public SQLite/Zstd sources, not a game binary or injected component. Build with `scripts/build-content-reader.ps1`; the build records input hashes and its output digest. The original database test checks file hashes before and after use, including a Unicode directory path.

Admission checks cached availability through the native database catalog or small private object headers. It does not decompress an entire multi-gigabyte collection on every join. Every demanded object is verified; new downloads are verified before caching. Active protocol rule tables are demanded and decoded before character admission. Corrupt cached content is diagnosed and refetched when a repository is available. Missing/corrupt/unsupported required content never substitutes a lower-priority stock resource.

`electron/server_resource_context.mjs` mounts the server's explicit HAK list, instead of rediscovering a potentially different list from a local module IFO. The lookup order is selected NWSync manifests, user/installed HAKs, module, ordinary loose overrides, localized/retail/base KEY catalogs. Later distinct manifests override earlier ones. HAK order is preserved within its native installed/user priority group. Repeated registrations do not promote a source. Resource, TLK, table, model, texture, font and UI caches belong to their connection/resolver owners; disconnect cancels pending content work and releases the helper. Existing network UI/scene owners already reset their asset and rule caches on connection entry.

`CTlkTable::OpenFile` first tries a registered resource before a physical TLK path. Custom TLKs can therefore come from manifests, HAKs or the module, not just loose files. The actual selected primary/female headers are checked before admission. The custom string-reference bit and server runtime TLK overrides retain their existing native ownership.

Native SQLite schema/query strings are retained in `rea-server-resource-db-schema.json`: `manifests`, `manifest_resrefs`, `manifest_cache`, `shards`, and shard `resrefs(sha1,data,size,...)`. The reader uses their resource/name/hash relationships, not guessed server-facing IDs.

`scripts/inspect-native-resource-priority.py` executes original `AddKeyTable` instructions in the existing isolated emulator. Allocation, catalog construction, string comparison/copy and reload are captured dependencies; original grouping, insertion scans and writes execute unchanged. **35 cases** cover all eight installed/user placements for three HAKs, zero through three additional manifests, and duplicate registrations. They validate lookup order, not the full native archive/downloader implementation.

The public wire/storage formats are also documented by [the NWSync author](https://github.com/niv/neverwinter.nim/blob/master/neverwinter/nwsync.nim), [the compressed-buffer implementation](https://github.com/niv/neverwinter.nim/blob/master/neverwinter/compressedbuf.nim), and [Beamdog's repository writer](https://github.com/Beamdog/nwsync/blob/master/private/libupdate.nim). [Arelith's FAQ](https://nwnarelith.com/faq) confirms its custom content uses NWSync. These sources establish format/use, not acceptance of our client on Arelith.

## Validation and remaining scope

Focused tests cover original requirement packets; original priority executions; aliases; bad headers/counts/mappings/hashes; empty resources; all three compression paths; cache corruption/recovery; cancellation; offline reuse; two different server table sets; active class/skill/spell decoder metadata; language and optional manifest selection; legacy HAK and NWSync TLKs; malformed primary/female TLK rejection; stale resource reads; and existing session/IPC/UI boundaries. **95 checks pass** in `server-content-focused-v6.txt`; the final closed-owner lifecycle guard also passes all10 content tests in `server-content-lifecycle-v1.txt`. The earlier v5 run's one EBUSY was a test/helper-rebuild overlap; v6 runs after the build completes and has no failures.

`scripts/smoke-server-content.cjs` runs production owners in the actual Electron33.4.11/Node20.18.3 process. Synthetic local HTTP manifests replace skill/spell tables and supply a custom TLK plus a Zstandard object; original Prelude and character UI model remain read-only fallback resources. Offline reuse also passes, with zero diagnostics. It does not join, move, disconnect or modify the current game/server session. Final result: `server-content-electron-v2.json`; renderer build `server-content-build-v2.txt` succeeds with `index-BCPMLm-D.js`.

Actual Arelith initial login, authenticated/public resource advertisement and a completely fresh large-collection download/read now pass:97,820 objects/3.12GB transferred,432 rule tables and custom TLK parsed, then production resolver/rule/TLK selection verified against those same downloaded hashes. No original NWSync content was reused. See [the cold connection evidence](arelith-cold-connect.md). This does not establish server-vault selection, world entry or public-server gameplay parity. The private cache does not implement native housekeeping/pruning or migration of its files into the original SQLite cache. Additional compression dictionaries/manifest versions are explicitly rejected. Steam Workshop/custom filesystem-alias discovery, development/NWSync development overrides, server-vault character selection and server-aware character creation remain separate work. No complete multiplayer or UI parity claim follows from these checks. The character record/inventory layout investigation and derived hook measurements remain available for the next UI pass.

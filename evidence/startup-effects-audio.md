## Audio format / implementation inference

The installed reward resource `gui_spell_mem` is RIFF WAVE type 0x11, mono IMA ADPCM, 44100 Hz, block alignment 1024, 2041 samples/block, fact count 60645. Electron/Chromium's direct `decodeAudioData` failed on it during the first renderer check. The replacement decodes this format in memory into channel PCM, using header predictors, low-first nibbles, four-byte channel groups, clamping and the fact length. Other encodings use browser decoding and report failures.

Format reference: [Microsoft Multimedia Standards Update, revision 3 (1994), IMA/DVI WAVE section](https://www.mmsp.ece.mcgill.ca/Documents/AudioFormats/WAVE/Docs/RIFFNEW.pdf). [RFC 3551 §4.5.1](https://www.rfc-editor.org/rfc/rfc3551.html#section-4.5.1) distinguishes WAVE's initial sample and low-first ordering from RTP DVI4. Decoder sample equality was independently validated with Python 3.12 `audioop`, with nibble-swapped payloads. This verifies decoded samples, not native audio mixer parity.

Browser audio can be suspended until user input. Decoding/queued-output/played state is tracked separately; user input resumes output without blocking the script pump. Resources are cached per loaded module; session replacement stops sources and discards pending audio. Spatial attenuation, ambient sounds/music, dialogue voices/SSFs and BMU-specific handling remain open.

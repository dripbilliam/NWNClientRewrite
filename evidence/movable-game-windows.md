# Movable standard game windows

## Concurrent multiplayer windows

Standard multiplayer menus now have independent `NetworkPanelWindow` instances, coordinated by `NetworkPanels`. Character record, map, journal, spellbooks, Options and level-up can coexist with inventory, examination and conversation. Opening or toggling one menu leaves the other windows and their native subscriptions open. Character/journal close notifications still apply to their own windows; connection/area resets close all views.

Clicking a window raises it; completing a title drag raises the dropped window again. Per-menu ranks survive replacement DOM from replicated updates, including the separate known/preparation spell windows. Ranks are periodically rebased within the standard-window range; the radial menu retains its browser top layer. Escape and conversation number keys respect the front standard window, so a conversation behind a menu is not aborted by closing that menu. Existing position persistence and outside-click/WASD routing remain in place. NUI retains its existing window owner.

## Original position implementation

`MovableWindows` owns presentation coordinates only. Drag a title bar to move the character record, map, journal, options, level-up, inventory/paired store or container, examination, conversation, and local fallback panels. Known spells, preparation and spell examination use separate positions. Native/server NUI geometry remains under its existing owner.

Positions are saved on drag completion in `nwn.ui.windowPositions.v1`, keyed by menu type, within the client profile. Reopening, shared-host menu changes, and replacement DOM from replicated updates restore the matching position. Coordinates are relative to the game viewport; a resize clamps displayed positions without destroying the preferred stored position. Oversized windows retain a reachable top/left edge. Only coordinates are stored, not character/server information.

CSS translations preserve native sizing, flex layout, scrolling and item hit boxes. Pointer capture keeps title dragging continuous outside the title; controls/links/editable fields/draggable item sources do not start window drags. Completed drags consume their resulting click so they cannot issue world movement. Other clicks and WASD retain existing routing. Focused standard windows raise within a bounded stacking range below the radial top layer. A title was added to the multiplayer conversation for dragging. Mutation/resize observers schedule work only when relevant UI/layout changes, without a permanent frame callback.

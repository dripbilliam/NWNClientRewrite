## Implemented architecture

`ModuleSession` owns a single `GameObjectArray` for the loaded module. ARE/GIT membership follows `Mod_Area_list` in the IFO, excluding unused ARE resources in HAKs. It indexes module/area objects, creatures, doors, placeables, waypoints, triggers, encounters, stores, sounds, ground items and owned inventory/equipped items. Inventory references point to owner OBJECT_IDs; equipment slot masks come from GFF structure-type metadata, kept separate from game IDs. Complete GIT instances retain their authored fields; absent fields do not inherit blueprint variables merely because TemplateResRef identifies their origin. Store InventoryRes entries explicitly resolve their UTI.

An area's `WorldObjects` is a membership/render-binding view, sharing the exact simulation records. Actions, radial requests, picking, script stacks, event subjects and player/area references use the same numeric OBJECT_ID. Source placement labels such as `area:door:index` identify resource provenance only. Rendering a new area does not allocate another player or recreate the module's simulation state. Disposed renderer bindings are released while locals, cached links, journal state and door state survive.

Local allocation follows the native allocation policy, but exact native construction order is not yet reconstructed; locally assigned numbers are **not claimed to equal IDs from an independently running NWN session**. A future network adapter must import server objects using the external/explicit insertion paths, retain authoritative handles, apply native namespace conversion at packet boundaries and avoid local gameplay authority. JavaScript records are a semantic implementation, not a native C++ memory-layout/ABI replacement.

NCS files and the command-signature table load directly through existing module/HAK/game precedence. There are no script-name-specific gameplay substitutes and no copied installed script/assets in this repository. Unsupported engine calls throw `script@PC` errors; earlier script effects/queued commands remain, making partial execution visible. They are not successful no-ops.

## Boundaries and next work

This is a first VM/object/door-script execution slice, not campaign startup compatibility or multiplayer support. Witch's Wake's entry cutscene reaches unsupported camera/character/encounter calls; Brogan's area-entry reward reaches `GiveXPToCreature` at `ww_enter_brogan@0x471`, and its queued sound reaches `PlaySound` at `0x438`. The runtime reports both. The actor is still an explicitly declared normal preview PC, not a loaded BIC character; XP/class/race/faction/combat/effects/dialogue cannot be invented to unblock those scripts.

The native module/client/area startup sequence, general event reentrancy, creation/spawn/destruction/heartbeat scripts, trigger traversal, timer calendar behavior, NPC actions, parties, journal timestamps/history/UI, JSON and other engine-structure operations, script debugging/parameters, saves and full safe-location/pathfinder behavior need further work. Exit scripts observe old area membership and enter scripts the destination in this slice; the full native scheduling order is not yet established. Journal category/state validation and monotonic updates support the tested single-PC entries, not all quest/party semantics. Inventory/equipment objects are indexed with IDs and provenance; their gameplay systems are not implemented.

Next: load a real player/BIC identity and map the character/XP engine state required by startup, then implement the blocking XP/audio/cutscene calls against native evidence. Extend the shared action/event lifecycle and object creation/destruction APIs incrementally instead of introducing a separate multiplayer identity store.

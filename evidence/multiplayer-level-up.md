# Manual multiplayer level-up

## Level-up opening latency, 2026-10-20

Observed in the replacement source: every `NetworkLevelUpView.open` waited for the begin response, transferred/parsed both TLKs, then called the full `loadCharacterRules`. That loader included unrelated combat/item/appearance tables and serial reads across all class dependencies. Nothing retained these resources when closing the wizard. This explains avoidable client work; the duration of the user's Arelith server reply has not been measured here.

The wizard now loads only progression tables and the eight class-table types its calculations consume, deduplicating names and limiting dependency reads to twelve concurrent requests. Preparation overlaps the fresh server begin request. A WeakMap keyed by the connection's world retains parsed rules and text across wizard closes/area changes; a replacement connection uses its own callback and cache entry. Preparation begins in the background when replicated state makes level-up available. Failed preparation can retry on opening. Character snapshot, class availability and token still come from each fresh server begin; no choices or canonical character state are cached or inferred. Cancellation/stale-control guards remain. Diagnostics `network.level-up-resources-ready` and `network.level-up-open-ready` record resource duration and separate open-time resource/server/total waits without character data.

`creation-experience-levelup-latency-v1.json`: actual Chromium IPC using installed stock resources measured old rule preparation **259.6 ms /167 reads**, focused loader **30.6 ms /115 reads**, and cached reopening **1.3 ms /zero reads**, with a captured immediate server callback. Shared progression tables and every retained class table matched the full loader. These are a single warm-installed-resource comparison, not original-client or Arelith timings; initial TLK transfer is outside this loader comparison. UI assertions cover parallel preparation/server request, reuse within a connection, reload for a new world, prewarming, cancellation, retry and server denial. Existing actual UI allocation/feat-group/wizard/submit checks pass; 72 focused loader/model/wire/session/IPC tests pass. Production build is `index-DYLZ3k8v.js`.

The running replacement PID54716 was opened earlier with `index-zJ6YIfau.js`. It was left running so this change does not interrupt the user's session; the new build takes effect on restart. No automated public-server join/chat or fresh live-server test was performed. The broader goal remains paused.

## Scope still open

This makes the basic manual flow usable, not all level-up presentation identical to the original wizard. HP currently uses the active class maximum hit die; original roll/max-HP preference and special hit-die feat combinations need further parity work. Spontaneous known-spell additions are supported; an optional replacement-spell chooser is not exposed yet. Unusual prestige/epic feat and spell-progression combinations need broader original-code and server validation. Singleplayer still has its separate progression owner; this change does not add a singleplayer manual wizard. Arelith server acceptance is not claimed from the local result. The larger active creation/performance goal remains active.

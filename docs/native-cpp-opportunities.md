## Evidence and current runtime

The latest owned DensePerfCX live review ran the grouped-rig release executable at **3440×1369**, with particles on and a separate render thread. This audit uses the **240-frame** profile ending at native tick **215,316 ms** for the steady estimates below. ## 1. World motion and pose dispatch

**Path.** Received world snapshots and deltas feed `LiveWorld.receive` and `receive_delta`. The world callback calls `NetworkMotion.update`, then `apply_poses`, `apply_pose`, combat update and motion finalization. `NetworkMotion.update` iterates Dictionary rows, advances path and correction state, resolves facing targets, and emits changes in an existing order. `apply_pose` looks up the visible instance and retained row, converts coordinates and facing, computes playback speed and dispatches animation and effect observations. It guards unchanged transform writes already. Static objects use receive or admission rather than the ordinary per-frame creature loop. The live world mean was **3.49 ms**, including **1.34 ms** motion and **1.73 ms** pose inputs. [World callback](../godot-client/systems/native_render/live_world.gd#L700) · [Pose dispatch](../godot-client/systems/native_render/live_world.gd#L634) · [Motion update](../godot-client/systems/network_motion.gd#L379)

**Move.** Start with an extension-owned typed motion table keyed by the existing object lifetime, plus compact ordered update records at receive. One `advance_motion` call per world tick would perform the existing numeric gait, path stepping, correction and bearing calculations and keep fractional milliseconds and F32 operations in the same order. Keep this first batch serial on the scene thread. A facing target can read another row's updated position, and a path step can depend on live support. Measure those calls separately before extracting any independent worker ranges. Add a second output to the same owner for position, heading, dirty-transform bits and current gait data. `apply_pose` consumes that output instead of constructing a second representation and repeating mixed Dictionary reads and per-actor math. Emit or consume dirty rows in the old order. Keep Node3D writes, combat events, signal delivery, effect observations and lifetime/authority changes with their existing scene owners.

**Partial work and test.** Already-active shortcuts cover stationary and fixed-bearing rows, unchanged transforms, indexed collision and delta reindexing. The older **5.18 ms** support share and **74.94 ms** Tracy reindex spike identify workloads to retest. They describe older source or a different scene and cannot be added to the current motion scope. Compare ordered results, signed zero where relevant, path progress, correction cues, facing, collision outcomes and animation speeds through owned idle, paced NPC movement, keyboard and click-to-move, and area transitions. Measure script-to-extension calls, temporary Dictionary/Array creation, support query counts, motion CPU, pose CPU, total frame p95 and live state memory. The first candidate should preserve the proven spatial admission and reduce row work, with a separate typed support batch only if the remaining path-step timer warrants it. [Movement and support measurements](native-pipeline-comparison.md#owned-denseperfcx-movement-and-bounds-capture) · [Indexed collision delta](../godot-client/systems/native_render/drive_collision_indexed.gd#L258) · [Historical reindex trace](../godot-client/tools/nwn62/drive-reindex-checkpoint.md)

## 2. Effect clocks and dispatch

**Path.** `EffectWorld.advance` resolves replicated, queued and private effect lifetimes and prepares models. The ordered loop in `VisualWorld._process` advances active effects and then retiring effects. A local visual can refresh bindings, advance its clock, run the owner selector and publish a phase status. Area visuals use their own runtime advance. In the live sample, **1.36 ms** of the **1.50 ms** effects callback was in the visual update. The nested clock scope was **0.93 ms** and bindings **0.14 ms**. [Effect owner](../godot-client/systems/native_render/effect_world.gd#L252) · [Ordered visual loop](../godot-client/systems/visual_world.gd#L285)

**Move.** Compile immutable per-effect timing parameters into native typed records once on admission. In a GDExtension, advance eligible numerical clocks and phase accumulators, returning ordered typed transition intents. Keep scene-bound attach/detach, resource lookups, audio, selector orchestration and callbacks with `VisualWorld`. Retain the phase ordering and owner lifetime checks. Split clocks whose transitions can call back synchronously into the scene from clocks that can safely advance as a batch. Reuse dirty binding or revision state and avoid allocating phase payloads until a field actually changes. Measure how much of the clock timer is arithmetic and how much is downstream notification before assigning a saving.

The timer wraps `VisualClock.advance`, including its call into `VisualPhases.update_milliseconds` and retirement notification. Retain fractional elapsed time, wrapping millisecond deltas and exactly-once retirement. Instrument the phase runtime separately from the wrapper before moving the inner update. [Clock implementation](../godot-client/systems/visual_clock.gd#L30) · [Phase update](../godot-client/systems/visual_phases.gd#L167)

**Partial work and test.** Effect membership is already indexed and sources are limited to owners with pending or active effects. The old per-type selector prototype reduced calls **192 to 96** in a two-type fixture, while transition probes found observable ordering differences. Use that as an eligibility warning. Start with pure clocks and match exact event order, bind state, suppression, reattachment, expiry, cancellation and competing types, including transitions on the same frame and area visuals. Test the single-type DensePerfCX load and a local multi-type fixture. Compare advance calls, phase-status updates, callback order, effect CPU and total frame p95. [Selector trial and ordering gap](native-pipeline-comparison.md#per-effect-selection-dispatch)

## 3. Requests, caches, and NWSync

**Path.** The JS session chooses and admits NWSync content. A Godot catalog worker prepares the ordered source stack and shares resident bindings with asset workers. Installed archive, override, module, Workshop and NWSync precedence determine one physical provider. `NwsyncStore.manifest` calls the installed reader before the decoded index reuse gate. The installed SQLite helper is already compiled C, with native resource-index methods available for supported catalog parsing and accounting. Blob lookup, decompression and verification are separate from copying and decoding the manifest export. The main-thread asset owner receives results and publishes resources after the worker stage. [NWSync JS owner](../electron/nwsync_content.mjs) · [Catalog preparation](../godot-client/systems/native_data/session_catalog.gd#L18) · [Manifest demand](../godot-client/systems/native_data/nwsync_store.gd#L90) · [Compiled reader](../scripts/native/nwn_content_reader.c) · [Native capability gate](../godot-client/systems/native_data/resource_index_backend.gd#L5)

**Move.** The best first change is a for-this-source-generation lookup before exporting data. Preserve the existing source generation and SHA checks. Extend the compiled reader with a small installed-index identity or resident-handle response and keep the decoded binding and shard-membership table behind a retained owner. Only a miss or revision change materializes or parses the full index. Replace per-blob cross-process reads with batches by known shard if copy and call timing still matters after the index gate. JS retains download, admission, progress and cancellation. Godot retains source priority and active area publication. SQLite reads and download waits have their own elapsed times.

The installed-cache fixture transferred **20,184,004 bytes** again and spent **184–222 ms** on a resident remount. Fresh JS admission also exported **4,640,004 bytes** of hash inventory and measured **548–723 ms**. The candidate should count manifest exports and bytes per owner, hash-inventory copies, shard probes, worker CPU, peak memory and first playable time. Match fresh process, resident remount, reconnect, a changed or missing manifest, corrupt blobs, aliases and module/override precedence. Test with the owned SQLite and NWSync fixtures. [Installed NWSync measurements](render-flow-measurement-ledger.md#installed-nwsync-admission-mount-and-demand)

The JS seams are `NWSyncContent.findManifest`, which coalesces promises inside one owner, and `loadManifest`, which crosses into `NWSyncReader.manifest` on an installed-cache hit. `ensureBlob` separately retains the reader's hash inventory. The reader accumulates chunks and concatenates them before parsing rows. A resident descriptor answers the same request without rematerializing that buffer. [JS admission](../electron/nwsync_content.mjs#L79) · [Hash inventory](../electron/nwsync_content.mjs#L53) · [Reader and buffer assembly](../electron/nwsync_reader.mjs#L12)

**Decode and cache.** `AssetService.request` assigns worker jobs. `_work`, `decode_uncached` and `model_raster` return prepared data to the publication owner. Model bytes can still be looked up and hashed before a warm prepared hit. Add a retained name-to-prepared binding keyed by catalog identity, selected provider, resource revision and full decoder options. A warm hit could bypass the worker hash and wrapper allocation. The raster worker already uses this pattern for installed rasters and removed a historical **53–55 ms** of repeated hash work across 150 references. For cold compiled MDLs, measure the parser's CPU separately from demand, dependencies and preparation. A native worker decoder could write vertex, index, controller and key data directly into packed buffers used by the current builder. Keep source rules, validation, options, cache leases, scheduling and publication with their current owners. Verify exact geometry, animations, light and emitter metadata, corrupt input rejection, prepared cache invalidation and memory under cold actor and terrain loads. Use the four existing models and add inherited, ASCII and emitter-heavy fixtures before choosing a broader port. [Asset worker](../godot-client/systems/native_data/asset_service.gd#L89) · [Existing raster binding](../godot-client/systems/native_data/asset_service.gd#L300) · [Measured warm model demand](render-flow-measurement-ledger.md#installed-model-decoding-and-warm-bundle-reuse) · [Raster trial](render-flow-measurement-ledger.md#installed-texture-request-and-publication-reuse)

The exact parser seams are `BinaryModel.parse`, `read_node` and `read_mesh` for binary models, and the worker's `ActorModel.parse` dispatch for packed actor and static render models. Keep existing GFF, 2DA, TLK, tile definitions, walkmesh, sound and palette consumers on the same resource path. The asset service records a **2.8 MB** 2DA expanding to **40.8 MB** when serialized with aliased row views. It already avoids that persisted derivative. For a residual table CPU hot spot, time native parser coverage and the cost of building keyed/ordered views before porting more. [Binary MDL parser](../godot-client/systems/native_data/binary_model.gd#L24) · [Asset decoder dispatch](../godot-client/systems/native_data/asset_service.gd#L595) · [2DA cache policy](../godot-client/systems/native_data/asset_service.gd#L571)

## 4. Rig application, inherited clips, and appearance

**Rig work already shipped.** Ordinary actors create annotated manual AnimationPlayers. The standard release mixer combines eligible position and rotation writes while preserving local-transform notifications and frame interpolation on their existing path. The candidate removed **15%** of propagation calls and passed **3,976** exact checks. Eight alternating windows in one release process measured **9.18 ms** without grouping and **8.85 ms** with it. The current route retains per-actor clocks, typed clip templates and the existing engine mixer. The native-only inherited-gait replacement measured **1.73–1.76 ms** against **1.33–1.40 ms** for the existing player in its own fixture. Same-frame exact primary phase matches were only about **5%**. A whole-pose sharing layer or switching scripting languages around `advance` offers little leverage at those frequencies. The **2.04 ms** live actor-animation timer overlaps the **2.29 ms** rig timer, and the **0.019 ms** attachments timer supplies a small first target. Larger skin-specific claims need a real skinned workload. [Rig and prior alternatives](rig-pipeline/README.md#previously-resolved-or-rejected-avenues) · [Active mixer patch](../godot-client/native/engine_patches/animation-mixer-batch-position-rotation.patch) · [Same-process test](../godot-client/reports/rig-release-toggle-a.json)

**Appearance candidate.** `LiveWorld.signature` and the worker metadata signature include the equipment and palette-bearing appearance payload. A new signature can queue a replacement. `CreatureStream._plan_object` turns palettes into piece-specific model options, `AssetService` prepares palette rasters, and `ActorInstance` constructs meshes, rig bindings and attachment anchors. The initial investigation found existing mesh source model and part metadata suitable for material targeting. No timed in-place recolor has been recorded. [World signature](../godot-client/systems/native_render/live_world.gd#L401) · [Worker signature](../godot-client/systems/native_data/world_snapshot_metadata.gd#L19) · [Piece planning](../godot-client/systems/native_render/creature_stream.gd#L163) · [Actor material and source identity](../godot-client/systems/native_render/actor_instance.gd#L293)

Prepare a palette-only plan before actor assembly once a changed packet is admitted. Match owner lifetime and ordered resolved models, Part topology, animation/form, skin bindings and attachments. An unchanged topology would reuse model geometry and the AnimationPlayer. Reuse worker-side palette preparation and publish only replacement material references onto existing meshes through the scene-thread actor owner. Shared materials and mesh resources remain immutable. A remove or newer appearance revision cancels an older pending publication. The full assembly route handles actual shape or topology changes. A C++ boundary is useful for a pure palette-expansion or per-piece mapping kernel only if those residual CPU parts remain large. Test one real recolor, equipment palette, head/shape change, update during motion and cast, rapidly superseded colors, actor removal and area travel. Check exact rendered colors and alpha, current clock and effect anchors, worker requests, meshes built, bindings allocated, publication time and peak memory. ## 5. World snapshots, publication and Electron

**Path.** The Electron bootstrap handles settings and protected login, then starts the JS host and Godot. The host owns the original-server session, command pump, and acknowledged world mirror. Its loopback transport writes serialized rows as scoped begin, chunk and end frames. Godot accepts the stream in `NativeSessionWorld`, stages metadata and commits through `NativeLiveWorld` and `LiveWorld` before publishing terrain, actor and object nodes. Script metadata can already run on a worker. Scene publication owns lifetime, current resource generations, terrain before player readiness, staged commit order and acknowledgements. In the recent live window `raw-world-end` averaged **0.146 ms** across captured frames and steady adoption **0.004 ms**. An older owned entry had a **328–390 ms** staged acknowledgement interval and **18–22 ms** largest individual commit steps. The latter warrants a loading-hitch trial after profiling the current seam. [Bootstrap](../godot-client/tools/native-session-bootstrap.cjs) · [Host publication and ACK poll](../godot-client/tools/native-session-host.cjs#L980) · [Godot receiver](../godot-client/native_session_world.gd#L655) · [Staged commit caller](../godot-client/native_live_world.gd#L184) · [Worker metadata](../godot-client/systems/native_data/world_snapshot_metadata.gd#L80) · [Area entry timings](render-flow-measurement-ledger.md#area-entry-terrain-placement-and-first-control)

**Move.** Use the existing changed-row and verified-packet boundaries before expanding native code. A narrower proposal is a C++ worker reader that validates and projects a complete ordered batch into typed row IDs, lifetime tokens, poses and immutable visual-key fields. Pass one prepared packet through the existing commit gate. This could eliminate a reboxed row list, repeated extraction and redundant serialization of stable descriptors. Compare the already selectable worker implementations first and measure validation, projection, transfer and main-thread commit separately. Keep admission, authority, generation fencing, bounded sizes, stale and malformed packet handling, ACK order, visual publication and owner callbacks with their existing owners. Preserve cancellation and monotonic publication across backpressure and reconnect. Native encoding on the JS side is only useful if encode and copy time remains material after arbitrary data is replaced by a compact batch. In that case use a host-native addon for just the validated record codec, with the loopback protocol and Node session state still in control.

There is limited evidence for migrating the host for steady FPS. Across nine ready-world host samples, Node CPU consumption was a median **2.32% of one logical core** and a maximum **3.92%**, with event-loop utilization **2.27%** at the median. These percentages use CPU time divided by each sample's wall interval. They do not measure the Electron parent, server or Godot IPC latency. The Godot outbound queue in the final sample was empty with zero partial writes or would-block events. Host-to-client latency needs its own measurement. The useful next attribution is per-direction messages and bytes, event-loop delay, JS parse/encode CPU, waiting for socket delivery, Godot projection CPU and time to ACK, with report serialization measured separately. Exercise lobby/character selection, NWSync, chat and inventory floods, a large world packet, steady deltas, travel, and disconnect on an owned server. Keep login, credential storage, vault and settings paths as they are unless a named CPU hotspot appears. [Host write path](../godot-client/tools/native-session-host.cjs#L126) · [Script log publication](../godot-client/tools/native-session-host.cjs#L711) · [Command pump](../godot-client/tools/native-command-pump.mjs) · [Live process telemetry](../godot-client/reports/rig-apply-user-review-1795428199700.performance.jsonl)

**Already measured implementation gaps.** Two owned delta projections cut repeated perception reducer work by **0.262–0.327 ms per accepted delta**, and relevant light deltas cut light reconciliation by **0.549–0.557 ms per delta**. They are candidates for more precise script invalidation before a C++ port. Keep observer changes, late-ready bodies, removal, lifetime changes, asset completion and independent dirty signals. Verify the actual ready worker/default route and paired elapsed time in the client. [Delta results and conditions](render-flow-measurement-ledger.md#replication-perception-and-placeable-light-admission)

## 6. Terrain, meshes, textures, shadows and rendering

**Publication and scene admission.** `AreaStream` loads area definitions on a worker, drives asset jobs, and publishes templates and tile instances. `LiveWorld` adopts prepared object and actor batches with a scoped budget. Geometry, skin and material resources flow to the render server through the scene-owning thread. The historical owned entry published 100 tiles in **75–77 ms** of accumulated main-thread work across **23–24 callbacks**, with additional late visuals after player control. A plausible C++ boundary is a packed publication description from workers for repeated template and mesh surface construction. Keep asset identity, material use and ownership, anchors, new pose, lifetime, placement order and collision publication. Hand off prepared CPU buffers once per admitted batch. Where per-node installation or shader creation dominates, change admissions or reuse templates and materials before moving the caller. Compare cold empty cache and return, first tile and player control, complete visuals, peak callback, total main-thread work, worker CPU and RSS. A copied template and the underlying model request are separate cost units. Native packed templates and clones already appear in the reviewed runtime counters. [Terrain worker and publication](../godot-client/systems/native_render/area_stream.gd#L148) · [Tile batch publisher](../godot-client/systems/native_render/area_stream.gd#L309) · [Owned entry timings](render-flow-measurement-ledger.md#area-entry-terrain-placement-and-first-control) · [Observed runtime construction counters](../godot-client/reports/rig-apply-user-review-1795428199700.startup.json)

**Lights and shadows.** The standard focus-light collector in `focus_lighting.gd` supplies a native history solver through a script registry and publication layer. The live sample measured **0.42 ms** for the whole history callback. A typed input registry can accept create, change, remove, camera and dirty-transform events in batches and return winner or changed-color records in registration order. First measure the present collection/publication split and reuse the existing native registry option as a control. Keep authored mesh/light lifetimes, ties, color transitions, ranges and receiver behavior. Verify raw input visits, stable colors, fade endpoints and actual scene or render-server updates. CX shadow proxy reconciliation has a different workload. In the high-caster fixture, moving-scene polling was **2.77–2.87 ms**, compared with **0.67–0.72 ms** when all sources supplied notifications. Measure notification delivery and transform flush as part of the change. The useful next move is revision-driven caster inputs, avoiding full scans and per-mesh bridge calls. A native caster batch is later work if high-volume residual reconciliation remains. Keep caster admission, visibility, pass eligibility, fixed and moving ownership and resource retire order. Test both active and inactive shadow profiles. **Visibility and draw submission.** The script bridge and visibility/scene ownership choose which persistent objects or draw bundles need to publish. Forward+, culling, render-thread list construction, light clusters, shadow/depth draws and device submission are already native engine work. Measure visible IDs, stable instance and draw counts, LOD, alpha, depth, shadow pass membership, render-thread CPU, present waits and actual GPU timestamps. The older live `thenewone` draw CPU figure used another runtime and scene. An old **49.89 ms** worker-group wait nested under the render-thread update has no recorded producer identity. ## 7. Particles, weather and remaining effect bridges

The ordinary scene owner routes emitter setup and lifetime, camera, collision and lighting input into the particle backend. The native presentation owns simulation, pose reads for that path, sort, geometry and packing. In the live window the particle callback averaged **1.24 ms**, of which native presentation used **1.05 ms**, including **0.29 ms** simulation and **0.25 ms** geometry. The script lighting DTO timer was **0.074 ms**. This supports retaining the native kernel and targeting repeated input work. A useful C++ move is typed dirty light/transform rows consumed at one frame boundary if emitter-heavy captures show repeated GDScript array creation. Keep emitter registration, lifetimes, reset, source identity, clocks and shader submission at their owners. Use the identical emitter populations and visibility and particle geometry to validate. The optional CX and shared paths have different costs. An earlier owned CX profile included **1.15–1.33 ms** of shadow preparation within the particle callback. That belongs to caster/shadow reuse analysis. [Native particle presenter](../godot-client/native/particle_presentation.hpp) · [Native resident simulation](../godot-client/native/particle_resident.hpp) · [Current and alternate workload evidence](render-flow-measurement-ledger.md#emitter-geometry-publication-and-weather)

The script handoff is `ParticleStreamGroup.step`, which gathers light, fog and optional collision inputs and issues one `dispatch`. A per-emitter native call would increase overhead. Prefer making the existing batch reuse unchanged inputs. [Particle frame handoff](../godot-client/systems/native_render/particle_stream_group.gd#L212)

The previous animation-snapshot and geometry-worker experiments belong in the same comparison. A worker moves eligible independent vertex work from the critical thread only when it has a sealed pose and lifetime snapshot, avoids waiting for a newer frame, and keeps final resource submission with the renderer. Reusing snapshots for unchanged emitters is a work reduction even if overall FPS stays level. Inspect sorted point geometry, linked emitters, double-rail, fog/gamma, timeline parity, supported fallbacks, GPU cost and worker queue tails in each dated fixture. For outdoor weather, separate script plan and cover capture from the GPU lattice and retained authored effects. Defer a weather port until measured outdoor CPU work outside shader/render waits is large enough. The current client has no generated-grass bin workload equivalent to the stock scene, so stock grass timing provides no available script cost to port. ## 8. UI, icons, text and startup

The normal art request goes through `NativeUIArt` and `NativeItemIcons.request` or `request_model`. Bitmap assets are decoded and cached through the asset pool. A model icon uses the viewport, render-fence, readback and publication path. Busy first-use windows measured **0.92–1.53 ms** of readback per sampled frame and peaks of **2.84–5.92 ms**. Upload itself was **0.05–0.06 ms** in those windows. The readback waits for device work. Prioritize the partial `GuiArtSnapshot.capture` render-thread GPU copy with the existing viewport fence, followed by a compact texture-delivery batch for the downstream listeners if their time persists.
